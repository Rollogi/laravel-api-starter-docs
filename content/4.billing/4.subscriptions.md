An owner has one subscription, named `default` (`BillingAccount::SUBSCRIPTION`). It starts through Stripe Checkout or Stripe Elements, and changes through the [endpoints](/billing/endpoints) or the Stripe billing portal.

## Starting a subscription

There are two ways in:

- **Stripe Checkout.** `POST /checkout` with `{plan, interval}` answers a Checkout URL. The payer leaves for Stripe and comes back to the success or cancel page from [`config/billing.php`](/billing/extending#configuration). The subscription appears when Stripe's webhook arrives.
- **Stripe Elements.** `POST /setup-intent` answers a SetupIntent client secret. The frontend collects a payment method with Stripe.js, then `POST /subscription` with `{plan, interval, paymentMethod}` subscribes straight away.

`interval` is `monthly` or `yearly`. An unknown plan, one sold to the other kind of owner, a free plan, or an interval the plan has no price for is a `422` on `plan` or `interval`.

### Payment results

Subscribing and swapping answer `PaymentResultData`:

```json
{
    "status": "requires_action",
    "paymentClientSecret": "pi_..._secret_...",
    "billing": { "plan": { ... }, "subscription": { ... }, "paymentMethodType": "card", "paymentMethodLastFour": "4242" }
}
```

| `status` | HTTP | Meaning |
| --- | --- | --- |
| `complete` | `201` (subscribe), `200` (swap) | The payment settled |
| `requires_action` | `202` | Confirm `paymentClientSecret` with Stripe.js: 3-D Secure, or a declined card to replace |
| `processing` | `202` | A direct debit is on its way; the plan follows `invoice.paid` |

`billing` is the same summary `GET /` returns.

### Trials

A first subscription gets the plan's `trialDays`. An owner that has had a subscription get going pays from the start. A first payment that never went through (a subscription left `incomplete` or `incomplete_expired`) does not count, so the owner keeps the trial.

### One subscription per owner

Buying while the last subscription still stands in Stripe is a `409 billing-already-subscribed`. That includes one that is incomplete or past due, since both would bill. Change plan with `PATCH /subscription`, and settle an unpaid one through the portal.

## Changing, cancelling and resuming

- **Swap** with `PATCH /subscription` and `{plan, interval}`. Stripe prorates the change. The seat and metered prices of the new plan come across with it.
- **Cancel** with `DELETE /subscription`. The subscription runs to the end of the period, and the plan stays until then.
- **Resume** with `POST /subscription/resume` during that grace period.

A change is refused with a `409` when it does not fit the subscription's state; the [problem types](/billing/endpoints#problem-types) list each one. Notably, swapping a cancelled subscription is refused with `billing-cancellation-pending`, because Cashier's swap would quietly take the cancellation back: resume it first.

The services that call Stripe drop `WrapInTransaction`. Stripe has acted before anything could roll back, so the rows Cashier writes are kept to match it.

## Seats

A plan with `perSeat($priceId, included: 3)` bills a tenant for its seats beyond the included ones. A subscription starts with the base price, the seat price at that quantity (left out while the included seats cover everyone) and each metered price. `BuildSubscriptionItemsAction` assembles them, and a plan swap carries them across.

Who takes a seat is the `SeatCounter` contract's call. The default, `MemberSeatCounter`, counts every member of the tenant, less any that `billing.seats.exclude` names by a column on the users table. In the starter kit, exclude API keys with `['kind' => 'machine']` (see [Installation](/billing/installation#seats-in-a-kit-project)). A member with no value in the column still counts. For anything the config cannot say, [rebind `SeatCounter`](/billing/extending#who-takes-a-seat).

### Keeping seats in step

The package cannot hear the application's membership events, so the application dispatches the sync itself. In the starter kit, from an app module's `boot()`:

```php
use App\Modules\Tenants\Events\MemberJoined;
use App\Modules\Tenants\Events\MemberRemoved;
use Illuminate\Foundation\Bus\PendingDispatch;
use Illuminate\Support\Facades\Event;
use Rollogi\Billing\Actions\SyncTenantSeatsAction;

Event::listen(
    [MemberJoined::class, MemberRemoved::class],
    fn (MemberJoined|MemberRemoved $event): PendingDispatch => SyncTenantSeatsAction::dispatch($event->tenant),
);
```

`SyncTenantSeatsAction` sets the seat quantity in Stripe, prorated on the next invoice. It calls Stripe only when the quantity has changed, and does nothing without a subscription that may be changed, or on a plan without seats.

`billing:sync-seats` runs it daily for every tenant with a subscription, on one server and never overlapping, so a change the application missed is billed within a day. One tenant's failure is reported and the sweep carries on, failing the command at the end. The billing summary shows the seats being paid for as `subscription.seats`.

## Metered usage

A plan's `metered('api-calls', $priceId, meter: 'mtr_...')` bills usage that Stripe counts from meter events. The metered name is the Stripe meter's event name. Report usage from the code that uses the metered thing, on the queue:

```php
use Rollogi\Billing\Actions\ReportUsageAction;

ReportUsageAction::queue($tenant, 'api-calls');      // one unit
ReportUsageAction::queue($tenant, 'api-calls', 25);
```

`queue()` fixes the meter event's identifier (a UUIDv7) and time when the usage happens. A retried job is dropped by Stripe as a duplicate rather than billed twice, and the usage counts in the period it happened in.

Usage is sent only while the owner's current plan bills that name and the owner is a Stripe customer, so an owner on a free plan reports nothing. `meter:` is optional and is kept for reading usage summaries.

## Direct debit

Bacs (GBP), SEPA (EUR), ACH (USD, `us_bank_account`), BECS (AUD) and ACSS (CAD) debits take three to seven business days to confirm, and can still fail.

- **What the package already does.** It keeps the plan back until the first invoice is paid, and refuses a second subscription meanwhile. Elements answers `processing`, and the summary's `subscription.paymentPending` says so.
- **Offering them.** Enable them in the Stripe Dashboard and leave `billing.checkout.payment_method_types` empty (Stripe offers what suits the price's currency), or list them there.
- **Bacs** cannot use Elements SetupIntents, so offer it through Checkout.
- **Customer details.** [Rebind `BillingDetails`](/billing/extending#the-customer-stripe-sees) so the customer has the name, email and address a mandate needs.
- **Failures.** Listen for `AsyncPaymentFailed` and `InvoicePaymentFailed` to act on a debit that failed, and `MandateUpdated` for a cancelled mandate. Stripe does not cancel the subscription itself. See [Webhooks](/billing/webhooks#events).

Stripe's guides cover each scheme: [Bacs](https://docs.stripe.com/billing/subscriptions/bacs-debit), [SEPA](https://docs.stripe.com/payments/sepa-debit), [ACH](https://docs.stripe.com/billing/subscriptions/ach-debit).
