Stripe tells the API what happened through a webhook. The package does not use Cashier's own webhook route: events arrive through Core's [inbound webhook pipeline](/core/integrations), like any other integration.

## Setting up the endpoint

In the Stripe Dashboard, add a webhook endpoint at:

```
POST https://<your-api>/api/integrations/stripe/webhook
```

Put its signing secret in `STRIPE_WEBHOOK_SECRET`. Subscribe the endpoint to at least:

- `customer.subscription.created`, `customer.subscription.updated`, `customer.subscription.deleted`
- `customer.updated`
- `invoice.paid`, `invoice.payment_failed`
- `checkout.session.completed`
- `checkout.session.async_payment_succeeded`, `checkout.session.async_payment_failed`

Add any of the [other events](#events) your application listens for.

## What happens to an event

`StripeWebhookHandler` is registered on Core's `WebhookRegistry` under the integration name `stripe`. For each request:

1. The `Stripe-Signature` header is checked against `STRIPE_WEBHOOK_SECRET` with Stripe's own verifier, within `STRIPE_WEBHOOK_TOLERANCE` seconds. A missing secret, a missing header or a bad signature is a `401`.
2. The event is stored in `webhook_events` once per Stripe event id. A repeat is answered `200` and not applied again.
3. Core's `ProcessWebhook` job applies it on the queue, so a queue worker must be running.

Applying an event runs three steps:

1. **Cashier's handlers** keep the subscriptions, items and card details in step.
2. **Payment state.** The package tracks whether a subscription's first payment is still processing, in the `payment_pending` column. A Checkout completed unpaid sets it, and the async payment or the first invoice clears it. Stripe does not order its events, so an older state never overwrites a newer one.
3. **Billing events.** The package raises its own Laravel events, below.

The current-plan memo is cleared after each event, so whatever runs next in the job sees the new plan.

## Events

Every event raises `Rollogi\Billing\Events\StripeEventReceived`. The ones Cashier leaves to the application also raise a typed event, listed by the `StripeEvent` enum:

| Event class | Stripe event |
| --- | --- |
| `InvoicePaid` | `invoice.paid` |
| `InvoicePaymentFailed` | `invoice.payment_failed` |
| `InvoicePaymentActionRequired` | `invoice.payment_action_required` |
| `InvoiceFinalizationFailed` | `invoice.finalization_failed` |
| `CheckoutCompleted` | `checkout.session.completed` |
| `AsyncPaymentSucceeded` | `checkout.session.async_payment_succeeded` |
| `AsyncPaymentFailed` | `checkout.session.async_payment_failed` |
| `PaymentProcessing` | `payment_intent.processing` |
| `MandateUpdated` | `mandate.updated` |
| `SubscriptionPaused` | `customer.subscription.paused` |
| `SubscriptionResumed` | `customer.subscription.resumed` |
| `TrialWillEnd` | `customer.subscription.trial_will_end` |
| `ChargeRefunded` | `charge.refunded` |
| `ChargeDisputed` | `charge.dispute.created` |

Each extends `BillingWebhookEvent` and carries:

| Property or method | Holds |
| --- | --- |
| `type` | The Stripe event type |
| `payload` | The whole Stripe event |
| `object()` | The Stripe object the event is about: the invoice, session, mandate or charge |
| `account` | The `BillingAccount`, or `null` when Stripe names no customer, as for a mandate |
| `owner` | The account's owner (a `Tenant` or a user), or `null` likewise |

Listen from an app module's `boot()`:

```php
use Illuminate\Support\Facades\Event;
use Rollogi\Billing\Events\InvoicePaymentFailed;

Event::listen(InvoicePaymentFailed::class, function (InvoicePaymentFailed $event): void {
    // email the tenant's admins, flag the account, ...
});
```

::warning
Listeners run on the queue worker with no tenant set. If you need tenant-scoped queries, activate the owner's tenant first, for example with `tenancy()->set($event->owner)` when the owner is a `Tenant`. See [Multi-tenancy](/kit/multi-tenancy).
::

::note
Cashier's own payment-action notification needs a `Notifiable` billable, which `BillingAccount` is not. Notify the owner from `InvoicePaymentActionRequired` instead.
::

## Testing webhooks

The handler verifies real Stripe signatures, so a test configures `cashier.webhook.secret` and signs its payload the way Stripe does: a `Stripe-Signature` header of `t=<timestamp>,v1=<signature>`, where the signature is the HMAC-SHA256 of `<timestamp>.<body>` under the secret. Run the queue synchronously (the default in the kit's test suite) and the event is applied before the response returns.
