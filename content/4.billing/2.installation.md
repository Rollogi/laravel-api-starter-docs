A project created from the starter kit does not include billing. You add it when you need it.

## Requirements

- PHP 8.5 and `laravel/framework` `^13.32`
- `rollogi/core` `^1.1`, which the kit already requires
- `laravel/cashier` `^16.5` and `stripe/stripe-php` 17.3 or later, which Composer installs with the package
- access to the private `Rollogi/billing` repository

## Add the repository

Add a VCS repository to the project's `composer.json`, after the ones it already lists:

```json [composer.json]
{
    "type": "vcs",
    "url": "https://github.com/Rollogi/billing",
    "only": ["rollogi/billing"]
}
```

The GitHub token that already reads `Rollogi/core` reads this one too, as long as it has access to both repositories. Set it once with `composer config --global github-oauth.github.com <token>`, or through `COMPOSER_AUTH` in CI.

## Require and migrate

```bash
composer require rollogi/billing:^1.0
php artisan migrate
```

The package's `composer.json` lists `Rollogi\Billing\BillingServiceProvider` under `extra.laravel.api-starter-modules`, so the kit's `ModuleServiceProvider` registers it before the application's own modules. An app module can therefore declare plans in its `boot()` and rebind anything the package binds. See [Package modules](/core/package-modules) for how this works.

The migrations create:

| Table | Holds |
| --- | --- |
| `billing_accounts` | One Stripe customer per tenant or person |
| `billing_subscriptions` | Cashier's subscriptions, plus the package's `payment_pending` column |
| `billing_subscription_items` | Cashier's subscription items |

All three are keyed by UUIDv7 like the rest of the kit. Cashier's own migrations are not used.

A further migration creates the `billing.view` and `billing.manage` permissions on the `api` guard, and gives them to the global `admin` role if it exists. On a fresh install the kit's `RolesAndPermissionsSeeder` runs afterwards and gives `admin` every `api` permission, these included. Give them to other roles as you see fit.

## Give users a billing account

Add the `HasBillingAccount` trait to the application's user model, so a person can pay for their own plan:

```php [app/Modules/Auth/Models/User.php]
use Rollogi\Billing\Models\Concerns\HasBillingAccount;

class User extends Authenticatable implements Auditable, MustVerifyEmail, OAuthenticatable, TenantMember
{
    use HasBillingAccount;

    // the traits the model already uses
}
```

`Tenant` gets the same `billingAccount` relation from the package, registered with `resolveRelationUsing()`, so there is nothing to add there.

## Stripe keys

The package reads Cashier's usual variables:

| Variable | Used for |
| --- | --- |
| `STRIPE_KEY` | The publishable key, for Stripe.js on the frontend |
| `STRIPE_SECRET` | The secret key, for every API call |
| `STRIPE_WEBHOOK_SECRET` | The webhook signing secret, checked on every [webhook](/billing/webhooks) |
| `STRIPE_WEBHOOK_TOLERANCE` | Seconds of clock skew a webhook signature may have (Cashier's default is 300) |

Set `FRONTEND_URL` too. Stripe Checkout and the billing portal send the payer back to paths on it, which [`config/billing.php`](/billing/extending#configuration) fixes so a request cannot choose them.

## Feature keys

The package adds three keys to the kit's feature registry, all on by default:

| Key | Guards |
| --- | --- |
| `billing.subscriptions` | Viewing billing and the plans, and swapping, cancelling or resuming a subscription |
| `billing.checkout` | Stripe Checkout and the billing portal |
| `billing.elements` | Subscribing with Stripe Elements |

An entry for the same key in your `config/features.php` replaces the package's, so switch one off there or per tenant with `feature:set`. See [Feature toggles](/kit/feature-toggles).

## Seats in a kit project

If you sell per-seat plans, leave tenant API keys out of the seat count. In the starter kit an API key is a member of kind `machine`, so add a `config/billing.php` to the application with:

```php [config/billing.php]
return [
    'seats' => ['exclude' => ['kind' => 'machine']],
];
```

::note
The package merges its own `config/billing.php` in as defaults, and the merge is shallow: a top-level key your file defines replaces the package's whole value for that key, and the other keys keep their defaults. There is no `vendor:publish` tag, so copy any default you want to keep from the [configuration reference](/billing/extending#configuration).
::

## Queue and schedule

Stripe webhooks are applied by a queued job and usage reports go on the queue, so run a queue worker. The package also schedules `billing:sync-seats` daily, on one server and never overlapping, so make sure the scheduler runs (`php artisan schedule:work` locally, a cron entry for `schedule:run` in production).
