## Billing accounts

Cashier allows one customer model, so the customer is a `BillingAccount` owned by a tenant or a person, at most one each. Subscriptions, payment methods and invoices hang off the account, and a webhook finds its way back to the owner through it.

```php
use Rollogi\Billing\Actions\ResolveBillingAccountAction;

$account = ResolveBillingAccountAction::run($tenant);   // created on first use
$account->subscribed('default');
$account->getRelationValue('owner');                    // the Tenant
```

`BillingAccount` is not tenant-scoped, because a person's account has no tenant. Authorise access at the route, as the package's own [endpoints](/billing/endpoints) do. Cashier's own routes (its webhook and Blade payment page) are switched off, since the API serves its own.

## Declaring plans

Declare the catalogue from an app module provider's `boot()`. The package registers before app modules, so the catalogue is ready for you:

```php [app/Modules/Plans/PlansServiceProvider.php]
use App\Modules\Auth\Models\User;
use Rollogi\Billing\Billing;
use Rollogi\Core\Tenancy\Models\Tenant;

public function boot(): void
{
    Billing::plan('team-free')
        ->for(Tenant::class)
        ->free()
        ->limit('api-keys', 1);

    Billing::plan('pro')
        ->for(Tenant::class)
        ->label('Pro')
        ->monthly(config('billing.prices.pro.monthly'))
        ->yearly(config('billing.prices.pro.yearly'))
        ->perSeat(config('billing.prices.pro.seat'), included: 3)
        ->metered('api-calls', config('billing.prices.pro.api_calls'), meter: 'mtr_123')
        ->features('tenants.api_keys', 'webhooks.outbound')
        ->limit('api-keys', 10)
        ->limit('webhook-subscriptions', null)   // unlimited
        ->trialDays(14);

    Billing::plan('personal-plus')
        ->for(User::class)
        ->monthly(config('billing.prices.personal_plus'));
}
```

Reading the Stripe price ids from your own config (here a `prices` key in the application's `config/billing.php`) keeps Stripe's test and live accounts apart.

| Method | Declares |
| --- | --- |
| `for(string ...$owners)` | The Eloquent models that may buy the plan, usually `Tenant` or the user model |
| `label(string $label)` | The display name; defaults to the key as a headline (`team-free` becomes `Team Free`) |
| `monthly(string $priceId)`, `yearly(string $priceId)` | The base Stripe price for each interval |
| `perSeat(string $priceId, int $included = 0)` | A seat price billed for each seat beyond `$included` |
| `metered(string $name, string $priceId, ?string $meter = null)` | A usage-based price under a meter event name |
| `features(string ...$features)` | Feature keys the plan switches on |
| `limit(string $name, ?int $value)` | How many of something the plan allows; `null` is unlimited |
| `trialDays(int $days)` | A trial for an owner's first subscription |
| `free()` | The owner's fallback plan when nothing is paid for |

A plan reads back through the same names as properties (`$plan->key`, `$plan->label`, `$plan->limits`, `$plan->seats`, `$plan->metered`, `$plan->features`, `$plan->trialDays`, `$plan->isFree`). The `Billing` facade fronts the `PlanCatalogue` singleton, and `Billing::get()`, `has()`, `all()`, `forOwner()`, `fallbackFor()` (the owner's free plan) and `findByPrice()` look plans up.

### Validation

Values are checked as they are declared, and the whole catalogue once the application has booted. A mistake fails the boot with an `InvalidPlanException` naming the plan:

- a plan key is declared once;
- every plan needs an owner;
- a paid plan needs a monthly or yearly price, and a free plan has no prices at all;
- each owner has at most one free plan;
- each Stripe price belongs to one plan;
- a per-seat plan can only be sold to tenants;
- every feature must be registered in `config/features.php`;
- seats, limits and trial days cannot be negative (and a trial is at least one day).

## The current plan

An owner is on the plan behind a price on its `default` subscription while that subscription grants it, and otherwise on its free plan. An owner with neither has no plan. What "grants" means is the [`SubscriptionAccess`](/billing/extending#what-a-subscription-grants) contract's call. By default, `StripeSubscriptionAccess` grants the plan while Cashier's `valid()` does (active, trialing, or cancelled but still in its grace period), with two exceptions:

- a subscription Stripe **paused** (a trial that ended without a payment method) grants nothing, though Cashier still calls it valid;
- while the **first payment is still processing**, as a direct debit is for several business days, the plan waits for `invoice.paid`, even if Stripe already calls the subscription active. Set `billing.access.grant_while_payment_pending` to grant it straight away instead.

A subscription that is past due, unpaid, incomplete or ended falls back to the free plan. Suspending the owner stays an operator's decision.

```php
use Rollogi\Billing\Plans\CurrentPlans;

$plans = app(CurrentPlans::class);

$plans->for($tenant)?->key;              // 'pro'
$plans->allowance($tenant, 'api-keys');  // 10; null is unlimited
$plans->forget($tenant);                 // after changing a subscription mid-request
```

`CurrentPlans` is bound `scoped()`, so it remembers each owner's plan for the rest of the request and an Octane worker or queued job starts fresh. `forget()` also flushes the kit's feature memo, so the next feature check sees the new plan too. `ResolveCurrentPlanAction::run($owner)` resolves a plan without the memo.

## Features

A plan is a layer of the kit's feature toggles. `PlanFeatureSource` is tagged as a Core `FeatureSource`, so `FeatureManager` resolves a feature in this order:

1. a per-tenant override;
2. a global override;
3. the plan;
4. the default in `config/features.php`.

A feature that any plan grants is governed by plans: it is on when the current plan of the active tenant, or of the acting user, grants it, and off otherwise. An owner on no plan, or on a plan without it, is refused. A feature no plan for those owners mentions keeps its config default.

Nothing changes at the route: `feature:tenants.api_keys` works as before, and `feature:list` names the plan as the deciding layer. See [Feature sources](/core/features) for the mechanism.

## Limits

A write that uses up a plan limit says so on its input Data, by implementing `ConsumesLimit`:

```php
use Illuminate\Database\Eloquent\Model;
use Rollogi\Billing\Contracts\ConsumesLimit;
use Spatie\LaravelData\Data;

class CreateApiKeyData extends Data implements ConsumesLimit
{
    public function limitName(): string
    {
        return 'api-keys';
    }

    public function limitUsage(Model $owner): int
    {
        return ApiKey::query()->count();   // already scoped to the tenant
    }
}
```

`limitUsage()` returns how much the owner already uses, not counting this call.

The `EnforcePlanLimit` stage, which the package inserts into every service on the [write preset](/core/service-pipeline), refuses the write once the usage reaches the plan's allowance:

```json
{
    "type": "https://api.example.com/problems/plan-limit-reached",
    "title": "Plan limit reached",
    "status": 403,
    "detail": "The current plan allows 10 of api-keys.",
    "instance": "/api/tenants/current/api-keys",
    "request_id": "...",
    "limit": "api-keys",
    "allowed": 10,
    "plan": "pro"
}
```

The `type` base is `PROBLEM_TYPE_BASE`, or `APP_URL/problems` when it is unset (see [HTTP conventions](/kit/http)). The rules:

- The owner is the active tenant, or the acting user when no tenant plan declares the limit.
- A limit the current plan does not declare allows none, and `null` allows any number.
- A limit no plan for the owner declares is not enforced.
- A Data class with a `limitName()` method that does not implement `ConsumesLimit` throws a `LogicException`, rather than being silently skipped.

The stage runs after `ReplayIdempotentCall`, so a replayed create is answered rather than refused, and before `AuditServiceCall`, so a refusal writes no audit row. A service drops the check with `stagesWithout(EnforcePlanLimit::class)`.

::warning
The count is not locked, so two concurrent writes at the last unit can both pass. Treat limits as commercial guardrails rather than hard invariants.
::
