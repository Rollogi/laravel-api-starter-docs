A project created from the kit is yours from the first commit, but it can keep taking the kit's improvements, security fixes and dependency bumps afterwards.

## Two channels

| What | How it arrives |
| --- | --- |
| Core: the service pipeline, tenancy, features, HTTP conventions, auditing, integrations, health (`Rollogi\Core`) | `composer update rollogi/core`, from the private `Rollogi/core` repository, within the current major |
| Everything else: the shipped modules, `bootstrap/`, `config/`, tests, tooling, `Dockerfile`, docs | a git merge from upstream |

Core needs no merge at all. Its version is in `composer.lock`, and an update is a Composer command you can run on its own between syncs.

## The rule that keeps merges quiet

**Put your code in `app/Modules/`. Change Core by extending it, never by editing it.**

Merges stay quiet as long as the two sides edit different files, and Core is not in your tree to edit. When it does not do what you need:

- Add a pipeline stage and list it in your service's `stages()` rather than changing a shipped stage.
- Rebind a Core service from a module provider's `register()`. `bootstrap/providers.php` lists `ModuleServiceProvider` after `CoreServiceProvider`, so a module's binding replaces Core's.
- Register anything else (a rate limiter, an event listener, a scheduled task) in a module provider's `boot()`.
- Subclass rather than modify. `WebhookHandler`, `Connector` and `SendIntegrationRequest` are designed as extension points.
- Ship a module as a package. A Composer package that lists its provider under `extra.laravel.api-starter-modules` registers like an app module (see [Package modules](/core/package-modules)). Until it has a repository of its own it can live in `packages/`, which the `packages/*` path repository installs.

If Core really is wrong, change it in the kit: that is the only place a change to it survives.

| You own, edit freely | Kit owns, avoid editing |
| --- | --- |
| `app/Modules/<YourModule>/**` | the shipped modules, if you want their fixes to merge cleanly |
| `tests/Feature/<YourModule>/**` | `tests/Feature/Core/**` |
| `config/features.php` entries you add, Core config files you published | `bootstrap/app.php`, `bootstrap/providers.php` |
| `.env`, `.env.example` additions, `packages/<your-package>` | `pint.json`, `rector.php`, `phpstan.neon`, `phpstan.core.php` |

## One-time setup

`laravel new` installs from a release archive and then runs `git init`, so your project starts with one root commit and no ancestry in common with the kit. Without a common ancestor git treats every differing file as an `add/add` conflict, including files you never touched:

```console
$ git merge upstream/main --allow-unrelated-histories
CONFLICT (add/add): Merge conflict in bootstrap/app.php     # you never touched this
CONFLICT (add/add): Merge conflict in composer.json
```

Fix it once per project, ideally on day one, by recording the release you generated from as an ancestor while taking none of its content:

```bash [Terminal]
git remote add upstream https://github.com/Rollogi/laravel-api-starter.git
git fetch upstream --tags
git merge -s ours --allow-unrelated-histories --no-edit v2.0.0   # the tag you generated from
```

`-s ours` keeps your tree byte for byte and only writes the ancestry link. From then on git does a proper three-way merge and only genuinely overlapping edits conflict.

::caution
Use the version you **generated from**, not the latest. Pointing `-s ours` at `upstream/main` marks every release up to now as already merged, and you will silently never receive them.
::

## Routine sync

```bash [Terminal]
git checkout -b chore/sync-upstream
git fetch upstream --tags
git merge --no-commit --no-ff upstream/main     # or a tag, such as v2.1.0
git rm -r -q -f --ignore-unmatch packages/core packages/billing packages/nuxt-ui
```

The `git rm` is part of every sync. The kit develops `rollogi/core`, `rollogi/billing` and `rollogi/nuxt-ui` in `packages/`, so a merge brings any file added there into your tree and reports every file changed there as a `modify/delete` conflict. Leaving them in would be worse than noisy: the `packages/*` path repository comes first, so Composer would install those copies in place of the released packages. Removing the directories resolves those conflicts; `-f` is needed because the merge staged the files, and packages of your own are untouched.

Resolve whatever else conflicts, then finish:

```bash [Terminal]
composer update rollogi/core      # plus any packages of your own whose constraints changed
composer check
git commit
```

Open it as a pull request. The merge diff is the clearest changelog you will get for everything outside Core.

## Updating Core

```bash [Terminal]
composer update rollogi/core
composer check
```

The kit requires `rollogi/core` with an `@dev` stability flag (`^1.1@dev` at the time of writing). The flag is there for the kit's own path checkout; `prefer-stable` gives your project the newest tagged release in the major. A new Core major arrives with a kit release that raises the constraint. See the [Core changelog](/core/changelog) for what each version changed.

## Conflicts you will actually hit

**`composer.json`** conflicts when both sides add dependencies in the same region. Start from upstream's version, re-add your own dependencies, and resolve Core and yours by name:

```bash [Terminal]
git checkout upstream/main -- composer.json composer.lock    # or the tag you are merging
# re-add your own dependencies to composer.json, then:
composer update rollogi/core <your/package>
```

**`composer.lock`** is not worth hand-merging. Take upstream's, as above: it pins the versions the kit was tested with, and naming `rollogi/core` in the update replaces its development entry with the released package.

**`packages/core`, `packages/billing` and `packages/nuxt-ui`** are handled by the `git rm` above, never resolved by hand.

**`.github/workflows/`**: a project created from a release has none, because the archive leaves them out, so a workflow the kit changed arrives as a `modify/delete` conflict. Keep it or `git rm` it. The jobs that only make sense in the kit's own repository (the package jobs in `ci.yml`, the `split-*.yml` workflows and `prepare-package-release.yml`) check the repository name and skip anywhere else.

**`CLAUDE.md`, `README.md`, `.env.example`** are documentation and templates. Usually you want upstream's version plus your project's additions.

**A shipped module you edited** conflicts like any other file. Take upstream's version if you can and re-apply your change as an extension.

If a merge goes badly, `git merge --abort` returns you to exactly where you were.

## Previewing a sync

```bash [Terminal]
# Commits you do not have yet
git log --oneline HEAD..upstream/main

# The surface that merges into your tree, without Core
git diff HEAD..upstream/main -- app bootstrap config database routes

# Files that would conflict, without touching the working tree
git merge-tree $(git merge-base HEAD upstream/main) HEAD upstream/main | grep -A2 '^changed in both'
```

For Core, compare the `rollogi/core` version in your `composer.lock` with the [Core changelog](/core/changelog).

::note
A project still on kit 1.x, with Core in `app/Core`, moves to the `rollogi/core` package first. The kit's repository has an `UPGRADE.md` that walks through it, through an upstream sync or by hand.
::
