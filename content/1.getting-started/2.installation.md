## Give Composer access

The kit and `rollogi/core` are private repositories, so Composer needs a GitHub token that can read both before the first install. Store it once, globally:

```bash [Terminal]
composer config --global github-oauth.github.com <token>
```

A fine-grained token with read access to the repositories' contents is enough. If you later add `rollogi/billing` or `rollogi/nuxt-ui`, the same token needs read access to those repositories too.

## Create the project

```bash [Terminal]
laravel new my-api --using=rollogi/laravel-api-starter
cd my-api
composer setup
```

`laravel new` runs `composer create-project` against the kit's latest release. The release archive leaves out `packages/core`, `composer.lock`, `.github/`, `CHANGELOG.md` and `UPGRADE.md`, so your project starts without the kit's own release tooling and installs `rollogi/core` from its private repository. Its `post-create-project-cmd` generates an app key, creates `database/database.sqlite` and runs the migrations.

`composer setup` is the full first-run bootstrap. In order, it:

1. runs `composer install`;
2. copies `.env.example` to `.env` if there is no `.env` yet;
3. runs `php artisan key:generate`;
4. migrates with `php artisan migrate --force`;
5. creates Passport's encryption keys with `php artisan passport:keys --force`;
6. creates a personal access client with `php artisan passport:client --personal`;
7. seeds with `php artisan db:seed --force`.

::warning
`passport:keys --force` overwrites any keys already in `storage/`. Run `composer setup` on a fresh checkout, not on an install whose tokens you want to keep.
::

### What the seeder creates

`DatabaseSeeder` calls `RolesAndPermissionsSeeder`, which creates the global `admin` and `user` roles and their permissions, then creates a tenant named `Demo Tenant` and a user who is its `admin`:

| Field | Value |
| --- | --- |
| Email | `admin@example.com` |
| Password | `password` |

Change or remove that account before the database is anywhere but your machine. You can create real tenants from the command line instead; `--owner` names an existing user, who joins the tenant with the role in `tenants.admin_role`:

```bash [Terminal]
php artisan tenant:create "Globex" --owner=owner@example.com
php artisan tenant:list
```

### The database

`.env.example` ships with `DB_CONNECTION=sqlite`, so the first run needs no database server. To use MySQL or PostgreSQL, set the connection in `.env`; the file has a commented example for each:

```ini [.env]
DB_CONNECTION=pgsql
DB_HOST=127.0.0.1
DB_PORT=5432
DB_DATABASE=my_api
DB_USERNAME=postgres
DB_PASSWORD=secret
```

Every migration in the kit runs on all three databases, and CI proves it. See [Testing](/kit/testing) for running the suite against each.

### Check it works

```bash [Terminal]
php artisan serve
curl -i http://localhost:8000/up
```

`/up` is the framework's public liveness probe. `GET /api/health` is the readiness report and needs `HEALTH_TOKEN`; see [Deployment](/kit/deployment).

## Wire up upstream on day one

`laravel new` gives your project a fresh git history with nothing in common with the kit's, so there is no `git pull` relationship by default. Two commands now save a lot of pain later:

```bash [Terminal]
git remote add upstream https://github.com/Rollogi/laravel-api-starter.git
git fetch upstream --tags
git merge -s ours --allow-unrelated-histories --no-edit v2.0.0   # the tag you generated from
```

`-s ours` keeps your tree exactly as it is and only records the release you generated from as an ancestor. After that, a merge from `upstream/main` brings in the kit's changes as an ordinary three-way merge, and `composer update rollogi/core` brings Core's.

::caution
Use the tag you **generated from**, not the latest one. Pointing `-s ours` at `upstream/main` marks every release up to now as merged, and you will never receive them. When in doubt pick the older tag: re-merging is harmless, skipping is not.
::

[Staying in sync](/getting-started/upstream-sync) covers routine syncs and the conflicts you will meet.

## Composer scripts

There is no `package.json`; everything runs through Composer.

| Command | What it does |
| --- | --- |
| `composer setup` | Full first-run bootstrap: install, `.env`, key, migrate, Passport keys and client, seed |
| `composer check` | The full gate: `composer lint`, then `composer test`. CI runs this. |
| `composer lint` | Check only: `pint --test`, `phpstan analyse` (Larastan level 8), `rector process --dry-run` |
| `composer lint:fix` | Write mode: `pint`, then `rector process` |
| `composer rector` / `composer rector:check` | Rector alone, in write or dry-run mode |
| `composer test` | Pest only, on SQLite in memory |
| `composer db:up` / `composer db:down` | Start or stop the MySQL and PostgreSQL test databases from `compose.yaml` |
| `composer test:mysql` / `composer test:pgsql` | Pest against MySQL 8.4 or PostgreSQL 17 |
| `composer test:all` | Pest on SQLite, then MySQL, then PostgreSQL |

Run a single test file or filter by name with Pest directly:

```bash [Terminal]
vendor/bin/pest tests/Feature/Auth/LoginTest.php
vendor/bin/pest --filter='creates an invoice'
```

::tip
Run `composer check` before every commit. Pint, Larastan and Rector enforce the house style, so a change that passes locally passes in CI.
::
