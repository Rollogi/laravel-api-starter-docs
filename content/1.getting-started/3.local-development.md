You can work on the kit with a local PHP 8.5 and `php artisan serve`, or in a container that runs the same Nginx and PHP-FPM stack as the production image. Either way, the test databases for MySQL and PostgreSQL come from a separate compose file.

## The development container

`Dockerfile.dev` and `compose.dev.yaml` run the app on [`rollogi/php-nginx-dev`](https://docker.rollogi.co.uk/images/php-nginx-dev): Nginx and PHP-FPM as in production, plus Xdebug 3.5, errors shown in responses and static files served with `no-store`. The image adds `pdo_pgsql`, `pdo_sqlite` and `sodium`, the same extensions the production `Dockerfile` adds, so the two never disagree about a driver.

```bash [Terminal]
docker compose -f compose.dev.yaml up --build                 # http://localhost:8080
docker compose -f compose.dev.yaml exec app php artisan tinker
docker compose -f compose.dev.yaml exec app composer check
```

Nothing is copied into the image. The project is bind-mounted at `/app`, so an edit is live on the next request.

### First start

`docker/bootstrap-dev.sh` is the image's `APP_INSTALL` hook and runs before Nginx and PHP-FPM start. Each step is skipped when its result already exists, so a second start costs nothing and nothing you set up is overwritten:

1. `composer install` when there is no `vendor/autoload.php`;
2. copies `.env.example` to `.env` and generates a key when there is no `.env`;
3. creates `database/database.sqlite` when it is missing;
4. runs `php artisan passport:keys` when there is no `storage/oauth-private.key`;
5. runs `php artisan optimize:clear` every time, because cached config or routes would hide your edits;
6. runs `php artisan migrate` when `RUN_MIGRATIONS` is `true` (the compose file sets it).

The bootstrap does not seed. Run `docker compose -f compose.dev.yaml exec app php artisan db:seed` for the demo tenant and admin, and `php artisan passport:client --personal` if you need a personal access client.

### Settings

`compose.dev.yaml` reads these from the environment:

| Variable | Default | Purpose |
| --- | --- | --- |
| `DEV_PORT` | `8080` | Host port mapped to the container's Nginx on `8080` |
| `UID` / `GID` | `1000` | The user the container runs as, so files it creates (`vendor`, `storage`, the SQLite file) stay editable on a Linux host. Docker Desktop maps ownership on its own. |

The service also sets `XDEBUG_MODE=develop,debug`, `XDEBUG_START_WITH_REQUEST=trigger` and `XDEBUG_IDEKEY=PHPSTORM`, and keeps the Composer cache and Xdebug output in named volumes. `Dockerfile.dev` sets `APP_ENV=local`, `APP_DEBUG=true`, `LOG_CHANNEL=stderr`, `PHP_MEMORY_LIMIT=512M` and 20M post and upload limits.

### Debugging with Xdebug

Xdebug connects to your IDE on `host.docker.internal:9003` and waits for a trigger: the Xdebug browser extension, an `XDEBUG_TRIGGER` cookie, or a `?XDEBUG_TRIGGER=1` query parameter.

- **PhpStorm:** add a PHP server named `laravel-api-starter` on `localhost:8080` with the project root mapped to `/app` (the image sets `PHP_IDE_CONFIG=serverName=laravel-api-starter` to match), then start listening.
- **VS Code:** a "Listen for Xdebug" configuration on port `9003` with `/app` mapped to the workspace folder.

To debug every request without a trigger, set `XDEBUG_START_WITH_REQUEST: "yes"` in `compose.dev.yaml`.

::caution
The development image shows errors in responses and runs Xdebug. Never deploy it. Production builds from `Dockerfile`; see [Deployment](/kit/deployment).
::

## Test databases

The suite runs on SQLite in memory by default. The kit also supports MySQL and PostgreSQL, and the bugs only one of them shows (a nullable column inside a primary key, a transaction left aborted after a caught constraint violation, a case-insensitive collation) are exactly what a SQLite run cannot catch. `compose.yaml` provides throwaway databases for them:

```bash [Terminal]
composer db:up          # MySQL 8.4 on 33306 and PostgreSQL 17 on 54329
composer test:mysql     # the whole suite against MySQL
composer test:pgsql     # the whole suite against PostgreSQL
composer test:all       # SQLite, then MySQL, then PostgreSQL
composer db:down
```

`composer db:up` runs `docker compose --profile pgsql up -d --wait`; `docker compose up -d --wait` without the profile starts MySQL alone. Both databases keep their data in tmpfs, so a restart gives you a clean one, and the ports avoid the defaults so a local MySQL or PostgreSQL is never in the way.

### Changing ports and credentials

The compose file, the `test:mysql` and `test:pgsql` scripts and the CI workflow all read the same variables, so exporting one changes every side at once:

| Variable | Default |
| --- | --- |
| `DB_TEST_DATABASE` | `api_starter_test` |
| `DB_TEST_USERNAME` | `api` |
| `DB_TEST_PASSWORD` | `secret` |
| `DB_TEST_MYSQL_PORT` | `33306` |
| `DB_TEST_PGSQL_PORT` | `54329` |

The scripts pass the connection to Pest through the environment, which wins over the `<env>` values in `phpunit.xml`. Any other database is a matter of exporting `DB_CONNECTION`, `DB_HOST`, `DB_PORT`, `DB_DATABASE`, `DB_USERNAME` and `DB_PASSWORD` before `vendor/bin/pest`.

::note
One test is skipped on MySQL by design: its default `utf8mb4_unicode_ci` collation already treats case-variant emails as equal, so the guard it exercises can never be reached there.
::

CI runs the same three databases on every pull request, so a change that touches migrations or raw SQL should pass `composer test:all` before you open one. [Testing](/kit/testing) covers the suite itself.
