An action is one reusable operation with a single typed `__invoke()`. It extends `Rollogi\Core\Actions\Concerns\Action`, has no pipeline, and has no side effects beyond its purpose. Services orchestrate actions; actions do the work.

```php [app/Modules/Billing/Actions/CreateInvoiceAction.php]
use Rollogi\Core\Actions\Concerns\Action;

class CreateInvoiceAction extends Action
{
    public function __invoke(string $tenantId, int $amount): Invoice
    {
        return Invoice::query()->create(['tenant_id' => $tenantId, 'amount' => $amount]);
    }
}
```

Whatever route an action takes, the container resolves the instance, so constructor injection works everywhere and a fake bound in a test replaces it everywhere.

## Running off the request

```php
CreateInvoiceAction::run($tenantId, 100);                              // inline, returns the result
SyncMemberToCrmAction::dispatch($user)->onQueue('integrations');       // queued
SyncMemberToCrmAction::dispatchAfterCommit($user);                     // queued once the transaction commits
SyncMemberToCrmAction::dispatchSync($user);                            // in process, through the queue wrapper, returns the result

Action::chain([ProvisionTenantAction::with($tenant), SeedRolesAction::with($tenant)])->dispatch();
Action::batch([ExportTenantAction::with($first), ExportTenantAction::with($second)])->dispatch();

Event::listen(InvitationCreated::class, SendInvitationEmailAction::class); // an action is a valid listener
```

| Method | Returns | Notes |
|--------|---------|-------|
| `run(...)` | `__invoke()`'s type | Inline, no queue |
| `dispatch(...)` | `PendingDispatch` | `onQueue`, `onConnection`, `delay` and `afterCommit` all apply |
| `dispatchAfterCommit(...)` | `PendingDispatch` | `dispatch()` with `afterCommit()` |
| `dispatchSync(...)` | `__invoke()`'s type | Runs the queued wrapper in process, inside the captured context |
| `with(...)` | `PendingAction` | Holds the action and its arguments until a chain or batch is dispatched |
| `Action::chain([...])` | `PendingChain` | The framework's chain; a plain job object may sit in the same list |
| `Action::batch([...])` | `PendingBatch` | The framework's batch |
| `fake($result)` | `ActionFake` | See [Testing](#testing) |

Laravel calls `__invoke()` on a listener that has no `handle()`, which is why an action can be registered as an event listener directly.

The arguments of `run()`, `dispatch()`, `dispatchAfterCommit()`, `dispatchSync()` and `with()` are checked against `__invoke()` by Core's PHPStan rule, named arguments included, and `run()` and `dispatchSync()` return `__invoke()`'s type. See [Static analysis](/core/static-analysis).

### Services off the request

A service has the same entry points, except `with()`, `chain()` and `batch()`:

```php
ExportTenantService::dispatch($data);           // the whole pipeline runs on the worker
ExportTenantService::dispatchAfterCommit($data);
$result = ExportTenantService::dispatchSync($data);
```

On the worker the stages authorise, audit and log under the tenant and user that dispatched the call.

## Execution context

Every dispatch captures a `Rollogi\Core\Support\Execution\ExecutionContext`: the active tenant id, the acting user id from the `api` guard, and the request id. The queued job (`QueuedInvocation`, internal) restores all three on the worker before invoking the class, sets the Spatie permission team id to match the tenant, and puts the worker's previous state back afterwards.

So a queued service writes the same `service_audits` row, carries the same log context, and passes the same `authorizeService()` check it would have inline.

- A tenant or user deleted between dispatch and execution leaves that part of the context untouched rather than failing the job.
- Eloquent models anywhere in the argument list, including inside arrays, are serialised as identifiers and reloaded on the worker, as `SerializesModels` does for a job's own properties.
- `ExecutionContext::forTenant($tenantId)` builds a context with only a tenant; `SendIntegrationRequest` runs its request inside one. See [Integrations](/core/integrations#queued-requests).

You can run your own code inside a context too:

```php
use Rollogi\Core\Support\Execution\ExecutionContext;

$context = ExecutionContext::capture();

// later, possibly elsewhere
$context->run(function (): void {
    // tenancy(), Auth::guard('api') and the request id are as they were at capture()
});
```

## Testing

`Bus::fake()` works as usual, and each class exposes its own assertions so a test does not have to match the internal queued job by hand. The callback receives the dispatched arguments, as `__invoke()` would.

```php
Bus::fake();

CreateInvitationService::run($data);

SendInvitationEmailAction::assertDispatched(fn (Invitation $invitation): bool => $invitation->getAttribute('email') === 'new@example.com');
SendInvitationEmailAction::assertDispatchedTimes(1);
SyncMemberToCrmAction::assertNotDispatched();
```

`fake()` binds a recording stand-in in the container. `$result` may be a value, or a closure that receives the arguments and returns one:

```php
$fake = CreateInvoiceAction::fake(fn (string $tenantId, int $amount): Invoice => new Invoice(['amount' => $amount]));

// ... exercise the code

$fake->assertRan(fn (string $tenantId, int $amount): bool => $amount === 100);
$fake->assertRanTimes(1);
```

`SomeService::fake($result)` does the same for a service; its `assertRan()` callback receives the input. Both fakes answer `assertRan(?Closure)`, `assertRanTimes(int)` and `assertNotRan()`. A controller test that fakes the service never reaches the pipeline or the database.

The sinks behind the `EmitMetric` and `IndexForSearch` stages have fakes of their own; see [Metrics and search](/core/metrics-and-search#testing).
