Core implements single-database tenancy: tenant-owned rows carry a `tenant_id` column, and a global scope filters every query to the active tenant. This page covers Core's classes. For how the kit applies them to routes, members and roles, see [Multi-tenancy](/kit/multi-tenancy) and [Tenants](/kit/tenants).

## The tenant context

`Rollogi\Core\Tenancy\TenantContext` holds the active tenant for the current request, job or command. It is bound with `scoped()`, so the container forgets it between Octane requests and queue jobs and each one starts without a tenant. Reach it through the `tenancy()` helper, autoloaded from Core's `src/Support/helpers.php`, rather than `app(TenantContext::class)`:

```php
tenancy()->id();          // ?string, the active tenant's id
tenancy()->current();     // ?Tenant
tenancy()->has();         // bool
tenancy()->set($tenant);  // make a tenant active
tenancy()->clear();       // no active tenant
tenancy()->runWithout(fn (): mixed => ...); // run with no tenant, then restore the previous one
```

`set()` changes the tenant scope only. To keep the Spatie permission team id aligned, which role checks need, use `ActivateTenantAction`:

```php
use Rollogi\Core\Tenancy\Actions\ActivateTenantAction;

ActivateTenantAction::run($tenant); // tenancy()->set() plus setPermissionsTeamId()
```

## Tenant-owned models

A tenant-owned model extends Core's base model and uses `BelongsToTenant`:

```php [app/Modules/Billing/Models/Invoice.php]
use Rollogi\Core\Models\Concerns\BelongsToTenant;
use Rollogi\Core\Models\Model;

class Invoice extends Model
{
    use BelongsToTenant;
}
```

`Rollogi\Core\Models\Model` is Eloquent's model with `#[WithoutIncrementing]`, a string key type and `HasUuidPrimaryKey`, which generates UUIDv7 keys. `BelongsToTenant` adds:

- the global `TenantScope`, which adds `where <table>.tenant_id = ?` to every query while a tenant is active;
- a `creating` hook that fills `tenant_id` from `tenancy()->id()` when it is not already set;
- a `tenant()` `BelongsTo` relation.

::caution
When no tenant is active, `TenantScope` is a **no-op**: queries are not filtered. An authenticated resource route without `ResolveTenant` in front of it (the kit's `api.tenant` group) sees every tenant's rows.
::

To read across tenants on purpose, in a job, a command or an operator tool, use the explicit escape hatch rather than clearing the context by hand:

```php
$allInvoices = tenancy()->runWithout(fn (): int => Invoice::query()->count());
```

## Resolving the tenant on a request

`Rollogi\Core\Tenancy\Middleware\ResolveTenant` (the `tenant` alias in the kit) runs after authentication. For a user that implements `TenantMember`:

| Situation | Result |
|-----------|--------|
| `X-Tenant: <uuid>` header and the user is a member | That tenant becomes active |
| `X-Tenant` header and the user is not a member (or it does not exist) | `403 tenant-forbidden` |
| No header and the user belongs to exactly one tenant | That tenant becomes active |
| No header and the user belongs to none or several | `400 tenant-required` |
| The resolved tenant has `suspended_at` set | `403 tenant-suspended` |

On success it sets the context and the permission team id. The membership check and the tenant load are one query, and the sole-tenant case reads at most two rows. A request whose user does not implement `TenantMember` (or has none) passes through untouched.

In the kit, `ResolveTenant` is forced ahead of `ThrottleRequests` in the priority list, so the `tenant` rate limiter can key on the active tenant.

## Members

Core never imports the application's user model. It resolves the class from `auth.providers.users.model` and checks it against the `Rollogi\Core\Tenancy\Contracts\TenantMember` contract, whose only method is `tenants(): BelongsToMany`. The `HasTenants` trait implements it over the `tenant_user` pivot (with `joined_at` and timestamps):

```php [app/Modules/Auth/Models/User.php]
use Rollogi\Core\Tenancy\Concerns\HasTenants;
use Rollogi\Core\Tenancy\Contracts\TenantMember;

class User extends Authenticatable implements TenantMember
{
    use HasTenants;
}
```

The other side, `Tenant::users()`, returns the configured user model. Core's PHPStan extension types it as that model rather than the bare contract; see [Static analysis](/core/static-analysis).

::note
The user model is deliberately **not** tenant-scoped. The authenticated principal has to load before any tenant context exists.
::

## The Tenant model

`Rollogi\Core\Tenancy\Models\Tenant` has `name` and `suspended_at` (cast to a datetime), `users()`, `settings()` and `isSuspended()`. A suspended tenant keeps its data and memberships, but `ResolveTenant` refuses to make it active, so tenant-scoped routes answer `403 tenant-suspended` while account-level routes still work.

| Action | Does |
|--------|------|
| `CreateTenantAction::run(string $name): Tenant` | Creates a tenant |
| `FindTenantAction::run(string $tenantId): Tenant` | `findOrFail()` by id |
| `ActivateTenantAction::run(Tenant $tenant): void` | Makes it active, with the permission team id |

`TenantNotFoundException` is rendered as `404 tenant-not-found`; the console commands that take `--tenant` throw it for an id that matches nothing (the `ResolvesTenantOption` trait).

## Permissions and teams

Core's `Authorization` concern creates the Spatie permission tables with teams on, where the team id is the tenant id. Outside an HTTP request, set the team before assigning a role, or the role lands in the wrong tenant:

```php
use Spatie\Permission\PermissionRegistrar;

app(PermissionRegistrar::class)->setPermissionsTeamId($tenant->getKey());
$user->assignRole('admin');
```

The pivot tables use a surrogate id plus a unique index rather than a composite primary key, so a global assignment with `tenant_id = null` can be stored on SQLite, MySQL and PostgreSQL alike.

### Octane

The Spatie team id lives on a plain singleton, which Octane would carry into the next request. `Rollogi\Core\Tenancy\Listeners\ResetTenantState` clears it on `OperationTerminated`; the kit lists it in `config/octane.php`. `TenantContext` itself is already forgotten by the container flush that runs before it.

## Per-tenant settings

`Rollogi\Core\Tenancy\TenantSettings` is the data twin of feature toggles. Every key is registered in `tenant-settings.php` with a default, a label and validation rules, and a `tenant_settings` row (JSON `value`, unique on `tenant_id` and `key`) overrides the default for one tenant:

```php [config/tenant-settings.php]
return [
    'settings' => [
        'locale' => [
            'default' => 'en',
            'label' => 'Default locale for members and notifications',
            'rules' => ['string', 'min:2', 'max:10'],
        ],
        'timezone' => [
            'default' => 'UTC',
            'label' => 'Timezone used when rendering dates for this tenant',
            'rules' => ['string', 'timezone:all'],
        ],
    ],
];
```

Those two keys are what Core ships. Publish the file with `vendor:publish --tag=rollogi-core-config` to add your own; remember the merge is shallow, so your `settings` array replaces Core's entirely.

```php
$settings = app(TenantSettings::class);

$settings->get('timezone', $tenant);       // stored value, or the registered default
$settings->all($tenant);                   // every registered key with its effective value
$settings->set('timezone', 'Europe/London', $tenant);
$settings->forget('timezone', $tenant);    // back to the default
$settings->rules();                        // validation rules keyed by setting
$settings->definition('timezone');         // default, label and rules
```

An unregistered key throws `UnknownTenantSettingException`. The store is bound `scoped()` and memoises each tenant's rows for the request; `set()` and `forget()` drop the memo. In the kit, `PATCH /api/tenants/current/settings` validates against `rules()`.
