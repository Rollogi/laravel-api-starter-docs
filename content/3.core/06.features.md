Core's `Features` concern decides whether a feature is on, for a tenant and an acting user. The registry itself, `config/features.php`, belongs to the application; for the kit's registry and how operators use it, see [Feature toggles](/kit/feature-toggles).

## The registry

Every feature key is declared under `features` in `config/features.php`, with a default and a label:

```php [config/features.php]
'features' => [
    'billing.invoices' => ['default' => true, 'label' => 'Invoice management'],
],

'disabled_message' => 'This feature is disabled.',
```

An unregistered key throws `Rollogi\Core\Features\Exceptions\UnknownFeatureException` from every `FeatureManager` method, so a typo fails loudly rather than reading as "off". `disabled_message` is the `detail` of the `feature-disabled` problem.

## Resolution order

`Rollogi\Core\Features\FeatureManager` decides a feature by the first layer that has an answer:

| Order | Layer (`FeatureLayer`) | Where it comes from |
|-------|------------------------|---------------------|
| 1 | `TenantOverride` (`tenant-override`) | A `feature_settings` row for the tenant |
| 2 | `GlobalOverride` (`global-override`) | A `feature_settings` row with `tenant_id = null` |
| 3 | `Source` (`source`) | Each `FeatureSource` tagged `FeatureManager::SOURCES`, in registration order |
| 4 | `Default` (`default`) | The `default` in `config/features.php` (false when missing) |

`FeatureManager` is bound `scoped()` and memoises each resolution for the request, keyed by feature, tenant and actor, so Octane never serves a stale answer and a route checked several times reads the database once.

## Using FeatureManager

```php
use Rollogi\Core\Features\FeatureManager;

$features = app(FeatureManager::class);

$features->enabled('billing.invoices');                     // active tenant, api guard user
$features->enabled('billing.invoices', $tenant);            // a given tenant
$features->enabledFor('billing.invoices', $tenant, $user);  // exactly this scope
$features->resolutionFor('billing.invoices', $tenant, null); // FeatureResolution
$features->all($tenant);                                    // array<string, bool>
$features->registered();                                    // every key
```

`enabled()` defaults the tenant to the active one and, only once a source is registered, the actor to the `api` guard's user, so a public route pays nothing for sources. `enabledFor()` takes its scope literally: a null tenant means no tenant, not the active one.

`resolutionFor()` returns a `FeatureResolution` with `enabled`, the deciding `layer`, and `source`, the class name when a `FeatureSource` decided.

### Writing overrides

```php
$features->setGlobal('billing.invoices', false);
$features->setForTenant('billing.invoices', $tenant, true);
$features->clearForTenant('billing.invoices', $tenant);
$features->clearGlobal('billing.invoices');
$features->flush(); // forget every resolution this request has made
```

Every write clears the memo. Call `flush()` yourself when something a source reads has changed mid-request.

## Guarding a route

The `EnsureFeatureEnabled` middleware (the `feature` alias in the kit) answers `403 feature-disabled` with a `feature` extension naming the key:

```php
Route::middleware(['api.tenant', 'feature:billing.invoices'])->get('/invoices', ListInvoicesController::class);
```

It calls `enabled()`, so it decides for the active tenant and, when sources exist, the signed-in user.

## Commands

| Command | Does |
|---------|------|
| `feature:list [--tenant=<uuid>]` | A table of every feature with its state and the layer that decided it, for example `source (PlanFeatureSource)`. Run without an actor, so a source that answers per person has nobody to answer for. |
| `feature:set <feature> --on\|--off\|--clear [--tenant=<uuid>]` | Writes or clears an override, globally or for one tenant. Exactly one of `--on`, `--off`, `--clear`. |

An unknown tenant id or feature key fails the command with a message rather than an exception.

## Feature sources

A source is a layer between the overrides and the config default. It implements `Rollogi\Core\Features\Contracts\FeatureSource`:

```php
use Rollogi\Core\Features\Contracts\FeatureSource;
use Rollogi\Core\Features\FeatureScope;

class PlanFeatureSource implements FeatureSource
{
    public function enabled(string $feature, FeatureScope $scope): ?bool
    {
        if (! str_starts_with($feature, 'billing.')) {
            return null; // no opinion: the next source, then the default, decides
        }

        return $this->planGrants($feature, $scope->tenant, $scope->actor);
    }
}
```

Return `true` or `false` to decide, or `null` to leave it to the next layer. `FeatureScope` carries `tenant` (`?Tenant`) and `actor` (`?Authenticatable`): on an account-level route the tenant is null and the actor set; in a console command both may be null.

Register it from a provider:

```php
use Rollogi\Core\Features\FeatureManager;

$this->app->scoped(PlanFeatureSource::class);
$this->app->tag([PlanFeatureSource::class], FeatureManager::SOURCES);
```

Sources are resolved once per `FeatureManager`, which is itself scoped, so a source may safely be scoped too. A tagged class that does not implement the contract throws a `LogicException` the first time a feature is resolved.

::note
With no source registered nothing changes from Core 1.0, and the guard is never asked for the user. Overrides always beat sources: an operator's `feature:set` still wins over a billing plan.
::

[rollogi/billing](/billing) is the reference: its `PlanFeatureSource` turns a feature on only where the tenant's or the actor's plan grants it.
