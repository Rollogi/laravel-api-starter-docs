Core's `Http` concern supplies the pieces the kit composes into its HTTP stack. The composition itself (which middleware is prepended, appended or aliased) lives in the application's `bootstrap/app.php`. For the conventions a client sees, see [HTTP conventions](/kit/http).

## Problem details

Every exception on an `api/*` or JSON-expecting request becomes one RFC 9457 `application/problem+json` document, rendered by `Rollogi\Core\Http\Problems\ProblemDetailsRenderer`. Register it as the render callback in `bootstrap/app.php`:

```php [bootstrap/app.php]
->withExceptions(function (Exceptions $exceptions): void {
    $exceptions->shouldRenderJsonWhen(fn (Request $request, Throwable $exception): bool => $request->is('api/*') || $request->expectsJson());
    $exceptions->render(fn (Throwable $exception, Request $request): ?JsonResponse => app(ProblemDetailsRenderer::class)($exception, $request));
})
```

A response looks like this:

```json
{
    "type": "https://api.example.com/problems/tenant-required",
    "title": "Tenant required",
    "status": 400,
    "detail": "X-Tenant header required: you belong to more than one tenant, or to none.",
    "instance": "/api/tenants/current",
    "request_id": "01972f4e-..."
}
```

`type` is `problems.type_base` (`PROBLEM_TYPE_BASE`) plus the slug, falling back to `APP_URL/problems`. There is no `message` key. Extension members sit beside the standard ones: `errors` on a validation failure, `retry_after` on a rate limit, `feature` on a disabled feature.

| Exception | Problem |
|-----------|---------|
| `ProblemException` | Its own status, type, title, detail and extensions |
| `ValidationException` | `validation-failed`, with `errors` |
| `AuthenticationException` | `401 unauthenticated` |
| `TenantNotFoundException` | `404 tenant-not-found` |
| Saloon's `RateLimitReachedException` | `429 too-many-requests`, `retry_after` and `Retry-After` |
| Any other HTTP exception | Named after its status (`Not Found` becomes `not-found`); a missing model's detail is just `Not found.` |
| Anything else | `500 internal-server-error`, except under `APP_DEBUG`, where the framework's trace is kept |

The renderer returns null, leaving the response to the framework, for a web request and for an exception that carries its own response.

### Throwing a named problem

Middleware and actions that reject a request throw a `ProblemException` rather than returning a response:

```php
use Rollogi\Core\Http\Problems\ProblemException;
use Symfony\Component\HttpFoundation\Response;

throw new ProblemException(
    Response::HTTP_CONFLICT,
    'invoice-already-sent',
    'Invoice already sent',
    'This invoice has already been sent and cannot be changed.',
    ['invoice' => $invoice->getKey()],
);
```

The problem types Core itself raises are `feature-disabled`, `tenant-required`, `tenant-forbidden`, `tenant-suspended`, `tenant-not-found`, `idempotency-key-invalid`, `idempotency-key-reused`, `idempotency-conflict`, `health-forbidden`, `validation-failed`, `unauthenticated`, `too-many-requests` and `internal-server-error`.

## Middleware

All in `Rollogi\Core\Http\Middleware`:

| Middleware | Does |
|------------|------|
| `RequestId` | Takes `X-Request-Id` from the request or generates a UUIDv7, binds it as `request-id`, and echoes it on the response |
| `SecurityHeaders` | `nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, a deny-all CSP and Permissions-Policy, COOP and CORP; HSTS (`http.hsts_max_age`) on secure requests only |
| `IdempotencyKey` | Reads the idempotency header into the request context and adds `Idempotency-Replayed: true` to a replay. See [Idempotent writes](/core/invocations#idempotent-writes) |
| `SetRequestLocale` | Picks the locale from `Accept-Language` against `api.locales`, sets `Content-Language` and `Vary: Accept-Language` |
| `ReportApiVersion` | Sets `API-Version` from `api.version` |
| `SetDefaultCacheControl` | Sets `cache-control.default` (`private, no-store`) on any response not already public |
| `AddEntityTag` | An ETag on every successful GET or HEAD, and a `304` when `If-None-Match` matches |
| `CachePublic` | Opt-in edge caching: public `Cache-Control`, `CDN-Cache-Control`, `Cache-Tag` and an ETag; never on a response that sets cookies |
| `MarkDeprecated` | `deprecated:<since>,<sunset>[,<link>]` adds `Deprecation`, `Sunset` and a `Link` with `rel="deprecation"` |

Elsewhere in Core: `ResolveTenant` ([Tenancy](/core/tenancy#resolving-the-tenant-on-a-request)) and `EnsureFeatureEnabled` ([Features](/core/features#guarding-a-route)).

## Rate limiters

The `Http` concern registers three named limiters from `rate-limiting.php`:

| Limiter | Default | Keyed by |
|---------|---------|----------|
| `api` | `RATE_LIMIT_API` = 60 per minute | User id, else IP |
| `auth` | `RATE_LIMIT_AUTH` = 10 per minute, plus `RATE_LIMIT_AUTH_ACCOUNT` = 5 per minute | IP, plus the lowercased `email` in the request when there is one |
| `tenant` | `RATE_LIMIT_TENANT` = 600 per minute | The active tenant |

The same concern forces the `https` scheme on generated URLs when `http.force_https` (`FORCE_HTTPS`) is on.

## List Data classes

`Rollogi\Core\Http\Data` holds three Data objects a list use-case builds in its controller and applies in its action:

```php
$data = new ListInvoicesData(
    pagination: PaginationData::fromRequest($request),
    sort: SortData::fromRequest($request, allowed: ['created_at', 'amount'], default: '-created_at'),
    filters: FilterData::fromRequest($request, allowed: ['status']),
);

// in the action
$data->sort->apply($query, ['amount' => 'invoices.amount']);
$data->filters->apply($query);
```

- `PaginationData` reads `per_page` (clamped to `pagination.per_page.max`, default from `pagination.per_page.default`) and the cursor parameter (`pagination.cursor_name`, `cursor`). `PaginationData::default()` is for callers outside HTTP.
- `SortData` reads `?sort=-created_at,name`; a leading minus means descending. A field outside the allow-list is a `422`.
- `FilterData` reads `?filter[status]=open,overdue`; a comma separates alternatives. A key outside the allow-list is a `422`. `apply()` uses `whereIn()` unless you pass an applier closure for that key.

## Health report

`GET /api/health` runs the checks listed in `health.checks` and answers with the worst status:

```json
{
    "status": "degraded",
    "checkedAt": "2026-10-26T09:00:00+00:00",
    "checks": [
        {"name": "database", "status": "ok", "message": "...", "details": {}, "durationMs": 3},
        {"name": "queue", "status": "degraded", "message": "database: 0 pending, 2 failed.", "details": {"connection": "database", "pending": 0, "failed": 2}, "durationMs": 1}
    ]
}
```

| Status | HTTP | Meaning |
|--------|------|---------|
| `ok` | `200` | Every check passed |
| `degraded` | `200` | Serving traffic, but something needs a look (the queue check reports failed jobs this way) |
| `failed` | `503` | A dependency is down; a load balancer can act on the code alone |

The route is guarded by a shared token, not `auth:api`, because the caller is a monitor. Send it as `X-Health-Token`; it must equal `HEALTH_TOKEN`. Without the header, or while `HEALTH_TOKEN` is unset, the route answers `403 health-forbidden` to everyone. The framework's `/up` stays the public liveness probe.

The shipped checks are `DatabaseCheck`, `CacheCheck`, `QueueCheck` and `MailCheck`. Add your own by implementing `Rollogi\Core\Health\Contracts\HealthCheck` and listing the class in `health.checks`:

```php
use Rollogi\Core\Health\Contracts\HealthCheck;
use Rollogi\Core\Health\Data\HealthCheckResultData;

class SearchBackendCheck implements HealthCheck
{
    public function name(): string
    {
        return 'search';
    }

    public function run(): HealthCheckResultData
    {
        return HealthCheckResultData::ok($this->name(), 'Reachable.');
    }
}
```

Checks are resolved from the container. An exception a check lets escape is reported as a failed check. `ShowHealthService` is a read that drops `LogServiceCall`, so a monitor polling every few seconds does not flood the log.

## Log context

`Rollogi\Core\Support\Logging\AddContext` is a Monolog tap that adds `request_id`, `user_id` and `tenant_id` to every log record. The kit adds it to its channels in `config/logging.php`:

```php
'tap' => [AddContext::class],
```
