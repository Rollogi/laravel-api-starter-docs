Core ships two Artisan generators. They write exactly the shape the [layering checks](/core/static-analysis#layering-checks) enforce, into the directory and namespace set by the [modules config](/core/package-modules#the-modules-config), and they **never overwrite** an existing file. For a walkthrough of building a use-case by hand, see [Use-cases](/kit/use-cases).

## make:module

```bash [Terminal]
php artisan make:module Billing
```

The name is a module in StudlyCase. The command refuses to run if the module directory already exists. With the default config it writes:

| File | Contents |
|------|----------|
| `app/Modules/Billing/BillingServiceProvider.php` | Loads `routes/api.php` inside `Route::middleware('api')` and the migrations directory |
| `app/Modules/Billing/routes/api.php` | A `GET /api/billing/ping` route answering `{"module": "billing"}` |
| `app/Modules/Billing/Database/Migrations/.gitkeep` | An empty migrations directory |
| `tests/Feature/Billing/BillingModuleTest.php` | A smoke test that calls the ping route |

`ModuleServiceProvider` discovers the provider on the next boot; there is nothing to register. Delete the ping route once the module has a real one.

## make:use-case

```bash [Terminal]
php artisan make:use-case Billing CreateInvoice --uri=/invoices
php artisan make:use-case Billing ListInvoices --read
```

| Argument / option | Meaning |
|-------------------|---------|
| `module` | An existing module, for example `Billing`. Its `routes/api.php` must exist. |
| `name` | The use-case in StudlyCase, verb first, for example `CreateInvoice` |
| `--read` | A use-case that persists nothing: a `ReadService`, `GET`, and a Data built in the controller |
| `--method=` | `get`, `post`, `put`, `patch` or `delete`. `post` by default, `get` with `--read` |
| `--uri=` | The path under `/api/<module>`. `/<use-case-in-kebab-case>` by default |

It writes six files and edits two:

| File | Contents |
|------|----------|
| `Data/CreateInvoiceData.php` | The input. Implements `AuthorizesService` with `Gate::authorize('<feature key>')` |
| `Data/CreateInvoiceResultData.php` | The output |
| `Actions/CreateInvoiceAction.php` | The operation, with a typed `__invoke()` |
| `Services/CreateInvoiceService.php` | `@extends Service<CreateInvoiceData, CreateInvoiceResultData>`, running the action |
| `Http/Controllers/CreateInvoiceController.php` | An invokable controller returning `JsonResponse` with `HTTP_CREATED` for `post`, `HTTP_OK` otherwise |
| `tests/Feature/Billing/CreateInvoiceTest.php` | Pest tests: a member with the permission succeeds, one without is refused |
| `routes/api.php` (edited) | Adds the controller import, sorted, and a route group on `api.tenant` and `feature:<key>` |
| `config/features.php` (edited) | Registers the feature key with `default => true` and a label |

If any of the six files already exists, nothing is written and the command lists the files in the way.

The feature key is the module in kebab case and the use-case in snake case: `billing.create_invoice`. The same name is used for the permission the generated Data checks, so the command reminds you to grant it in the seeder, or to swap the gate for a policy once the module has a model. If `config/features.php` is not laid out the way the command expects (a `features` array followed by `disabled_message`), it asks you to add the key by hand instead.

The generated route:

```php [app/Modules/Billing/routes/api.php]
Route::middleware(['api.tenant', 'feature:billing.create_invoice'])->prefix('api/billing')->group(function (): void {
    Route::post('/invoices', CreateInvoiceController::class);
});
```

### Write and read shapes

| | Write (default) | Read (`--read`) |
|-|-----------------|-----------------|
| Service base | `Service` (the write preset) | `ReadService` (the read preset) |
| Input | Validated from the request body, injected into the controller | Built in the controller from `tenancy()->id()` |
| Default method | `POST` | `GET` |

### Placeholders

The generated slice runs and its tests pass straight away on placeholder fields: the write shape takes a `name` and returns it with the tenant id, and the read shape returns the tenant id alone. Replace them with the real fields in the Data, result Data and action, then run `composer check`.

The generated test imports the user model named by `auth.providers.users.model` and uses the kit's `createUserInTenant()` and `actingAsMember()` helpers from `tests/Pest.php`.
