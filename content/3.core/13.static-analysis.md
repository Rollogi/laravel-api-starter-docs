Core keeps its conventions honest in two ways: PHPStan extensions that give Larastan the types PHP's variadic entry points hide, and a set of layering checks a test suite runs over module source.

## PHPStan extensions

`Action::run()` and its siblings are variadic static methods, so PHPStan on its own sees `mixed` going in and coming out. Core's `extension.neon` fixes that with two extensions and one rule, in the `Rollogi\Core\PhpStan` namespace:

| Class | Kind | What it does |
|-------|------|--------------|
| `ActionReturnTypeExtension` | Dynamic static return type | `SomeAction::run()` and `SomeAction::dispatchSync()` return whatever `SomeAction::__invoke()` returns |
| `ActionArgumentsRule` | Rule | Checks the arguments of `run()`, `dispatch()`, `dispatchAfterCommit()`, `dispatchSync()` and `with()` against `__invoke()`: arity, types and named arguments |
| `TenantMembersReturnTypeExtension` | Dynamic method return type | Types `$tenant->users()` as a relation of the model in `auth.providers.users.model`, which Larastan can read because it boots the application |

They also resolve the action when it is held in a variable (`$action::run()`). All three are `@internal`: the behaviour is covered by semantic versioning through `extension.neon`, the classes are not.

### Including it

Core is a library, not a `phpstan-extension` package, so `phpstan/extension-installer` does not pick it up. Include the file from your `phpstan.neon`:

```yaml [phpstan.neon]
includes:
    - vendor/larastan/larastan/extension.neon
    - vendor/rollogi/core/extension.neon
```

A project created from the kit already has this.

### What it catches

Given `class DoubleAction extends Action` with `__invoke(int $value, string $label = 'x'): int`, these are all reported:

```php
DoubleAction::run('three');            // Parameter #1 $value ... expects int, string given.
DoubleAction::run();                   // invoked with 0 parameters, 1-2 required
DoubleAction::dispatch(1, 'label', 'x'); // invoked with 3 parameters, 1-2 required
DoubleAction::run(amount: 3);          // Missing parameter $value, Unknown parameter $amount
strlen(DoubleAction::run(3));          // Parameter #1 $string of function strlen expects string, int given
```

Nothing is needed on the action beyond a typed `__invoke()`.

Services get the same benefit from generics instead: `@extends Service<Input, Output>` types `handle()`, `run()`, `dispatchSync()` and `fake()`. See [Service pipeline](/core/service-pipeline#typing).

::note
The kit proves the extensions with `tests/Feature/Core/Analysis/ActionTypingTest.php`, which runs PHPStan over deliberately wrong fixtures in `tests/Fixtures/PhpStan/` (excluded from the main analysis) and checks each expected message.
::

## Layering checks

`Rollogi\Core\Support\Testing\Layering` checks source files against the use-case flow (Data, Controller, Service, Action). Each method returns a list of violations, so a test asserts an empty list and a failure names the file and the fix.

| Method | Reports |
|--------|---------|
| `files(array $patterns)` | Not a check: expands globs into a file list |
| `packageModuleDirectories()` | Not a check: the directories of every installed [package module](/core/package-modules#package-modules) provider |
| `controllersNotDelegatingToServices($controllers)` | A controller with no `SomeService::run(` call |
| `controllersThatPersist($controllers)` | A controller calling `->create(`, `->update(`, `->delete(`, `->save(` or `->forceFill(` |
| `servicesNotRunningActions($services)` | A service with no `SomeAction::run(` call |
| `dataAuthorizingWithoutContract($dataFiles)` | A Data class with `authorizeService()` that does not implement `AuthorizesService`, which the `AuthorizeAction` stage would refuse |
| `misnamedModuleProviders($modulesPath)` | A module directory whose provider is not named `<Directory>ServiceProvider`, so it is never registered |

The checks are deliberately textual (regular expressions over the source), which keeps them fast and dependency-free.

### Running them in a project

The kit's `tests/Feature/Core/Modules/ModuleLayeringTest.php` runs them over the application's modules and every installed package module. Condensed:

```php [tests/Feature/Core/Modules/ModuleLayeringTest.php]
use Rollogi\Core\Support\ModuleLayout;
use Rollogi\Core\Support\Testing\Layering;

function moduleFiles(string $pattern): array
{
    return Layering::files([
        ModuleLayout::fromConfig()->modulePath('*', $pattern),
        ...array_map(fn (string $directory): string => $directory.'/'.$pattern, Layering::packageModuleDirectories()),
    ]);
}

it('delegates every controller to a service', function (): void {
    $controllers = moduleFiles('Http/Controllers/*.php');

    expect($controllers)->not->toBeEmpty()
        ->and(Layering::controllersNotDelegatingToServices($controllers))->toBe([]);
});

it('names every app module provider after its directory', function (): void {
    expect(Layering::misnamedModuleProviders(ModuleLayout::fromConfig()->path))->toBe([]);
});
```

Core runs the same methods over its own concerns in its `CoreLayoutTest`, so a project and the package hold their code to one shape.
