`rollogi/core` is the shared infrastructure underneath the starter kit: the service pipeline and its stages, actions and queued execution, single-database tenancy and per-tenant settings, feature toggles, RFC 9457 problem responses and the HTTP middleware, auditing, the reshaped Spatie permission tables, outbound integrations on Saloon, inbound webhooks, metrics, search indexing, health checks, module discovery, the `make:module` and `make:use-case` generators, the PHPStan extensions and the layering checks.

It holds **no business logic**. Anything about invoices, invitations or members belongs in an application module; Core only gives those modules a consistent shape to live in.

The namespace is `Rollogi\Core`, the licence is MIT, and Core is versioned on its own, independently of the starter kit. See the [changelog](/core/changelog).

## Installing

A project created from the starter kit already requires Core, so there is nothing to do. Installing it anywhere else needs access to the private `Rollogi/*` repositories: Composer reads the package from a VCS repository with a GitHub token that can see it.

```json [composer.json]
"repositories": [
    {"type": "vcs", "url": "https://github.com/Rollogi/core", "only": ["rollogi/core"]}
],
"require": {
    "rollogi/core": "^1.1"
}
```

The kit itself requires `^1.1@dev`. In the kit's own repository a `packages/*` path repository comes first and is canonical, so Composer symlinks `packages/core` and reports it as `1.x-dev`; `@dev` admits that, and `prefer-stable` makes a project created from a release take the newest `1.x` tag instead. A project may tighten the constraint to `^1.1`.

### Wiring

Core is wired explicitly rather than through package discovery. Two providers go in `bootstrap/providers.php`:

```php [bootstrap/providers.php]
return [
    AppServiceProvider::class,
    CoreServiceProvider::class,
    ModuleServiceProvider::class,
];
```

The middleware aliases, the `api.tenant` group, the priority list and the problem-details renderer are composed in `bootstrap/app.php`, which stays the one place the whole HTTP stack is visible. See [HTTP and health](/core/http) for the renderer line.

### What Core expects of the application

- a user model named by `auth.providers.users.model` that implements `Rollogi\Core\Tenancy\Contracts\TenantMember` (use the `HasTenants` trait), in a `users` table with UUID keys;
- an `api` guard, which queued calls restore the acting user on;
- the framework's jobs migration (`jobs`, `failed_jobs`), which queued calls rely on;
- `config/permission.php` with teams on and keyed by `tenant_id`, and `config/audit.php`. Core creates the permission and `audits` tables itself and reads their names and columns from these two files;
- `config/features.php` as the feature registry.

## Concerns

`CoreServiceProvider` registers one provider per concern from its `CONCERNS` constant. It is a list rather than a directory scan, because a package has nothing under the application's path to scan.

| Concern | What it owns |
|---------|--------------|
| `Auditing` | The owen-it `audits` table and `Audit` model, `AuditsWithRequestContext`, the daily prune |
| `Authorization` | The Spatie permission tables reshaped for Core (UUID keys, `tenant_id`, surrogate pivot keys), `Role`, `Permission` |
| `Features` | `FeatureManager`, `FeatureSource`, `feature_settings`, `feature:list` and `feature:set`, the `EnsureFeatureEnabled` middleware |
| `Generators` | `make:module` and `make:use-case` with their stubs |
| `Health` | `GET /api/health`, the `HealthCheck` contract and the shipped checks |
| `Http` | The middleware, problem details, `PaginationData`, `SortData`, `FilterData`, the `api`, `auth` and `tenant` rate limiters, `FORCE_HTTPS` |
| `Integrations` | `Connector`, `CacheableRequest`, `SendIntegrationRequest`, `integration_audits`, inbound webhooks and `webhook_events` |
| `Metrics` | The `Metrics` contract, the `null` and `log` drivers, `MetricsFake` |
| `Search` | The `SearchIndexer` contract, its drivers, `IndexesForSearch`, `RemovesFromSearch`, `SearchIndexerFake` |
| `Services` | `Service`, `ReadService`, `StagePreset`, the stages, `ServiceInvocation` and its events, idempotency, `service_audits` |
| `Tenancy` | `Tenant`, `TenantContext`, `TenantScope`, `ResolveTenant`, `TenantSettings`, `ResetTenantState`, the `tenants`, `tenant_user` and `tenant_settings` tables |

Four more directories have no provider: `Actions` (the `Action` base and `PendingAction`), `Models` (the shared base `Model` and its traits, and nothing else), `Support` (execution context, logging, `ModuleLayout`, the `tenancy()` helper and the layering checks) and `Providers` (`CoreServiceProvider` and `ModuleServiceProvider`).

Each concern is laid out like an application module: it owns its `Models/` and `Database/Migrations/`, plus `Actions/`, `Services/`, `Http/Controllers/` and `routes/` where it has any. A model owned by a concern lives in that concern, for example `Rollogi\Core\Tenancy\Models\Tenant` or `Rollogi\Core\Integrations\Models\WebhookEvent`.

## Configuration

Core ships fourteen config files, listed in `CoreServiceProvider::CONFIG`, and merges them in as defaults. A project only keeps the ones it changes in `config/`:

```bash [Terminal]
php artisan vendor:publish --tag=rollogi-core-config
```

::warning
The merge is shallow. A published file replaces each top-level key it defines, so if you publish `rate-limiting.php` and delete the `tenant` entry, the tenant limiter loses its configuration rather than falling back to Core's default.
::

| File | Holds |
|------|-------|
| `api.php` | `version` (`API_VERSION`), the `API-Version` header value; `locales` (`API_LOCALES`) |
| `cache-control.php` | The default `Cache-Control` directive and the `cache.public` lifetimes |
| `health.php` | `token` (`HEALTH_TOKEN`) and the list of `checks` |
| `http.php` | `force_https` (`FORCE_HTTPS`), `hsts_max_age` (`HSTS_MAX_AGE`) |
| `idempotency.php` | `header`, `ttl_minutes`, `lock_seconds` |
| `integrations.php` | Timeout, retries, audit bodies and redaction, webhook signature header, rate-limit and cache stores |
| `metrics.php` | `driver` (`METRICS_DRIVER`), `log_channel` |
| `modules.php` | `path`, `namespace`, `tests_path` for module discovery and the generators |
| `pagination.php` | `per_page.default`, `per_page.max`, `cursor_name` |
| `problems.php` | `type_base` (`PROBLEM_TYPE_BASE`), the base URL of problem `type` URIs |
| `rate-limiting.php` | `api`, `auth`, `auth_account` and `tenant` limits |
| `search.php` | `driver` (`SEARCH_DRIVER`), `log_channel` |
| `service-audits.php` | `retention_days` (`SERVICE_AUDIT_RETENTION_DAYS`, default 365) |
| `tenant-settings.php` | The per-tenant settings registry |

## Public API

Semantic versioning covers everything that is not marked `@internal`. Within `1.x` these keep working as documented:

- **Use-cases:** `Services\Concerns\Service` and `ReadService` (including `stages()`, `stagesWithout()`, `afterCommit()` and `failed()`), `StagePreset` and `StageInsertion`, the shipped stages in `Services\Stages`, `ServiceInvocation`, the `ServiceStarted`, `ServiceCompleted` and `ServiceFailed` events, the `AuthorizesService` and `InvalidatesCacheTags` contracts, `Actions\Concerns\Action` and `PendingAction`, the `dispatch*()`, `chain()`, `batch()` and `fake()` helpers with their fakes, and `Support\Execution\ExecutionContext`.
- **Tenancy:** `tenancy()` and `TenantContext`, `TenantScope`, `Tenant`, `TenantSetting` and `TenantSettings`, the `TenantMember` contract and `HasTenants` trait, `ResolveTenant`, `ResetTenantState`, `ActivateTenantAction`, `CreateTenantAction` and `FindTenantAction`, and their exceptions.
- **Models:** `Models\Model`, `BelongsToTenant`, `HasUuidPrimaryKey`, and each concern's models (`Audit`, `Role`, `Permission`, `FeatureSetting`, `ServiceAudit`, `IntegrationAudit`, `WebhookEvent`) with their tables. Core's migrations keep their file names.
- **Features:** `FeatureManager` (with its `SOURCES` tag), the `FeatureSource` contract, `FeatureScope`, `FeatureResolution`, the `FeatureLayer` enum, `EnsureFeatureEnabled`, `UnknownFeatureException` and `ResolvesTenantOption`.
- **HTTP:** the middleware in `Http\Middleware`, `ProblemDetails`, `ProblemException`, `ProblemDetailsRenderer`, and `PaginationData`, `SortData` and `FilterData`.
- **Extension points:** `Integrations\Connector`, `CacheableRequest`, `SendIntegrationRequest`, `WebhookHandler` and `WebhookRegistry`; `Health\Contracts\HealthCheck` and the shipped checks; the `Metrics` and `SearchIndexer` contracts with their drivers and fakes, `IndexesForSearch` and `RemovesFromSearch`; `AuditsWithRequestContext`; `Support\Logging\AddContext`.
- **Wiring and tooling:** `CoreServiceProvider`, `ModuleServiceProvider` and its manifest key, `ModuleLayout`, `Support\Testing\Layering`, `extension.neon`, the artisan commands' names and options, every config key, the problem `type` names and the HTTP headers Core reads and writes.

### What is `@internal`

Classes Core wires up itself carry `@internal` and may change in any release: the concern service providers, the controllers, services and actions behind Core's own routes and stages, the idempotency store and context, the queued invocation job (`QueuedInvocation`), the generators' classes and the PHPStan rules and extensions. Reach them through the public classes above, or rebind them in the container at your own risk.

## Developing Core

Core is developed in `packages/core` of the starter kit's repository and published to a read-only copy on every push. It has its own suite on Testbench, with a minimal workbench `User`, which CI runs as the `core` job:

```bash [Terminal]
cd packages/core && composer install && composer analyse && composer test
```
