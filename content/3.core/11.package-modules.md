`Rollogi\Core\Providers\ModuleServiceProvider` registers every module's service provider. There is no registry to edit: an application module is found by its directory, and a package module by a key in its `composer.json`.

## Application modules

For every directory directly under the modules path, `ModuleServiceProvider` registers `<namespace>\<Name>\<Name>ServiceProvider` when that class exists, in directory-name order. With the defaults that means `app/Modules/Billing/BillingServiceProvider.php`, class `App\Modules\Billing\BillingServiceProvider`.

::warning
The naming is load-bearing. A provider not named after its directory is silently never registered. `Layering::misnamedModuleProviders()` catches it in a test; see [Static analysis](/core/static-analysis#layering-checks).
::

A module provider wires everything the module owns in its `boot()`: `loadRoutesFrom`, `loadMigrationsFrom`, singleton bindings, `$this->commands(...)` and `Gate::policy(...)`. [make:module](/core/generators) writes one.

### The modules config

`modules.php`, read through `Rollogi\Core\Support\ModuleLayout`:

| Key | Default (null means) | Used for |
|-----|----------------------|----------|
| `path` | `app_path('Modules')` | Where modules are discovered and where the generators write |
| `namespace` | The application namespace plus `Modules` (`App\Modules`) | The namespace that directory autoloads as; it must match the PSR-4 mapping in `composer.json` |
| `tests_path` | `base_path('tests/Feature')` | Where the generators write a module's tests, one directory per module |

`ModuleLayout::fromConfig()` gives you the same answers in your own tooling: `providerClass($module)`, `moduleNamespace($module)`, `modulePath($module, $relative)` and `testPath($module, $relative)`.

## Package modules

A module can also ship as a Composer package. The package lists its module providers under `extra.laravel.api-starter-modules`:

```json [composer.json]
"extra": {
    "laravel": {
        "api-starter-modules": ["Acme\\Billing\\BillingServiceProvider"]
    }
}
```

`ModuleServiceProvider` reads them from Laravel's package manifest (`bootstrap/cache/packages.php`, rebuilt by `package:discover` on `composer dump-autoload`). The key is `ModuleServiceProvider::ManifestKey`.

- **Not in `providers` as well.** A provider listed under `extra.laravel.providers` too registers early, before Core, and twice.
- **Order.** Package modules register first, in manifest order, then application modules by directory name. An application module's `register()` therefore runs after every package's.
- **Rebinding.** A package binds its defaults with `bindIf` or `singletonIf`. An application replaces one with a plain `bind` or `singleton` in its own module's `register()`, and that wins whichever registers first.
- **Opting out.** Listing the package under `extra.laravel.dont-discover` in the root `composer.json` drops its modules along with its providers.
- **Missing provider.** A declared class that does not exist fails the boot with `Package <name> declares module <class>, which does not exist.` rather than being skipped.
- **Data classes** in a package are reflected at runtime. `data:cache-structures` maps class names from paths under `base_path()`, so it cannot cache classes under `vendor/`.

### What a package module wires itself

Nothing outside a package module applies its middleware or registries, so it does all of this itself:

- **Routes inside `Route::middleware('api')`**, as Core's own concerns do:

  ```php
  public function boot(): void
  {
      Route::middleware('api')->group(function (): void {
          $this->loadRoutesFrom(__DIR__.'/../routes/api.php');
      });
  }
  ```

- **Tenancy on authenticated resource routes**: the application's `api.tenant` group or the package's own middleware. Nothing enforces it, and a route without it sees every tenant's data.
- **A static guard around anything process-global** (Saloon's global middleware, a static registry), so a second registration in the same process (Octane, tests) does not add it twice. Core's `IntegrationsServiceProvider` shows the pattern:

  ```php
  private static bool $registered = false;

  public function boot(): void
  {
      if (self::$registered) {
          return;
      }

      self::$registered = true;

      // register the global middleware once
  }
  ```

- **Stage insertions and feature sources** through Core's extension points, from `boot()`: `StagePreset::insert()` ([Service pipeline](/core/service-pipeline#inserting-into-a-preset)) and the `FeatureManager::SOURCES` tag ([Features](/core/features#feature-sources)).

The kit's `ModuleLayeringTest` runs its controller and service checks over each package module's directory too, through `Layering::packageModuleDirectories()`.

::tip
[rollogi/billing](/billing) and [rollogi/nuxt-ui](/nuxt-ui) are both package modules, and are the fullest examples of all of the above.
::

## Developing a package alongside the kit

The kit's `composer.json` has a `packages/*` path repository listed first, so a package in `packages/<name>` with its own `composer.json` is symlinked into `vendor/` by `composer require`. `packages/` stays in every project created from the kit for exactly this purpose.
