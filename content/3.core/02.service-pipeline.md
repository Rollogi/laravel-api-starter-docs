A service orchestrates one use-case. It extends `Rollogi\Core\Services\Concerns\Service`, and when it runs, its input passes through a list of **stages** (a Laravel `Pipeline`) with the service's `handle()` as the terminal. The stages give every use-case the same authorisation, logging, audit trail, metrics and transaction boundary without the service writing any of it.

**Services orchestrate; actions execute.** A service holds no logic that could be reused elsewhere. It runs [actions](/core/actions), which is where the work lives. For how a request reaches a service (Data, invokable controller, service, action, policy), see [Use-cases](/kit/use-cases).

## Writing a service

```php [app/Modules/Billing/Services/CreateInvoiceService.php]
use Rollogi\Core\Services\Concerns\Service;

/**
 * @extends Service<CreateInvoiceData, InvoiceResultData>
 */
class CreateInvoiceService extends Service
{
    protected function handle(mixed $input): mixed
    {
        return CreateInvoiceAction::run((string) tenancy()->id(), $input->amount);
    }
}
```

Run it from anywhere:

```php
$invoice = CreateInvoiceService::run($data);
```

`run()` resolves the service from the container and invokes it. The same service can also be queued with `dispatch()`, `dispatchAfterCommit()` or `dispatchSync()`, which run the whole pipeline on the worker under the dispatching tenant and user; see [Actions](/core/actions#services-off-the-request).

### Typing

`Service` is generic over its input and output. Declare both with `@extends Service<Input, Output>` and Larastan types the rest: `handle()` receives the input type without an `assert()`, and `run()`, `dispatchSync()` and `fake()` return the output type, so a controller that misreads the result fails static analysis. A service that returns nothing declares `null` as its output; one that may return either of two Data classes declares the union.

## The presets

A service that does not override `stages()` runs the **write preset**, `StagePreset::WRITE`, in this order:

1. `AuthorizeAction`
2. `LogServiceCall`
3. `ReplayIdempotentCall`
4. `AuditServiceCall`
5. `EmitMetric`
6. `InvalidateCacheTags`
7. `IndexForSearch`
8. `WrapInTransaction`

Authorisation runs first so a denied caller never reaches the work, and it is a no-op for an input that does not carry its own authorisation, so a public or account-level use-case loses nothing by it. `ReplayIdempotentCall` sits after the log, so a replay is still logged, and before the audit, so a replay writes no second audit row. The cache and search stages do nothing unless the input or result asks for them, and the metric costs nothing under the default `null` driver.

A use-case that persists nothing extends `ReadService` instead, which runs the **read preset**, `StagePreset::READ`:

1. `AuthorizeAction`
2. `LogServiceCall`
3. `EmitMetric`

No audit row, no transaction, nothing to invalidate or index, and no idempotency.

```php
use Rollogi\Core\Services\Concerns\ReadService;

/**
 * @extends ReadService<ListInvoicesData, InvoiceListData>
 */
class ListInvoicesService extends ReadService
{
    protected function handle(mixed $input): mixed
    {
        return ListInvoicesAction::run($input->pagination);
    }
}
```

## Shipped stages

| Stage | What it does |
|-------|--------------|
| `AuthorizeAction` | Calls `authorizeService()` on an input that implements `Rollogi\Core\Services\Contracts\AuthorizesService`. An input that has an `authorizeService()` method **without** the interface is refused with a `LogicException`, because a check the stage would silently skip is worse than none. |
| `LogServiceCall` | Writes `service.<Class> ok` at info level, or `service.<Class> failed` at error level with the exception message, with `duration_ms` in the context. |
| `ReplayIdempotentCall` | Under an `Idempotency-Key` header, answers a repeat of the same input with the first call's stored result and runs nothing after it. See [Invocations and idempotency](/core/invocations#idempotent-writes). |
| `AuditServiceCall` | Writes a `service_audits` row: service, `actor_id`, `tenant_id`, `status` (`ok` or `failed`), `duration_ms` and `request_id`. The tenant is read when the call ends, so a service that creates and activates a tenant audits under it. |
| `EmitMetric` | Increments `service.calls` and records `service.duration` (milliseconds) on the `Metrics` contract, tagged `service` and `outcome`. See [Metrics and search](/core/metrics-and-search). |
| `InvalidateCacheTags` | Flushes the tags an input declares through `InvalidatesCacheTags`, once the outermost transaction commits. |
| `IndexForSearch` | Queues a search-index write for a result implementing `IndexesForSearch`, or a removal for an input implementing `RemovesFromSearch`, after commit. |
| `WrapInTransaction` | Runs the rest of the pipeline and `handle()` inside `DB::transaction()`, rolling back on an exception. |

### Authorising a use-case

The input Data carries its own authorisation, so the check travels with the input wherever the service is run from (a controller, a queued job, a console command), not only at the HTTP door:

```php
use Illuminate\Support\Facades\Gate;
use Rollogi\Core\Services\Contracts\AuthorizesService;
use Spatie\LaravelData\Data;

class CreateInvoiceData extends Data implements AuthorizesService
{
    public function __construct(public readonly int $amount) {}

    public function authorizeService(): void
    {
        Gate::authorize('create', Invoice::class);
    }
}
```

Throw an `AuthorizationException` to deny; `Gate::authorize()` does.

### Invalidating cache tags

An input that implements `Rollogi\Core\Services\Contracts\InvalidatesCacheTags` returns its tags from `cacheTags()`. The stage sits outside `WrapInTransaction`, so the service's own transaction has closed by the time it flushes; inside an outer transaction (one service calling another) the flush waits for the outermost commit and is dropped on rollback, so a reader never sees a cache cleared for a write that did not land.

As with `authorizeService()`, a `cacheTags()` method without the interface is refused with a `LogicException`. The file and database cache stores cannot tag: on one of those the stage logs a `cache.tags-unsupported` warning and leaves the entries alone rather than failing the write.

## Dropping a stage

A write that must not run inside a transaction keeps the rest of the preset and says why:

```php
/**
 * A failed attempt is recorded and then ValidationException is thrown; a transaction would roll
 * the record back.
 */
#[Override]
protected function stages(): array
{
    return $this->stagesWithout(WrapInTransaction::class);
}
```

Core's own inbound webhook receiver does this: it relies on a unique index rejecting a duplicate insert, and on PostgreSQL a failed statement aborts the surrounding transaction.

## Side effects after commit

Work that must wait for the write to land is registered from `handle()`:

```php
protected function handle(mixed $input): mixed
{
    $invoice = CreateInvoiceAction::run((string) tenancy()->id(), $input->amount);

    $this->afterCommit(function () use ($invoice): void {
        event(new InvoiceCreated($invoice));
    });

    return InvoiceResultData::from($invoice);
}
```

The callback runs when the outermost transaction commits (immediately when there is none) and is discarded on rollback, so a nested service defers to the service that called it.

A service may also override `failed(Throwable $exception)` to react to an exception from any stage or from `handle()` before it propagates.

## Adding a stage of your own

A stage is any class with `handle(mixed $passable, Closure $next): mixed`. It reads the running call through `ServiceInvocation::currentOrStart($passable)`:

```php
use Closure;
use Rollogi\Core\Services\ServiceInvocation;

class RecordThroughput
{
    public function handle(mixed $passable, Closure $next): mixed
    {
        $invocation = ServiceInvocation::currentOrStart($passable);

        try {
            return $next($passable);
        } finally {
            // $invocation->service, ->tenantId, ->actorId, ->requestId, ->durationMs()
        }
    }
}
```

For one service, append it to the preset rather than listing every stage by hand:

```php
protected function stages(): array
{
    return [...$this->defaultStages(), RecordThroughput::class];
}
```

## Inserting into a preset

A package that wants a stage on **every** service inserts it into the preset from a provider's `boot()`. `StagePreset` is a singleton filled once at boot, so it holds no per-request state.

```php
use Rollogi\Core\Services\StagePreset;
use Rollogi\Core\Services\Stages\EmitMetric;
use Rollogi\Core\Services\Stages\ReplayIdempotentCall;

public function boot(): void
{
    $this->app->make(StagePreset::class)->insert(EnforcePlanLimit::class)->after(ReplayIdempotentCall::class);
    $this->app->make(StagePreset::class)->insert(TraceRead::class)->before(EmitMetric::class)->reads();
}
```

The first line is how [rollogi/billing](/billing) enforces plan limits on every write.

| Call | Effect |
|------|--------|
| `insert(Stage::class)` | Starts an insertion. With no anchor the stage is appended. |
| `->before(Anchor::class)` / `->after(Anchor::class)` | Places it next to a stage. The anchor may be a stage inserted earlier; insertions at the same anchor keep their registration order. |
| (default) | Joins the write preset only. |
| `->reads()` | Joins the read preset only. |
| `->both()` | Joins both presets. |

The rules:

- An insertion is placed against the **full** preset, before `stagesWithout()` filters it. A service that drops `WrapInTransaction` still runs a stage inserted after it; `stagesWithout(EnforcePlanLimit::class)` drops the inserted stage itself.
- A service whose `stages()` returns a hand-written list, without `defaultStages()`, gets no insertions, deliberately.
- An anchor missing from the preset, or a stage the preset already holds, throws a `LogicException` once the application has booted (Core validates both presets in a `booted()` callback), not on the first request.

`StagePreset::WRITE` and `StagePreset::READ` remain the base lists; `app(StagePreset::class)->write()` and `->read()` return them with the insertions applied.
