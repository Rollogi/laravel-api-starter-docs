Core receives webhooks from third parties at one route, verifies their signature, stores them and processes them on the queue. Outbound webhooks to your own customers are a kit module; see [Webhooks](/kit/webhooks).

## The endpoint

```http
POST /api/integrations/{integration}/webhook
```

Public (no authentication), inside the `api` middleware group and on the `throttle:api` limiter. `{integration}` is the key a handler was registered under.

## Registering a handler

Extend `Rollogi\Core\Integrations\Webhooks\WebhookHandler` and implement `secret()` and `handle()`:

```php [app/Modules/Acme/Webhooks/AcmeWebhookHandler.php]
use Rollogi\Core\Integrations\Models\WebhookEvent;
use Rollogi\Core\Integrations\Webhooks\WebhookHandler;

class AcmeWebhookHandler extends WebhookHandler
{
    public function secret(): string
    {
        return (string) config('services.acme.webhook_secret');
    }

    public function handle(WebhookEvent $event): void
    {
        // $event->getAttribute('payload'), $event->getAttribute('event_type')
    }
}
```

Register it in your module provider's `boot()`:

```php
use Rollogi\Core\Integrations\Webhooks\WebhookRegistry;

$this->app->make(WebhookRegistry::class)->register('acme', AcmeWebhookHandler::class);
```

`WebhookRegistry` is a singleton holding class names; each handler is resolved from the container when it is needed.

### What the base class does

| Method | Default | Override when |
|--------|---------|---------------|
| `verify(Request $request): bool` | `hash_hmac('sha256', <raw body>, secret())` compared with `hash_equals` against the signature header; an empty header fails | The provider signs differently (timestamps, other algorithms) |
| `signatureHeader(): string` | `integrations.webhooks.signature_header` (`WEBHOOK_SIGNATURE_HEADER`, default `X-Signature`) | The provider uses its own header |
| `eventId(Request $request): ?string` | `event_id` from the JSON body | The id lives elsewhere |
| `eventType(Request $request): ?string` | `type` from the JSON body | The type lives elsewhere |

Keep secrets in env and config, read through `secret()`. They are never stored.

## Processing flow

`ReceiveWebhookService` returns a `WebhookOutcome`, and the controller maps it onto a status code:

1. **Handler lookup.** An unknown integration key answers `404` and stores nothing.
2. **Signature.** An invalid signature stores a `webhook_events` row with `signature_valid = false` and `status = failed`, **without** the payload, and answers `401`.
3. **Duplicates.** When `eventId()` returns an id already stored for that integration, the request answers `200` and nothing new is written.
4. **Storage.** A row is created with `status = received`. The signature header and the headers in `integrations.audit.redact_headers` are stripped from the stored `headers`. If a concurrent delivery wins the race, the unique index on `(integration, event_id)` rejects the insert and the request is treated as a duplicate (`200`).
5. **Dispatch.** A `ProcessWebhook` job is queued and the request answers `200`.
6. **Processing.** The job calls `handle($event)`. Success sets `status = processed`; an exception sets `status = failed` with the message in `error` and is rethrown, so the queue retries it (3 tries).

The response bodies are small JSON acknowledgements (`Unknown integration.`, `Invalid signature.`, `Already processed.`, `Received.`) rather than problem documents, since the caller is the provider's delivery system.

::note
The receiving service drops `WrapInTransaction`. Step 4 recovers from a unique-constraint violation, and on PostgreSQL a failed statement aborts the surrounding transaction, so the insert runs in its own savepoint instead.
::

## No ambient tenant

Webhooks carry no tenant context: `webhook_events.tenant_id` is null and `ProcessWebhook` does not set one. A handler that does tenant-scoped work resolves the tenant from the payload and activates it itself:

```php
public function handle(WebhookEvent $event): void
{
    $tenant = FindTenantAction::run((string) $event->getAttribute('payload')['tenant_id']);

    ActivateTenantAction::run($tenant);

    // tenant-scoped work
}
```

## The webhook_events table

| Column | Holds |
|--------|-------|
| `integration` | The `{integration}` key |
| `event_id` | The provider's id, nullable; unique with `integration` |
| `event_type` | The type read from the payload, nullable |
| `signature_valid` | `false` for rejected attempts |
| `status` | `received`, then `processed` or `failed` |
| `payload` | The JSON body; null for rejected attempts |
| `headers` | Stored headers with the signature and denylisted headers removed |
| `error` | The exception message when processing failed |

Rows are pruned daily after `WEBHOOK_EVENT_RETENTION_DAYS` (default 90). Duplicate detection works only while a row exists, so keep that window longer than any provider's redelivery window.

::tip
Rejected attempts are stored too, for audit. On a public endpoint, consider a dedicated rate limiter on top of `throttle:api` so repeated forgeries cannot grow the table quickly.
::
