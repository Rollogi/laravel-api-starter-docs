## ServiceInvocation

Every service call is described by one `Rollogi\Core\Services\ServiceInvocation`. `Service::__invoke()` starts it before the first stage, binds it in the container as `running-invocation` so every stage shares one clock and one identity, and completes or fails it when the pipeline returns or throws.

| Property / method | Value |
|-------------------|-------|
| `service` | The service class name. For an anonymous class the NUL byte PHP puts in the name is replaced with `@`, because PostgreSQL cannot store it. |
| `input` | The input the service was called with |
| `tenantId` | The active tenant when the call started; once it has ended, the tenant it ended under (a service that creates and activates a tenant reports the new one) |
| `actorId` | `Auth::id()` when the call started |
| `requestId` | The request id, when one is bound |
| `startedAt` | `microtime(true)` at the start |
| `outcome` | `null` while running, then `ServiceOutcome::Ok` or `ServiceOutcome::Failed` |
| `result` / `exception` | Set once the call has completed or failed |
| `durationMs()` | Milliseconds since the start, frozen once the call has ended |
| `metricTags($outcome)` | `['service' => ..., 'outcome' => ...]`. The tenant is left out on purpose. |

Read it from anywhere inside a call:

```php
use Rollogi\Core\Services\ServiceInvocation;

ServiceInvocation::current();              // ?ServiceInvocation, null outside a service
ServiceInvocation::currentOrStart($input); // starts one when a stage runs on its own, as in a unit test
```

Nested services each get their own invocation; when the inner call ends, the outer one is bound again. The container also holds the bare class name as `running-service`. Both bindings are listed under `flush` in the kit's `config/octane.php`, so a reused worker never sees the previous request's call.

`ServiceOutcome` values double as the `status` column of `service_audits` and the `outcome` metric tag (`ok`, `failed`).

## Lifecycle events

`Service::__invoke()` fires three events, each carrying the invocation:

| Event | When | What the invocation has |
|-------|------|-------------------------|
| `ServiceStarted` | Before the first stage | No outcome yet |
| `ServiceCompleted` | After the pipeline returned | `outcome`, `result`, `durationMs()` |
| `ServiceFailed` | When a stage or `handle()` threw, before it propagates and before `failed()` runs | `outcome`, `exception`, `durationMs()` |

All three live in `Rollogi\Core\Services\Events`. Listen for anything that should see every call without being a stage, such as a tracing span or an alert on repeated failures:

```php
use Illuminate\Support\Facades\Event;
use Rollogi\Core\Services\Events\ServiceFailed;

Event::listen(function (ServiceFailed $event): void {
    $invocation = $event->invocation;

    report(sprintf('%s failed after %d ms', $invocation->service, $invocation->durationMs()));
});
```

::note
Listeners run inline, inside the call. Anything slow belongs in a queued [action](/core/actions).
::

## Idempotent writes

A client that may have to retry a write (a mobile app on a flaky connection, a payment flow) sends an `Idempotency-Key` header with a fresh value per logical request; a UUID is the usual choice. Two pieces handle it:

- the `IdempotencyKey` middleware, prepended to the kit's `api` group, validates the header and reads it into the request-scoped `IdempotencyContext`;
- the `ReplayIdempotentCall` stage in the write preset does the replaying.

### What happens

- **First call.** It runs normally. Once the write has committed, its result is stored in the cache, keyed by tenant, actor, service and a SHA-1 of the key, for `ttl_minutes`. The stored result is encrypted with the application key, because a replayable answer can carry a credential (a new API key, a webhook secret, a session token).
- **Repeat, same input.** The stored result is returned and nothing after the stage runs: no second audit row, metric, cache flush or index write. The log line is still written. The middleware adds `Idempotency-Replayed: true` to the response, and the controller answers with the same status code it gave the first time.
- **Repeat, different input.** Refused with `422 idempotency-key-reused`. Inputs are compared by a fingerprint of the serialised input.
- **Duplicate in flight.** While the first call is still running, a duplicate is refused with `409 idempotency-conflict`. The lock is held until the result has been stored, so a duplicate arriving between the write and the store cannot slip through; it expires on its own after `lock_seconds`.
- **A call that throws** stores nothing and releases the lock at once, so the client may retry with the same key.
- **An invalid key** (empty, longer than 255 characters, or not printable ASCII) is refused with `400 idempotency-key-invalid` before anything runs.

### Scope

Only the first service of the request takes part. A service it calls passes straight through, so the key describes the request's use-case rather than every step of it. Requests without the header are never deduplicated. Reads are not covered, since `ReadService` has no such stage, and neither is a queued service, since the key belongs to the HTTP request.

A cache store that cannot lock gets no in-flight protection, but replays still work.

### Configuration

`packages/core/config/idempotency.php`, published with the rest of [Core's configuration](/core#configuration):

| Key | Env | Default | Meaning |
|-----|-----|---------|---------|
| `header` | `IDEMPOTENCY_HEADER` | `Idempotency-Key` | The request header the middleware reads |
| `ttl_minutes` | `IDEMPOTENCY_TTL_MINUTES` | `1440` | How long a stored result stays replayable |
| `lock_seconds` | `IDEMPOTENCY_LOCK_SECONDS` | `30` | How long the lock around the first execution may be held before it expires |

::tip
A stage a package [inserts](/core/service-pipeline#inserting-into-a-preset) after `ReplayIdempotentCall` is skipped on a replay, along with everything else after it. That is why rollogi/billing's plan-limit check sits there: a replayed create is answered from the store rather than refused against the row it already made.
::
