The starter kit and its three packages are versioned separately. The kit is tagged `v<semver>` on `main` and released from GitHub's Releases page; `rollogi/core`, `rollogi/billing` and `rollogi/nuxt-ui` each have their own tags and are published to their own repositories (see [Releasing the packages](/releases/packages)).

This page is for maintainers of the kit itself. A project generated from the kit has no `.github/` directory, and the kit's release tooling skips in any other repository.

## Cutting a release

1. Open **Releases > Draft a new release**. Create the tag there, for example `v2.1.0`, on `main`.
2. Click **Generate release notes**, edit them if you like, and **Publish**.

Publishing starts `.github/workflows/release.yml`, which does the rest.

::note
Tag Core first. The release's fresh-install check resolves `rollogi/core` from its own repository, so the Core version the tag requires must already be split and tagged there.
::

## How the notes are grouped

`.github/release.yml` shapes the notes GitHub generates. Each merged pull request lands under the first category whose label it carries:

| Label | Section |
| --- | --- |
| `enhancement` | Added |
| `bug` | Fixed |
| `documentation` | Documentation |
| `dependencies`, `github_actions`, `php` | Dependencies |
| anything else | Other changes |

A pull request labelled `skip-changelog` is left out.

## What the workflow does

The workflow runs on `release: published` and has five jobs.

| Job | What it checks or does |
| --- | --- |
| `verify` | Refuses a tag that is not `v<semver>` or whose commit is not on `main`, and finds the previous `v*` release for the compare link |
| `checks` | Runs the whole CI matrix (`ci.yml`) on the tagged commit: Pint, Larastan, Rector and Pest on SQLite, the package suites, and Pest on MySQL 8.4 and PostgreSQL 17 |
| `install` | Creates a fresh project from the tag with `composer create-project`, as a consumer would, then runs `composer setup` and `composer test` inside it |
| `image` | Builds the production `Dockerfile` from the tag, without pushing it |
| `changelog` | Once all of the above pass, folds the release into `CHANGELOG.md` on `main` |

If `verify`, `checks`, `install` or `image` fails, a `rollback` job turns the release back into a draft and the run summary says why, so a broken tag is never shown as the latest release. Fix `main`, move or recreate the tag, and publish again.

### The fresh install

The install job is the closest thing to a real consumer. Both repositories it needs are private: Composer downloads the tag's archive from the kit's repository and, since the archive leaves `packages/core` out, installs `rollogi/core` from `Rollogi/core`. The workflow's own token reaches the kit's repository only, so the job authenticates with the `ROLLOGI_CORE_TOKEN` secret, which reads both.

### The image

`image` builds the production image with Docker Buildx and the GitHub Actions cache, tagged `laravel-api-starter:<tag>`, but does not push it, because the kit has no registry of its own. A project that wants to publish its image adds a registry login and `push: true` to that job, or copies the job into its own workflow.

## Recording the release in the changelog

The `changelog` job checks out `main` and:

1. reads the release notes, and if the release was published with empty notes, generates GitHub's notes and writes them onto the release too;
2. runs `scripts/release/update-changelog.php`, which makes a `## [2.1.0] - <date>` section out of whatever was waiting under **Unreleased**, followed by the release notes with their headings demoted one level, and rewrites the compare links at the bottom;
3. commits `CHANGELOG.md` to `main` as `github-actions[bot]` with the message `Record v2.1.0 in the changelog`, and puts the new section in the run summary.

The date is the release's publish date. The script is idempotent: a version already in the changelog is left alone, so re-running a release never duplicates its section. It fails if there is nothing to record, that is when Unreleased is empty and the release has no notes.

::tip
Write Unreleased entries by hand when a change needs more explanation than its pull request title gives. They end up beside the generated pull request list in the release's section.
::

The script is covered by `tests/Unit/Release/UpdateChangelogTest.php`. It runs with plain `php` and no Composer autoload, which is why everything under `scripts/` stays free of framework helpers.

## Secrets

| Secret | Used by | Needs |
| --- | --- | --- |
| `ROLLOGI_CORE_TOKEN` | `release.yml` (fresh install), `split-core.yml` | A fine-grained token with Contents read and write on `Rollogi/core` and read on the kit's repository |

The rest of the workflow uses the job's own `github.token`, with `contents: write` to push the changelog and edit the release.
