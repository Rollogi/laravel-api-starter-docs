`rollogi/core`, `rollogi/billing` and `rollogi/nuxt-ui` are developed in the kit's repository under `packages/` and published to their own private, read-only repositories, which is where a project installs them from. Each is versioned on its own, apart from the kit and from each other.

| Package | Source | Published to | Workflow | Tag in the kit | Secret |
| --- | --- | --- | --- | --- | --- |
| `rollogi/core` | `packages/core` | `Rollogi/core` | `split-core.yml` | `core-v<semver>` | `ROLLOGI_CORE_TOKEN` |
| `rollogi/billing` | `packages/billing` | `Rollogi/billing` | `split-billing.yml` | `billing-v<semver>` | `ROLLOGI_BILLING_TOKEN` |
| `rollogi/nuxt-ui` | `packages/nuxt-ui` | `Rollogi/nuxt-ui` | `split-nuxt-ui.yml` | `nuxt-ui-v<semver>` | `ROLLOGI_NUXT_UI_TOKEN` |

## A release in three steps

1. **Date the changelog on `develop`.** Run the [prepare-package-release workflow](#preparing-a-release), which moves the package's Unreleased entries into a dated section and merges that into `develop`.
2. **Merge `develop` into `main`.**
3. **Tag `main`** with the package's tag, and push it:

```bash [Terminal]
git tag -a nuxt-ui-v1.0.1 origin/main -m "rollogi/nuxt-ui 1.0.1"
git push origin refs/tags/nuxt-ui-v1.0.1
```

The split workflow then publishes the version. Dating the changelog before the merge means a release needs only one merge to `main`.

## The split workflows

The three split workflows are the same apart from their names. Each runs on every push to `main` and on its own tag.

**On a push to `main`**, it copies the package's directory and its history into a branch of its own with `git subtree split --prefix=packages/<name>`, and pushes that to the package repository's `main`. That branch is installable as `1.x-dev`. The split is deterministic, so the same commits always produce the same history and every push is a fast-forward.

**On a `<name>-v<semver>` tag**, it first:

1. checks the tagged commit is on `main`;
2. checks the version is semver (`x.y.z`, or a prerelease such as `x.y.z-rc.1`);
3. runs the package on its own: `composer install`, `composer analyse` (Larastan) and `composer test` (Pest on Testbench) inside `packages/<name>`.

Only when those pass does it push the split history to the package repository and tag the same commit `v<semver>` there. So `core-v1.1.0` in the kit becomes `v1.1.0` in `Rollogi/core`. The push is never forced: a version that already exists in the package repository is refused, not moved.

Every job checks that it runs in the kit's own repository, so a project that receives these files through an upstream sync never runs or publishes anything.

### Tokens

Each workflow needs a fine-grained token owned by the Rollogi organisation with Contents read and write on its package repository. `ROLLOGI_CORE_TOKEN` also needs read on the kit's repository, because `release.yml` uses it for the fresh install. Before splitting, the workflow checks the token can reach the target with `git ls-remote` and fails with a message naming the permission if it cannot.

## Order of releases

Core comes first whenever something depends on a new version of it:

- **The kit** requires `rollogi/core` (`^1.1@dev` today). Its release workflow installs Core from `Rollogi/core`, so tag Core before releasing a kit that needs the new version.
- **Billing and nuxt-ui** require `rollogi/core` `^1.1`. A release that needs a new Core comes after that Core is tagged.
- The kit does not require billing or nuxt-ui, so a kit release never waits for either.

A new Core major means raising the kit's constraint, the path repository's `1.x-dev` version and the package's `branch-alias` together. `tests/Unit/Release/CoreDistributionTest.php` fails while they disagree, and also keeps the Core requirement of billing and nuxt-ui on Core's major.

## Preparing a release

`.github/workflows/prepare-package-release.yml` does the dating step for any of the three packages. Run it from **Actions > Prepare a package release**, or from the command line:

```bash [Terminal]
gh workflow run prepare-package-release.yml -f package=nuxt-ui -f version=1.0.1
```

| Input | Values |
| --- | --- |
| `package` | `core`, `billing` or `nuxt-ui` |
| `version` | `x.y.z`, or a prerelease such as `x.y.z-rc.1` |

Working from `develop`, the workflow:

1. refuses a version that is malformed, already tagged as `<package>-v<version>`, or already dated in `packages/<package>/CHANGELOG.md`;
2. moves whatever is waiting under **Unreleased** into a `## [x.y.z] - <today>` section, using `scripts/release/update-changelog.php` with no repository URL, so no compare links are added (the package's versions are tagged in its own repository);
3. checks the changelog is the only file that changed;
4. commits it as `github-actions[bot]` on a `release/<package>-<version>` branch, opens a pull request into `develop` titled `Date rollogi/<package> <version> in its changelog`, and squash-merges it, deleting the branch;
5. writes the new section and the exact tag commands for the next step into the run summary.

The workflow merges its own pull request because the repository's plan has no branch protection, so GitHub's auto-merge is unavailable. The check in step 3 is what makes that safe.

::warning
The workflow needs **Allow GitHub Actions to create and approve pull requests** under Settings > Actions > General > Workflow permissions. Without it, the job's token cannot open the pull request.
::

::note
Write the release's entries under Unreleased in the package's `CHANGELOG.md` before running it. The changelog script fails when there is nothing to record.
::
