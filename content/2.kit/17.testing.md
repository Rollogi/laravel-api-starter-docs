The suite is Pest, split into `tests/Unit` and `tests/Feature`, and runs on SQLite in memory by default (`phpunit.xml`). `composer check` runs it after Pint, Larastan and Rector, and CI runs the same on SQLite, MySQL and PostgreSQL.

```bash
composer test                                        # Pest only
vendor/bin/pest tests/Feature/Auth/LoginTest.php     # one file
vendor/bin/pest --filter='creates an invoice'        # by name
composer check                                       # lint, analyse, then test
```

Tests of rollogi/core alone live in the package and run on Testbench ([rollogi/core](/core)); tests that need the kit's modules, routes or whole-app wiring stay in the kit.

## Helpers

`tests/Pest.php` binds every test to `Tests\TestCase` and adds:

| Helper | What it does |
|---|---|
| `createUserInTenant(string $email = 'user@example.com', string $tenantName = 'Acme'): array` | Creates a tenant and a user (password `secret-password`, no role) attached to it, and returns `[$user, $tenant]` |
| `actingAsMember(User $user, Tenant $tenant): void` | Authenticates with `Passport::actingAs()` on the `api` guard and sets the `X-Tenant` header |
| `queriesDuring(Closure $callback, ?string $fromTable = null): array` | The SQL the callback ran, optionally only the statements reading from one table; useful for N+1 tests |

Tests build rows directly (`User::query()->create()`, `createUserInTenant()`); the kit has no factories. Seed roles with `$this->seed(RolesAndPermissionsSeeder::class)` and set the team before assigning one:

```php [tests/Feature/Billing/CreateInvoiceTest.php]
use Database\Seeders\RolesAndPermissionsSeeder;
use Illuminate\Foundation\Testing\RefreshDatabase;
use Spatie\Permission\PermissionRegistrar;

use function Pest\Laravel\postJson;

uses(RefreshDatabase::class);

beforeEach(function (): void {
    $this->seed(RolesAndPermissionsSeeder::class);
});

it('creates an invoice for an admin', function (): void {
    [$user, $tenant] = createUserInTenant('admin@example.com');
    app(PermissionRegistrar::class)->setPermissionsTeamId($tenant->getKey());
    $user->assignRole('admin');

    actingAsMember($user, $tenant);

    postJson('/api/billing/invoices', ['amount' => 100])->assertCreated();
});
```

### Real bearer tokens

`Passport::actingAs()` carries a transient token with no id. Anything that needs a real token (sessions, password change, two-factor, logging out one device) signs in through `POST /api/auth/login` and uses `withToken()`. That needs a personal access client, which a test creates with `app(ClientRepository::class)->createPersonalAccessGrantClient('Test Personal Access Client')`.

Passport's guard caches the user it resolved, and the test client reuses one guard across a test's requests, so `tests/TestCase.php` forgets the auth guards before any request that carries a bearer token. Without it, a second request with a different or revoked token would be answered as the first request's user. `TestCase` also creates Passport's signing keys when a fresh checkout has none.

## Faking the outside world

Third parties are never called:

| Dependency | How to fake it |
|---|---|
| Socialite | `Socialite::fake($provider, SocialiteUser::fake([...]))` ([Social sign-in](/kit/social-sign-in#testing)) |
| Firebase | A Mockery `Kreait\Firebase\Contract\Messaging` bound with `app()->instance()` ([Notifications](/kit/notifications#testing)) |
| Saloon | `MockClient`, and the connectors in `tests/Fixtures/Integrations/` |
| WebAuthn | `tests/Fixtures/Auth/SoftwareAuthenticator.php`, a P-256 authenticator in PHP |
| Queued actions and services | `Bus::fake()` with `SomeAction::assertDispatched()`, or `SomeAction::fake($result)` ([Actions](/core/actions)) |
| Metrics and search | `MetricsFake::bind()` and `SearchIndexerFake::bind()` |
| Mail and notifications | `Notification::fake()`, `Mail::fake()` as usual |

## Architecture tests

A few tests guard the shape of the code rather than its behaviour:

| Test | Guards |
|---|---|
| `tests/Feature/Core/Modules/ModuleLayeringTest.php` | Controllers delegate to services and never persist, services run actions, `authorizeService()` only through the contract, provider names match their directories; over app modules and installed package modules |
| `tests/Feature/Core/Octane/OctaneStateTest.php` | A reused Octane worker leaks no tenant, team id, feature memo or request id |
| `tests/Feature/Docs/ScrambleTest.php` | The OpenAPI document still generates |
| `tests/Feature/Core/Schedule/ScheduleTest.php` | The schedule's entries, which you update when you add one |
| `tests/Feature/Core/Analysis/ActionTypingTest.php` | Core's PHPStan extensions, against `tests/Fixtures/PhpStan/` |

The layering checks themselves are `Rollogi\Core\Support\Testing\Layering`, so a package can hold its own code to the same rules.

## MySQL and PostgreSQL

SQLite cannot catch everything: a nullable column inside a primary key, a transaction left aborted after a caught constraint violation, a case-insensitive collation. `compose.yaml` provides throwaway databases on non-default ports with their data in tmpfs:

```bash
composer db:up          # MySQL 8.4 on 33306 and PostgreSQL 17 on 54329 (Docker)
composer test:mysql     # the whole suite against MySQL
composer test:pgsql     # the whole suite against PostgreSQL
composer test:all       # SQLite, then MySQL, then PostgreSQL
composer db:down
```

The scripts pass the connection through the environment, which wins over `phpunit.xml`, so another database is a matter of exporting `DB_CONNECTION`, `DB_HOST`, `DB_PORT`, `DB_DATABASE`, `DB_USERNAME` and `DB_PASSWORD` before `vendor/bin/pest`.

| Env | Default | Used by |
|---|---|---|
| `DB_TEST_DATABASE` | `api_starter_test` | compose file, Composer scripts, CI |
| `DB_TEST_USERNAME` | `api` | compose file, Composer scripts, CI |
| `DB_TEST_PASSWORD` | `secret` | compose file, Composer scripts, CI |
| `DB_TEST_MYSQL_PORT` | `33306` | compose file, Composer scripts |
| `DB_TEST_PGSQL_PORT` | `54329` | compose file, Composer scripts |

If a port clashes with a local server, exporting one variable changes every side at once. One test skips on MySQL by design (its default collation already treats case-variant emails as equal), and one runs only on PostgreSQL (the permission pivot key conversion).

### Two portability rules

- **No nullable column in a primary key.** SQLite tolerates it, MySQL refuses the table, PostgreSQL refuses the insert. Use a surrogate `id` plus a unique index, as the Spatie pivot tables do.
- **Catch a unique violation inside `DB::transaction()`.** PostgreSQL aborts the whole transaction after any failed statement; a nested `DB::transaction()` becomes a savepoint, so the outer transaction survives. `CreateUserAction` and `RecordWebhookEventAction` do this.

A migration that has shipped is never edited in place, because the edit would not reach existing installs; add a guarded follow-up migration instead. Run `composer db:up && composer test:all` before opening a pull request that touches migrations or raw SQL.
