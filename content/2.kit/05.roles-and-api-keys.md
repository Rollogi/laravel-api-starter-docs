The rest of the Tenants module: roles a tenant defines for itself, API keys for its integrations, and the activity stream an administrator reads. All three sit under `/api/tenants/current` behind `api.tenant`. For how roles relate to tenants in general, see [Multi-tenancy](/kit/multi-tenancy#roles-are-per-tenant).

## Roles and permissions API

All routes require `api.tenant` and `feature:tenants.roles`. Listing needs `roles.view`, which both seeded roles hold; defining roles needs `roles.manage`, which only `admin` holds.

| Method | Path | Permission | Effect |
|---|---|---|---|
| `GET` | `/api/tenants/current/roles` | `roles.view` | The roles a member can hold here: the global ones plus this tenant's, each `{ id, name, scope, permissions }` with a `scope` of `global` or `tenant` |
| `GET` | `/api/tenants/current/permissions` | `roles.view` | Every permission name, for building a role editor |
| `POST` | `/api/tenants/current/roles` | `roles.manage` | `{ "name": "editor", "permissions": ["members.view", "tenant.update"] }`; `201` with the role |
| `PATCH` | `/api/tenants/current/roles/{role}` | `roles.manage` | Rename and/or replace the permission list; an omitted field is left alone |
| `DELETE` | `/api/tenants/current/roles/{role}` | `roles.manage` | Removes a tenant role nobody holds; `204` |

A tenant role is an ordinary Spatie role row whose `tenant_id` is the tenant, so everything that takes a role name accepts it inside that tenant: changing a member's role, invitations, `tenant:add-member`, API keys. `EnsureRoleIsAssignableAction` resolves a name the way Spatie's `findByName()` does (global, or defined by the active tenant), so another tenant's role is a `422` rather than an error inside `assignRole()`. Outside HTTP, set the permission team id before calling it.

Rules worth knowing:

- **Built-in roles are read-only.** `PATCH` or `DELETE` on a global role is a `422` on `role`. The seeder owns them, and the last-admin guard relies on `admin` keeping its meaning.
- **Names are unique per tenant, ignoring case.** A tenant role may not reuse a global name or another of the tenant's names. Two tenants may each have an `editor`.
- **Permissions must exist.** An unknown name is a `422` on `permissions` that names the offenders. The set of permissions comes from the seeder and the code that checks them, not from the API.
- **A held role cannot be deleted.** `DELETE` is a `422` on `role` while any member holds it.
- **Other tenants' roles are invisible**: absent from the list, and `404` on `PATCH` or `DELETE`.

To add a permission of your own, create it in `RolesAndPermissionsSeeder` (or in a migration, as rollogi/billing does) and check it from a policy or `Gate::authorize()`. The seeder gives `admin` every permission on the `api` guard.

## API keys

A tenant gives an integration credentials of its own with an API key. A key is two things:

- a **machine member** of the tenant: a `User` of kind `machine` (`UserKind`, the `users.kind` column) that nobody can sign in as, holding one of the tenant's roles;
- a Passport **personal access token** whose scopes are the subset of that role's permissions the key may use.

All routes require `api.tenant`, `feature:tenants.api_keys` and the `api-keys.manage` permission.

| Method | Path | Body | Effect |
|---|---|---|---|
| `GET` | `/api/tenants/current/api-keys` | | The tenant's live keys: `{ id, name, actorId, role, scopes, expiresAt, createdAt }` |
| `POST` | `/api/tenants/current/api-keys` | `name`, `role`, `scopes[]`, `expiresAt?` | Creates the machine member and the token; `201` with `{ key, token }`, the only time the plaintext is shown |
| `DELETE` | `/api/tenants/current/api-keys/{id}` | | Revokes the token and, when it was the machine's last, removes the machine from the tenant and deletes it; `204` |

Creating a key is a `422` for an unknown role, an empty `scopes`, a scope the role does not grant, or an expiry in the past. Without `expiresAt` the key lives `api-keys.lifetime_days` (`API_KEY_LIFETIME_DAYS`, default 365). Another tenant's key is a `404`.

```bash
curl https://api.example.com/api/tenants/current/members \
  -H "Authorization: Bearer <token>"
```

### How a key is authorised

Calls made with the key authenticate as the machine member, so everything built on `User` applies unchanged:

- The machine belongs to exactly one tenant, so `ResolveTenant` activates it without an `X-Tenant` header.
- Its role decides what it may do, and the scopes narrow it: `User::hasPermissionTo()` grants a machine user checked through a token only the permissions its token's scopes name. A key with the `admin` role and `scopes: ["members.view"]` can read members but not change them.
- Off the request (an action the call queued) there is no token, so the role applies in full.
- `service_audits` and the activity stream name the machine as the actor, and the member list shows it with `kind: "machine"`.
- A machine is never counted as the tenant's last administrator, and a tenant that requires two-factor does not turn its keys away.

A key acts on its tenant only. The account-level surface (passkeys, two-factor enrolment, password and sessions, linked social accounts, `/api/account`, notification devices, preferences and inbox, creating a tenant) carries the `person` middleware and answers a key with `403 machine-forbidden`. Logout stays open, so a key can revoke its own token.

Removing a machine from the member list, revoking its key or deleting the tenant deletes the machine user, which ends every token it holds.

### Explicit scope checks

The `scopes` and `scope` route middleware aliases (Passport's `CheckToken` and `CheckTokenForAnyScope`) are registered for routes meant for keys that want a scope check on top of the permission one:

```php
Route::get('/exports', ListExportsController::class)->middleware('scopes:members.view,members.update'); // every scope
Route::get('/reports', ListReportsController::class)->middleware('scope:members.view,tenant.view');      // any one
```

A person's login token carries no scopes, so apply these only to routes meant for keys.

### Configuration

| Key | Env | Default | Meaning |
|---|---|---|---|
| `api-keys.lifetime_days` | `API_KEY_LIFETIME_DAYS` | `365` | Lifetime of a key created without `expiresAt` |
| `api-keys.email_domain` | `API_KEY_EMAIL_DOMAIN` | `machine.invalid` | Domain of the address a machine user is created with. Nothing is sent to it; the local part is a UUID |

## Activity

`GET /api/tenants/current/activity` requires `api.tenant`, `feature:tenants.activity` and `activity.view` (seeded on `admin` only, because the rows say who did what and carry the attribute values that changed). It is one cursor-paginated stream over both audit tables, newest first:

| `kind` | Source | Fields |
|---|---|---|
| `service` | `service_audits`, one row per service call in this tenant | `service`, `status` (`ok` or `failed`), `durationMs` |
| `change` | `audits`, one row per attribute change on an auditable model in this tenant | `event`, `subjectType`, `subjectId`, `oldValues`, `newValues` |

Every entry carries `id`, `kind`, `occurredAt`, `actor` (`{ id, name, email }`, or `null` for an unauthenticated call or a deleted user) and `requestId`, so a model change can be tied to the service call and log lines of the same request. `?kind=service` or `?kind=change` narrows the stream; `per_page` and `cursor` page it. Rows with no tenant (account-level calls, registration) and other tenants' rows never appear.

Both tables issue UUIDv7 ids, so ordering the merged stream by `id` is chronological and the cursor is stable. How rows get their `tenant_id` and `request_id` is covered in [Auditing](/kit/auditing).
