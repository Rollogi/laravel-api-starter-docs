The Auth module signs people in with Google, GitHub, Microsoft and Apple through `laravel/socialite` plus the `socialiteproviders/microsoft` and `socialiteproviders/apple` providers. Everything sits behind `feature:auth.social_login`. `App\Modules\Auth\Social\SocialiteGateway` is the only class that touches Socialite.

## Enabling providers

`SOCIAL_PROVIDERS` (`config/social.php`) lists the providers that accept sign-ins, comma-separated; by default all four. The `{provider}` route parameter is constrained to the enabled ones, so a provider left out is a `404` on every social route before any controller runs. Credentials live in `config/services.php` under the provider's name:

| Provider | Env |
|---|---|
| Google | `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `GOOGLE_REDIRECT_URI` |
| GitHub | `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET`, `GITHUB_REDIRECT_URI` |
| Microsoft | `MICROSOFT_CLIENT_ID`, `MICROSOFT_CLIENT_SECRET`, `MICROSOFT_TENANT` (default `common`), `MICROSOFT_REDIRECT_URI` |
| Apple | `APPLE_CLIENT_ID`, `APPLE_CLIENT_SECRET`, `APPLE_TEAM_ID`, `APPLE_KEY_ID`, `APPLE_PRIVATE_KEY`, `APPLE_REDIRECT_URI` |

Each redirect URI defaults to `FRONTEND_URL/auth/callback/<provider>`. Register exactly that URI with the provider. Apple's client secret is derived from `APPLE_PRIVATE_KEY` when it is set.

## The flow

There is no session, so the API issues the OAuth `state` itself and every driver runs stateless. The frontend owns the browser redirect.

1. `GET /api/auth/social/{provider}/redirect` returns `{ url, state, expiresIn }`. The state is single-use, bound to the provider, lives `SOCIAL_STATE_TTL` seconds (default 600) in the cache (`SocialStateStore`), and for Apple carries the `nonce` the `id_token` must echo.
2. The frontend sends the browser to `url`. The provider redirects back to the frontend's callback URI with `code` and `state`.
3. The frontend posts `{ code, state, tenantName?, deviceName? }` to `POST /api/auth/social/{provider}/callback` and receives `AuthSessionData`, or a `202` two-factor challenge ([Two-factor and passkeys](/kit/two-factor-and-passkeys)).

Both calls are public and on `throttle:auth`.

::note
Apple uses `response_mode=form_post`, so a plain SPA cannot receive its redirect. Use Apple's JS SDK in popup mode to obtain the code, or end the redirect on a server page that forwards `code` and `state` to the callback.
::

The validated code is handed to the provider on a request of its own, never read off the global request, so the social services run from a job or command as well as from HTTP.

## Identity resolution

`SocialCallbackService` decides whose session to issue:

| Situation | Result |
|---|---|
| `(provider, provider_id)` already in `social_accounts` | Signs that user in, whatever email the provider now reports |
| First-seen identity, provider email **verified**, a user with that email exists | Links the identity to that user and signs them in |
| First-seen identity, provider email **verified**, no such user | Creates the user (random password, email marked verified) and a tenant named `tenantName` or `<name>'s workspace` with them as `admin`, links, signs in |
| First-seen identity, email missing or **not verified** | `422` on `code`: sign in with the password and link from inside the account |

"Verified" is decided per provider by `SocialProvider::emailIsVerified()`: Google and Apple must report `email_verified`, GitHub returns only the primary verified email, Microsoft addresses are directory-managed. Linking on an unverified email would let anyone who registers that address at the provider take over the matching account.

`EnsureSocialIdentityLinkableAction` guards both unique indexes on `social_accounts` before any link. Every social sign-in is recorded in `login_attempts` as `social:<provider>`.

## Managing linked accounts

These run on `auth:api` and `person`:

| Route | Body | Effect |
|---|---|---|
| `GET /api/auth/social` | | `data: [{ provider, email, name, linkedAt }]` |
| `POST /api/auth/social/{provider}/link` | `code`, `state` | Links the identity to the **bearer token's** user, never to a user carried in the state. `422` when the identity belongs to another user, or this user already holds a different identity from that provider |
| `DELETE /api/auth/social/{provider}` | `password` | Unlinks. Requiring the password guarantees the person keeps a way in; a social-only account sets one through password reset first |

Provider tokens are not stored: the kit only authenticates. `social_accounts.user_id` cascades when the user is deleted.

## Testing

Use `Socialite::fake()` with a fake user:

```php
use Laravel\Socialite\Facades\Socialite;
use Laravel\Socialite\Two\User as SocialiteUser;

Socialite::fake('github', SocialiteUser::fake([
    'id' => '987654321',
    'name' => 'Grace Hopper',
    'email' => 'grace@example.com',
]));
```

`SocialiteGateway` configures the real provider underneath, so the stateless path is still exercised.
