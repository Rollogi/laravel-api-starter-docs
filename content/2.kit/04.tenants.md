The `Tenants` module is one module for a tenant and the people in it: the tenant's lifecycle and settings, its members and invitations, and (on [Roles and API keys](/kit/roles-and-api-keys)) its roles, API keys and activity stream. There is no separate "team": Spatie's team is the tenant.

Routes live under `/api/tenants`. Listing and creating tenants is account-level (`auth:api`), because a caller may belong to several tenants or to none. Everything under `/api/tenants/current` acts on the active tenant resolved by `api.tenant` ([Multi-tenancy](/kit/multi-tenancy)). Accepting an invitation is `POST /api/invitations/{token}/accept`, account-level because the invitee is not a member yet.

## Tenant lifecycle

| Method | Path | Middleware | Permission | Feature key |
|---|---|---|---|---|
| `GET` | `/api/tenants` | `auth:api` | none (the caller's own memberships) | `tenants.list` |
| `POST` | `/api/tenants` | `auth:api`, `person` | none; the caller becomes its first `admin` | `tenants.create` |
| `GET` | `/api/tenants/current` | `api.tenant` | `tenant.view` | `tenants.manage` |
| `PATCH` | `/api/tenants/current` | `api.tenant` | `tenant.update` | `tenants.manage` |
| `DELETE` | `/api/tenants/current` | `api.tenant` | `tenant.delete`, plus the caller's `password` | `tenants.manage` |
| `GET` | `/api/tenants/current/settings` | `api.tenant` | `tenant.view` | `tenants.settings` |
| `PATCH` | `/api/tenants/current/settings` | `api.tenant` | `tenant.update` | `tenants.settings` |

`POST` and `PATCH` take `{ "name": "..." }`. A tenant is returned as `{ id, name, suspendedAt, createdAt }`. The permission checks live on the Data objects through `TenantPolicy`, so they hold wherever the services are called from.

Deleting a tenant removes its memberships, pending invitations, feature overrides, settings and every role or permission grant scoped to it. Users are global and survive; audit rows keep the tenant id as history.

## Settings

Per-tenant settings are the data twin of [feature toggles](/kit/feature-toggles). Every key is registered in Core's `tenant-settings.php` config with a default, a label and the validation rules applied on write. The shipped keys:

| Key | Default | Rules |
|---|---|---|
| `locale` | `en` | `string`, `min:2`, `max:10` |
| `timezone` | `UTC` | `string`, `timezone:all` |

Add your own by publishing the config (`php artisan vendor:publish --tag=rollogi-core-config`) and adding entries under `settings`:

```php [config/tenant-settings.php]
'settings' => [
    'locale' => ['default' => 'en', 'label' => 'Default locale for members and notifications', 'rules' => ['string', 'min:2', 'max:10']],
    'invoice_prefix' => ['default' => 'INV', 'label' => 'Prefix for invoice numbers', 'rules' => ['string', 'max:8']],
],
```

`GET /api/tenants/current/settings` returns every registered key as `{ key, value, default, label }`. `PATCH` takes `{ "settings": { "locale": "fr" } }` and rejects an unregistered key or an invalid value with `422`. In code, read through the request-scoped `Rollogi\Core\Tenancy\TenantSettings`:

```php
app(TenantSettings::class)->get('locale', tenancy()->current());
```

It memoises each tenant's rows for the request and throws `UnknownTenantSettingException` for a key that is not registered.

## Members

All member routes require `api.tenant` and `feature:tenants.members`.

| Method | Path | Permission | Effect |
|---|---|---|---|
| `GET` | `/api/tenants/current/members` | `members.view` | Cursor-paginated list: `{ id, name, email, kind, roles, joinedAt }`, roles within this tenant only. Sortable by `name` and `email`, filterable by `role` and `kind` |
| `PATCH` | `/api/tenants/current/members/{user}` | `members.update` | `{ "role": "admin" }` replaces the member's role in this tenant and returns the member |
| `DELETE` | `/api/tenants/current/members/{user}` | `members.remove` | Removes the member from this tenant; `204` |
| `DELETE` | `/api/tenants/current/membership` | none | The caller leaves the tenant; `204` |

```http
GET /api/tenants/current/members?per_page=25&sort=-name&filter[role]=admin,user
```

The query string conventions are described in [HTTP conventions](/kit/http).

Rules worth knowing:

- **The last admin is protected.** Removing, demoting or letting leave the final holder of the admin role (`tenants.admin_role`, `TENANT_ADMIN_ROLE`, default `admin`) is a `422`. A tenant without an administrator could never be administered again. Machine users never count as that administrator.
- **Self-removal goes through `leave`.** `DELETE /members/{me}` is a `422` that points at the leave endpoint: removing others needs `members.remove`, leaving needs nothing.
- **Roles are cleared before the pivot is detached**, so a person who is invited back does not silently get their old role again.
- **Tokens are not revoked.** Tokens are global, so revoking would sign the person out of their other tenants; `ResolveTenant` re-checks membership on every request anyway.
- **Other tenants are invisible.** A member of another tenant is a `404`, the same as a user that does not exist.

## Invitations

| Method | Path | Requires | Effect |
|---|---|---|---|
| `POST` | `/api/tenants/current/invitations` | `api.tenant`, `members.invite` | `{ email, role }`; `201` with `{ invitation, token, acceptUrl }` |
| `GET` | `/api/tenants/current/invitations` | `api.tenant`, `members.invite` | Pending invitations (not accepted, not expired) |
| `DELETE` | `/api/tenants/current/invitations/{id}` | `api.tenant`, `members.invite` | Deletes the invitation |
| `POST` | `/api/invitations/{token}/accept` | public, `throttle:auth` | `{ name?, password? }`; `201` with the session |

All four sit behind `feature:tenants.invitations`; the permission is checked by `InvitationPolicy`.

```json
{
  "invitation": { "id": "...", "email": "bob@example.com", "role": "user", "expiresAt": "...", "acceptedAt": null },
  "token": "<40-character random string>",
  "acceptUrl": "https://api.example.com/api/invitations/<token>/accept"
}
```

Only the SHA-256 hash of the token is stored; the plaintext appears in this response and in the email, nowhere else. Creating an invitation fires `InvitationCreated`, and the module's `SendInvitationEmail` listener emails the invitee a link to `FRONTEND_URL/accept-invitation?token=<token>`. Your frontend collects a name and password for a new account and posts them to the accept endpoint.

::note
`acceptUrl` points at the API's own accept endpoint, which takes a `POST`; it is not a link a browser can follow. Use your frontend URL when you email invitations yourself.
::

Accepting with a **new** email creates the account from `name` and `password` (the [password policy](/kit/authentication#password-policy) applies). With an **existing** email, `name` and `password` are ignored and the user is attached to the tenant. Either way the response is the same `AuthSessionData` as login, so the caller is signed in. Tokens are single-use (`accepted_at` is set), expire after `tenants.invitation_ttl_days` (7), and the accept endpoint locks the invitation row before checking it, so two concurrent accepts cannot both succeed.

## Suspension

Suspension is an operator action, not an endpoint, so a tenant administrator cannot lock their own members out:

```bash
php artisan tenant:suspend <tenant-id>          # every tenant-scoped request answers 403 tenant-suspended
php artisan tenant:suspend <tenant-id> --lift   # back to normal
```

Account-level routes keep working, and the suspended tenant still appears in `GET /api/tenants` with its `suspendedAt`.

## Operator commands

```bash
php artisan tenant:create "Globex" --owner=owner@example.com   # optional existing user becomes admin
php artisan tenant:list                                        # id, name, member count, suspension
php artisan tenant:add-member <tenant-id> user@example.com --role=admin   # --role defaults to user
php artisan tenant:suspend <tenant-id> [--lift]
php artisan permission:list [--tenant=<tenant-id>]            # every permission and the roles that grant it
```

## Domain events

The module raises events from `App\Modules\Tenants\Events` that your own modules can listen to: `InvitationCreated`, `MemberJoined`, `MemberRoleChanged`, `MemberRemoved` and `TenantUpdated`. The Webhooks module turns each one into an outbound webhook ([Webhooks](/kit/webhooks)).

## Configuration

| Key | Env | Default | Meaning |
|---|---|---|---|
| `tenants.invitation_ttl_days` | | `7` | Days an invitation stays acceptable |
| `tenants.admin_role` | `TENANT_ADMIN_ROLE` | `admin` | The role a tenant may never run out of |
| `tenant-settings.settings` | | `locale`, `timezone` | The per-tenant settings registry (Core config) |
