The kit keeps two independent audit trails, and both record the tenant and the request id, so a tenant administrator can read them as one stream ([Activity](/kit/roles-and-api-keys#activity)) and any row can be tied to the log lines of its request.

| Trail | Table | Written by | One row per |
|---|---|---|---|
| Service calls | `service_audits` | the `AuditServiceCall` pipeline stage | write service call |
| Model changes | `audits` | owen-it/laravel-auditing on `Auditable` models | attribute change |

## Service-call audit

Every service on the write preset runs the `AuditServiceCall` stage, so every write use-case is audited without asking for it. Reads (`ReadService`) are not. A row holds:

| Column | Value |
|---|---|
| `service` | The service class |
| `actor_id` | The acting user, or `null` for an unauthenticated call |
| `tenant_id` | The active tenant, or `null` for an account-level call |
| `status` | `ok` or `failed` |
| `duration_ms` | How long the call took |
| `request_id` | The request's `X-Request-Id` |
| `subject_type`, `subject_id` | An optional morph to the record the call was about |
| `meta` | Optional JSON |

The stage takes the actor, tenant, request id and timing from the `ServiceInvocation` the pipeline shares between stages; see [Service pipeline](/core/service-pipeline). A service that replays an [idempotent](/kit/http#idempotency-keys) result writes no second row. A queued service writes the same row it would have inline, because the execution context is restored on the worker.

## Model audit

A model that implements owen-it's `Auditable` gets a row in `audits` for every change. Use Core's `AuditsWithRequestContext` trait alongside it so the row carries `tenant_id` and `request_id`. Both traits declare `transformAudit()`, so name the winner:

```php [app/Modules/Billing/Models/Invoice.php]
use OwenIt\Auditing\Auditable as AuditableTrait;
use OwenIt\Auditing\Contracts\Auditable;
use Rollogi\Core\Auditing\Concerns\AuditsWithRequestContext;
use Rollogi\Core\Models\Concerns\BelongsToTenant;
use Rollogi\Core\Models\Model;

class Invoice extends Model implements Auditable
{
    use AuditableTrait, AuditsWithRequestContext {
        AuditsWithRequestContext::transformAudit insteadof AuditableTrait;
    }
    use BelongsToTenant;

    /** @var list<string> */
    protected array $auditExclude = ['internal_note'];
}
```

`User` is the reference: it excludes `password`, `remember_token` and the two-factor secret and recovery codes. Exclude anything secret from your own models the same way.

The `audits` table uses UUID keys and is created by Core's `Auditing` concern, reading its name and columns from `config/audit.php`. Rows are stored as `Rollogi\Core\Auditing\Models\Audit`.

## Retention

Every audit and log table is pruned daily by `model:prune`, scheduled by the module or concern that owns it, after a window set in its own config:

| Table | Model | Env | Default (days) |
|---|---|---|---|
| `service_audits` | `Rollogi\Core\Services\Models\ServiceAudit` | `SERVICE_AUDIT_RETENTION_DAYS` | 365 |
| `audits` | `Rollogi\Core\Auditing\Models\Audit` | `AUDIT_RETENTION_DAYS` | 365 |
| `integration_audits` | `Rollogi\Core\Integrations\Models\IntegrationAudit` | `INTEGRATION_AUDIT_RETENTION_DAYS` | 90 |
| `webhook_events` | `Rollogi\Core\Integrations\Models\WebhookEvent` | `WEBHOOK_EVENT_RETENTION_DAYS` | 90 |
| `webhook_deliveries` | `App\Modules\Webhooks\Models\WebhookDelivery` | `WEBHOOK_DELIVERY_RETENTION_DAYS` | 30 |
| `login_attempts` | `App\Modules\Auth\Models\LoginAttempt` | `LOGIN_ATTEMPT_RETENTION_DAYS` | 90 |
| `push_devices` | `App\Modules\Notifications\Models\PushDevice` | `PUSH_DEVICE_RETENTION_DAYS` | 90 |
| `notifications` (read entries) | `App\Modules\Notifications\Models\InboxNotification` | `INBOX_NOTIFICATION_RETENTION_DAYS` | 90 |

The audit models use `MassPrunable` (one `DELETE`, no model events), because nothing hangs off a row. Keep `webhook_events` at least as long as any provider's redelivery window: the unique index on `(integration, event_id)` only recognises a duplicate while the original row exists.

Deleting a user leaves their audit rows and login attempts in place as history until retention removes them ([Account](/kit/account#deleting-the-account)).

## Scheduling a prune of your own

A module that owns a `Prunable` or `MassPrunable` model schedules its own prune in its provider, never in `bootstrap/app.php`:

```php [app/Modules/Billing/BillingServiceProvider.php]
$this->callAfterResolving(Schedule::class, function (Schedule $schedule): void {
    $schedule->command('model:prune', ['--model' => [InvoiceDraft::class]])->daily();
});
```

`tests/Feature/Core/Schedule/ScheduleTest.php` counts the schedule's entries, so add yours there. The only entry in `bootstrap/app.php` is the framework's own `passport:purge`. Run the scheduler in production (`php artisan schedule:run` every minute, see [Deployment](/kit/deployment)).
