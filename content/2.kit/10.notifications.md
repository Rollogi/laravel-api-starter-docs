The `Notifications` module sends Firebase Cloud Messaging pushes through `laravel-notification-channels/fcm`, which authenticates with `kreait/laravel-firebase`, lets each user switch channels off per category, and keeps an in-app inbox on the `database` channel. Every route runs on `auth:api` and `person`: devices, preferences and the inbox belong to the account, not to a tenant, so their `service_audits` rows carry no `tenant_id`.

Set `FIREBASE_CREDENTIALS` to the service-account JSON (a path relative to the project root, an absolute path, or the JSON itself). `config/firebase.php` is kreait's published config. A user with no registered devices never reaches the FCM channel, so credentials are only needed once a device exists.

## Endpoints

| Method | Path | Body | Effect | Feature key |
|---|---|---|---|---|
| `PUT` | `/api/notifications/devices` | `token`, `platform`, `name?` | Registers or updates a device; returns `{ id, platform, name, lastSeenAt }` | `notifications.devices` |
| `GET` | `/api/notifications/devices` | | The caller's devices, newest first; tokens are never returned | `notifications.devices` |
| `DELETE` | `/api/notifications/devices/{id}` | | Removes one of the caller's devices (call it on sign-out) | `notifications.devices` |
| `GET` | `/api/notifications/preferences` | | `data: [{ category, label, channels: { push: true, mail: false, database: true } }]` | `notifications.preferences` |
| `PUT` | `/api/notifications/preferences` | `category`, `channel`, `enabled` | Stores one choice and returns the full list | `notifications.preferences` |
| `GET` | `/api/notifications` | | The inbox, newest first, cursor-paginated; `?unread=1` for unread only | `notifications.inbox` |
| `GET` | `/api/notifications/unread-count` | | `{ unread }` | `notifications.inbox` |
| `PATCH` | `/api/notifications/{id}/read` | | Marks one entry read and returns it | `notifications.inbox` |
| `PATCH` | `/api/notifications/read` | | Marks every unread entry read; `{ marked }` | `notifications.inbox` |

## Devices

A client registers its FCM token on every launch. `platform` is one of `ios`, `android` or `web` (`DevicePlatform`). The device is upserted by token in one statement, and omitting `name` keeps the stored one.

A token identifies the app install, so it moves to whoever signs in on that device. When that happens the previous owner is emailed (`PushDeviceReassignedNotification`, category `security`) and a warning is logged, because anyone who learns a token could claim it the same way.

When Firebase reports a token it no longer knows (an uninstalled app, a rotated token), `FcmChannel` dispatches `NotificationFailed` and the `RemoveUnregisteredDevice` listener deletes the device. Any other failure (quota, outage) keeps it for the next send. `PushDevice` is prunable: a device not re-registered within `PUSH_DEVICE_RETENTION_DAYS` is removed by the daily `model:prune` that `NotificationsServiceProvider` schedules.

## Sending a notification

`User` uses the `ReceivesNotifications` trait, so `routeNotificationForFcm()` returns every registered token and the channel multicasts to them in one call. Extend `PushNotification` for a push:

```php [app/Modules/Billing/Notifications/InvoicePaid.php]
use App\Modules\Notifications\Notifications\PushNotification;

class InvoicePaid extends PushNotification
{
    public function __construct(private readonly string $invoiceNumber) {}

    public function category(): string
    {
        return 'tenant.membership';
    }

    public function title(mixed $notifiable): string
    {
        return 'Invoice paid';
    }

    public function body(mixed $notifiable): string
    {
        return sprintf('Invoice %s has been paid.', $this->invoiceNumber);
    }

    /**
     * @return array<string, string>
     */
    public function data(mixed $notifiable): array
    {
        return ['tenant_id' => (string) tenancy()->id()];
    }
}

$user->notify(new InvoicePaid('INV-42'));
```

The message carries `category` in its data payload so the client can route it. `PushNotification::channels()` returns `[NotificationChannel::Push]`; override it to add `NotificationChannel::Mail` (and implement `toMail()`) or `NotificationChannel::Database`, or override `toFcm()` for platform options such as sound or badge.

For a notification that is not a push, extend `PreferenceAwareNotification` directly and implement `category()` and `channels()`. Transactional mail with no opt-out (password reset, invitations) stays a plain Laravel notification.

## Preferences

`config/notifications.php` registers the categories a user can be notified about and the channels each may use:

```php [config/notifications.php]
'categories' => [
    'tenant.membership' => ['label' => 'Membership changes', 'channels' => ['push', 'mail', 'database']],
    'security' => ['label' => 'Security alerts', 'channels' => ['push', 'mail', 'database']],
],
```

Everything not stored is on. A preference-aware notification is filtered twice:

- `via()` runs when the notification is dispatched and trims what can be decided up front: channels the category does not offer, channels the user has switched off, and push when there is no device.
- `shouldSend()` runs again on the worker for each channel, because Laravel fixes the channel list when it queues. A preference changed, or a device removed, while the job waited is still honoured.

A user's stored choices are loaded once per request or job (`NotificationPreferences` is request-scoped) and writes go through `UpdateNotificationPreferenceAction`, which drops the memo. Non-user notifiables (an invitee's email address) are not filtered. An unregistered category throws `UnknownNotificationCategoryException`; `PUT /preferences` answers `422` for an unknown category or a channel the category does not offer.

## Inbox

A notification that lists `NotificationChannel::Database` is stored in the `notifications` table and read back through the inbox routes. Each entry is `{ id, type, category, data, readAt, createdAt }`, where `data` is whatever `toDatabase()` returned:

- `PreferenceAwareNotification` stores `{ category }`;
- `PushNotification` stores `{ category, title, body, data }`, so a client can render an entry without knowing the class behind it.

Override `toDatabase()` for anything else. `InboxDatabaseChannel` replaces the framework's `database` channel only to key each row with a UUIDv7, so the inbox orders and paginates by id like every other table. Marking an entry read twice keeps the first `readAt`, and another user's entry is a `404`. A read entry is pruned after `INBOX_NOTIFICATION_RETENTION_DAYS`; an unread one stays until it is read.

## Configuration

| Env | Config key | Default | Meaning |
|---|---|---|---|
| `FIREBASE_CREDENTIALS` | `firebase.projects.app.credentials` | | Service-account JSON for FCM |
| `FIREBASE_PROJECT` | `firebase.default` | `app` | The kreait project to use |
| `PUSH_DEVICE_RETENTION_DAYS` | `notifications.device_retention_days` | `90` | Days a device may go without re-registering |
| `INBOX_NOTIFICATION_RETENTION_DAYS` | `notifications.inbox_retention_days` | `90` | Days a read inbox entry is kept |
| | `notifications.categories` | `tenant.membership`, `security` | Categories, labels and allowed channels |

## Testing

Bind a Mockery mock of `Kreait\Firebase\Contract\Messaging` with `app()->instance()` and have it return a `MulticastSendReport`; `tests/Feature/Notifications/PushSendingTest.php` shows success, preference filtering and dead-token clean-up. `Notification::fake()` works as usual when the send itself is not under test.
