Both live in the Auth module. A person can enrol an authenticator app, register passkeys, or both; `User::hasTwoFactorEnabled()` is true with either, and `hasTotpEnabled()` with the app alone.

## Two-factor (TOTP)

Authenticator-app codes with single-use recovery codes, via `pragmarx/google2fa`. The secret is stored with the `encrypted` cast and recovery codes as SHA-256 hashes inside an `encrypted:array`; both are hidden from serialisation and excluded from model audits.

### Enrolment

These routes run on `auth:api` plus `person` and `feature:auth.two_factor`, without a tenant on purpose: enrolment belongs to the account, and a tenant that requires two-factor has to leave the way to comply open.

| Route | Body | Effect |
|---|---|---|
| `GET /api/auth/two-factor` | | `{ enabled, totp, passkeys, pendingConfirmation, confirmedAt, recoveryCodesRemaining }`; `passkeys` is a count |
| `POST /api/auth/two-factor` | `password` | Starts enrolment and returns `{ secret, otpauthUrl }`. The client renders the `otpauth://` URI as a QR code. The secret protects nothing until confirmed |
| `POST /api/auth/two-factor/confirm` | `code` | Verifies a code, turns two-factor on and returns `{ recoveryCodes }` (eight of them) exactly once |
| `POST /api/auth/two-factor/recovery-codes` | `password` | Replaces the recovery codes; the old ones stop working |
| `DELETE /api/auth/two-factor` | `password` | Turns two-factor off |

Enabling, disabling and re-issuing codes all re-prove the password, so a stolen bearer token alone cannot change the second factor. `UserData` (login, register, `/me`) carries `twoFactorEnabled`.

### Signing in

When the password is right and two-factor is on, `POST /api/auth/login` answers `202 Accepted` with no session:

```json
{ "challengeToken": "...", "expiresIn": 300, "twoFactorRequired": true }
```

The client then calls `POST /api/auth/two-factor/challenge` (public, `throttle:auth`) with `challengeToken` and one of `code` (six digits), `recoveryCode` or `passkey`, and receives the usual `AuthSessionData`.

- The challenge lives in the cache (`TwoFactorChallengeStore`) for `TWO_FACTOR_CHALLENGE_TTL` seconds from when it was issued; a wrong code does not extend it.
- It is single-use and destroyed after `TWO_FACTOR_CHALLENGE_MAX_ATTEMPTS` wrong codes.
- Codes are accepted within `TWO_FACTOR_WINDOW` 30-second steps either side of now, and a code from a time step at or before the last accepted one is refused, so an observed code cannot be replayed.
- Each recovery code works once.

Magic links and social sign-in honour two-factor the same way.

### Requiring it per tenant

`auth.two_factor.required` is an ordinary [feature toggle](/kit/feature-toggles), off by default, meant to be set per tenant:

```bash
php artisan feature:set auth.two_factor.required --tenant=<uuid> --on
```

`EnsureTwoFactorSatisfied` runs inside `api.tenant` after `ResolveTenant`. A member of that tenant with no second factor gets `403 two-factor-required` on every tenant-scoped route. The enrolment routes, logout, password change, sessions and the member's other tenants keep working. Machine users (tenant API keys) are exempt, since they have no second factor to enrol.

## Passkeys (WebAuthn)

Passkeys are both a sign-in of their own and a second factor, built on `web-auth/webauthn-lib` behind `feature:auth.passkeys`. Every ceremony is two calls: the API issues options for the browser's `navigator.credentials` API and keeps them in the cache (`PasskeyCeremonyStore`), the browser answers, and the API verifies the answer against the options it issued. `App\Modules\Auth\Passkeys\WebAuthn` is the only class that touches the library.

### Managing passkeys

Account-level, like two-factor enrolment (`auth:api`, `person`):

| Route | Body | Effect |
|---|---|---|
| `POST /api/auth/passkeys/options` | | `{ options }` for `navigator.credentials.create()`: `none` attestation, ES256 and RS256, a resident (discoverable) key required, user verification preferred, existing passkeys excluded |
| `POST /api/auth/passkeys` | `name`, `credential` (the `create()` result as JSON) | Verifies and stores the passkey; `201` with `{ id, name, transports, lastUsedAt, createdAt }`. `422` when no registration is in progress, the credential does not verify, or it is already registered |
| `GET /api/auth/passkeys` | | The caller's passkeys |
| `DELETE /api/auth/passkeys/{id}` | | Removes one; another user's is a `404` |

### Signing in with a passkey

Public and `throttle:auth`:

| Route | Body | Effect |
|---|---|---|
| `POST /api/auth/passkeys/login/options` | | `{ options, ceremonyToken }` for `navigator.credentials.get()`. `allowCredentials` is empty, so the options are the same for every caller and reveal nothing about which addresses have accounts |
| `POST /api/auth/passkeys/login` | `ceremonyToken`, `credential`, `deviceName?` | Verifies the assertion, bumps the counter and `lastUsedAt`, records a `passkey` login attempt and answers with the session (`200`). No two-factor challenge follows: a passkey is both factors |

A wrong origin, a bad signature, an unknown passkey or a used ceremony is a `422` on `credential` with one generic message (the library's reason goes to the log), and each failure is recorded in `login_attempts`.

### As a second factor

A registered passkey counts as two-factor, so a password sign-in answers `202` with a challenge and a tenant that requires two-factor is satisfied. To answer the challenge with a passkey, fetch options with `POST /api/auth/two-factor/passkey-options` (`challengeToken`), then post `challengeToken` and `passkey` (the `get()` result) to `POST /api/auth/two-factor/challenge`. That route needs both `auth.two_factor` and `auth.passkeys`.

### Relying party

The relying party id is the SPA's host and the allowed origins are the SPA's origin, both derived from `FRONTEND_URL` unless set. A passkey registered for one relying party id is useless for another, so set these once and keep them.

::tip
Tests drive the real verification path with `tests/Fixtures/Auth/SoftwareAuthenticator.php`, a P-256 authenticator written in PHP that answers both ceremonies.
::

## Configuration

All in `config/security.php`:

| Env | Config key | Default | Meaning |
|---|---|---|---|
| `TWO_FACTOR_ISSUER` | `security.two_factor.issuer` | `APP_NAME` | Account name authenticator apps display |
| `TWO_FACTOR_WINDOW` | `security.two_factor.window` | `1` | 30-second steps either side of now a code is accepted for |
| `TWO_FACTOR_CHALLENGE_TTL` | `security.two_factor.challenge_ttl_seconds` | `300` | Lifetime of a login challenge |
| `TWO_FACTOR_CHALLENGE_MAX_ATTEMPTS` | `security.two_factor.challenge_max_attempts` | `5` | Wrong codes before a challenge is destroyed |
| | `security.two_factor.recovery_codes` | `8` | Recovery codes issued on confirmation |
| `PASSKEY_RP_ID` | `security.passkeys.rp_id` | `FRONTEND_URL`'s host | Domain passkeys are bound to |
| `PASSKEY_RP_NAME` | `security.passkeys.rp_name` | `APP_NAME` | Name shown by the authenticator |
| `PASSKEY_ORIGINS` | `security.passkeys.origins` | `FRONTEND_URL` | Comma-separated origins allowed to answer a ceremony |
| `PASSKEY_TIMEOUT_MS` | `security.passkeys.timeout_ms` | `60000` | Ceremony timeout passed to the browser |
| `PASSKEY_CEREMONY_TTL` | `security.passkeys.ceremony_ttl_seconds` | `300` | Seconds a ceremony's options stay in the cache |
