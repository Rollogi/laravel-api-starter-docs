The `Account` module is self-service on the caller's own account, under `/api/account`. Every route runs on `auth:api` and `person`, never `api.tenant`: a person with several tenants or none must still be able to manage and close their account, and a tenant that requires two-factor must not be able to trap a member in it. None of the Data objects authorises, because the subject is always the caller.

## Endpoints

| Method | Path | Body | Effect | Feature key |
|---|---|---|---|---|
| `PATCH` | `/api/account` | `name` | Renames the caller; returns `{ id, name, email, twoFactorEnabled }` | `account.profile` |
| `PUT` | `/api/account/email` | `email`, `password` | Starts an email change; `202` with `{ email, expiresAt }` | `account.email_change` |
| `GET` | `/api/account/email/confirm/{id}/{hash}` | signed link | Applies the change and redirects to `FRONTEND_URL/email-changed` | `account.email_change` |
| `DELETE` | `/api/account` | `password` | Closes the account; `204` | `account.deletion` |
| `POST` | `/api/account/export` | | Queues an export of everything held about the caller; `202` | `account.export` |

Every route is on `throttle:auth`. The confirmation link is public and proven by its signature (`signed` middleware), because it may be followed on a device that is not signed in.

## Changing the email address

The new address has to be proven before it takes effect, so nothing on `users` changes at request time.

1. `RequestEmailChangeService` re-checks the password and rejects an address another account uses (case-insensitively, through `UniqueUserEmail`) or the caller's current one.
2. It parks the lowercased address in the cache (`PendingEmailChangeStore`) for `EMAIL_CHANGE_TTL_MINUTES` (default 1440, one day) and emails a temporary signed link to the new address (`VerifyNewEmailNotification`). Requesting again replaces the pending address and invalidates the earlier link.
3. Following the link runs `ConfirmEmailChangeService`: the hash must match the pending address (`ConsumePendingEmailChangeAction`, single-use), the address is written and marked verified in one go, and the old mailbox receives `EmailChangedNotification` after commit.

| Outcome | Response |
|---|---|
| Tampered or expired signature | `403` from the `signed` middleware |
| Link already used, or superseded by a newer request | `410 email-change-expired` |
| Address taken between request and confirmation | `422` on `email` |

## Deleting the account

`DeleteAccountService` re-checks the password, then refuses with `422` on `tenants` while the caller is the last administrator of any tenant (`EnsureTenantsKeepAnAdminAction`, which wraps the Tenants module's `EnsureNotLastAdminAction` and names the tenant). The person has to promote someone or delete the tenant first.

Otherwise it leaves every tenant the way the Tenants module does (`RemoveUserFromTenantAction`, so tenant-scoped roles go with the membership), and `DeleteUserAction` revokes every access token, removes any global role or permission grant, and deletes the row.

- Social accounts, passkeys, push devices and notification preferences cascade.
- `audits`, `service_audits` and `login_attempts` keep their rows as history until their own retention prunes them ([Auditing](/kit/auditing)).
- Revoked tokens are removed by the daily `passport:purge`.

## Exporting the account

`POST /api/account/export` dispatches `SendAccountExportAction` to the queue under the caller's execution context. On the worker, `BuildAccountExportAction` assembles `AccountExportData`, and `AccountExportNotification` mails it to the account's address as `account-export.json`. The export holds:

- the profile (`id`, `name`, `email`, `emailVerifiedAt`, `twoFactorEnabled`, `createdAt`);
- memberships, with the roles held in each tenant;
- linked social accounts;
- live sessions;
- push devices, without their tokens;
- notification preferences;
- login attempts.

A project that stores more about its users extends the action and the Data class and rebinds the action in its own module's provider.

## Working across tenants

Account-level work that must look at every tenant (roles in the export, the last-admin check, leaving) goes through the `VisitsUserTenants` trait. It activates each tenant in turn and restores the previous tenant context and permission team id afterwards, so the request's own `service_audits` row stays tenant-less.
