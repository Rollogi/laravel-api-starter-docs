## Health checks

There are two probes:

- `/up` is the framework's **liveness** probe. It answers `200` when PHP boots and is public.
- `GET /api/health` is the **readiness** report, owned by Core's `Health` concern. It says which dependency is down.

```http
GET /api/health
X-Health-Token: <HEALTH_TOKEN>
```

```json
{
  "status": "degraded",
  "checkedAt": "2026-10-22T09:00:00+00:00",
  "checks": [
    { "name": "database", "status": "ok", "message": "Connected (pgsql).", "details": { "connection": "pgsql", "driver": "pgsql" }, "durationMs": 2 },
    { "name": "cache", "status": "ok", "message": "Store redis reads back what it writes.", "details": { "store": "redis" }, "durationMs": 1 },
    { "name": "queue", "status": "degraded", "message": "redis: 12 pending, 3 failed.", "details": { "connection": "redis", "pending": 12, "failed": 3 }, "durationMs": 1 },
    { "name": "mail", "status": "ok", "message": "Mailer smtp accepted a connection.", "details": { "mailer": "smtp", "probed": true }, "durationMs": 40 }
  ]
}
```

The report names drivers, connections and failure messages, so it is never public: the route answers `403 health-forbidden` unless `X-Health-Token` matches `HEALTH_TOKEN`, and to everyone while that variable is empty.

- The overall `status` is the worst of the checks: `ok`, `degraded` or `failed`.
- `failed` answers `503`, so a load balancer can act on the status code alone; `degraded` (failed jobs waiting, for example) answers `200` with the detail.
- Every check runs even after one has failed, and a check that throws is reported as a failed check, not a failed request.
- `ShowHealthService` drops the `LogServiceCall` stage so a monitor polling it does not flood the log.

| Check | What it does |
|---|---|
| `DatabaseCheck` | Runs `select 1` |
| `CacheCheck` | Writes a probe key and reads it back |
| `QueueCheck` | Reads the backlog and the `failed_jobs` count |
| `MailCheck` | Opens and closes a connection to an SMTP mailer; any other mailer is reported as configured, not probed |

### Adding a check

Implement `Rollogi\Core\Health\Contracts\HealthCheck` and list the class in Core's `health.php` config (publish it with `php artisan vendor:publish --tag=rollogi-core-config`):

```php [app/Modules/Search/Health/SearchCheck.php]
use Illuminate\Support\Facades\Http;
use Rollogi\Core\Health\Contracts\HealthCheck;
use Rollogi\Core\Health\Data\HealthCheckResultData;

class SearchCheck implements HealthCheck
{
    public function name(): string
    {
        return 'search';
    }

    public function run(): HealthCheckResultData
    {
        $url = (string) config('services.search.health_url');

        return Http::timeout(3)->get($url)->successful()
            ? HealthCheckResultData::ok($this->name(), 'Search engine answered.', ['url' => $url])
            : HealthCheckResultData::failed($this->name(), 'Search engine did not answer.', ['url' => $url]);
    }
}
```

`HealthCheckResultData` also has `degraded()`, and every constructor takes an optional `details` array.

## Production image

The `Dockerfile` builds on the [Rollogi PHP images](https://docker.rollogi.co.uk): Alpine, Nginx and PHP-FPM, an unprivileged `appuser`, and every PHP, FPM and Nginx setting taken from environment variables. It has two stages:

1. `rollogi/php:8.5` installs the production dependencies with an authoritative classmap.
2. `rollogi/php-nginx:8.5` copies the result to `/app`, serves `public/` on port `8080`, and adds `pdo_pgsql`, `pdo_sqlite` and `sodium` (the image already has `pdo_mysql` and `redis`; Passport's JWT library needs sodium).

The code is root-owned and read-only to the runtime user; only `storage` and `bootstrap/cache` are writable. OPcache is on with timestamp validation off, `APP_ENV=production`, `APP_DEBUG=false` and `LOG_CHANNEL=stderr`, and the memory and upload limits are set through the image's `PHP_*` and `OPCACHE_*` variables, so a deployment can override any of them without a rebuild.

Nothing environment-specific is baked in. `docker/bootstrap.sh` is the image's `APP_INSTALL` hook: before Nginx and PHP-FPM start it builds the config, route and event caches from the container's environment, and runs `migrate --force` when `RUN_MIGRATIONS=true`. Any command replaces the web services, and the image's cron runs the scheduler:

```bash
docker build -t my-api .
docker run --rm -p 8080:8080 --env-file .env.production my-api                                              # web
docker run --rm --env-file .env.production my-api php artisan queue:work                                     # worker
docker run --rm -p 8080:8080 --env-file .env.production -e CRON_COMMAND="php artisan schedule:run" my-api    # web plus scheduler
```

::note
A project created from a release installs rollogi/core from the private `Rollogi/core` repository, so its build needs a GitHub token that can read it. Pass it as a BuildKit secret, which never lands in a layer or the build history:

```bash
COMPOSER_AUTH='{"github-oauth":{"github.com":"<token>"}}' \
    docker build --secret id=composer_auth,env=COMPOSER_AUTH -t my-api .
```
::

The image's own `HEALTHCHECK` probes Nginx at `/health`. Point your orchestrator's readiness probe at `/api/health` with the token, or at the image's `/fpm-ping` on `NGINX_METRICS_PORT` when you only need to know PHP-FPM is up. Logs from Nginx, PHP-FPM and the bootstrap hook arrive on the container's output tagged per service; `LOG_FORMAT=json` switches them to one JSON object per line.

`release.yml` builds the image from every release tag without pushing it; a project adds its registry login and `push: true` to that job. The development image (`Dockerfile.dev`, `compose.dev.yaml`) is covered in [Local development](/getting-started/local-development) and is never the one to deploy.

### Production checklist

| Variable | Why |
|---|---|
| `APP_KEY`, `APP_URL` | Encryption (including stored idempotent results) and generated URLs |
| `FRONTEND_URL` | Every link in an email, CORS, and the passkey relying party |
| `DB_*`, `CACHE_STORE=redis`, `QUEUE_CONNECTION` | Shared counters, locks and caches across instances |
| `MAIL_*` | Mail defaults to the `log` driver |
| `HEALTH_TOKEN` | Without it `/api/health` answers `403` to everyone |
| `TRUSTED_PROXIES`, `FORCE_HTTPS` | Behind a load balancer |
| `FIREBASE_CREDENTIALS`, social provider credentials | Only for the features you use |

Run at least one queue worker and the scheduler: notifications, exports, webhook deliveries and search indexing are queued, and pruning and `passport:purge` are scheduled.

## Octane

`laravel/octane` ships as a dependency with FrankenPHP as the default server (`OCTANE_SERVER`). The production image does not use it; to run it:

```bash
php artisan octane:install --server=frankenphp   # downloads the binary; frankenphp, caddy and rr are gitignored
php artisan octane:start --watch
```

Octane keeps one application alive across requests, so anything a request leaves behind is visible to the next one on the same worker. The kit resets its own state in `config/octane.php`:

- `TenantContext`, `TenantSettings`, `FeatureManager`, `NotificationPreferences` and `IdempotencyContext` are bound with `scoped()`, which Octane forgets between operations, so their memos never outlive a request.
- `ResetTenantState` (`Rollogi\Core\Tenancy\Listeners`) runs on every `OperationTerminated` and clears the Spatie permission team id, which lives on a plain singleton and would otherwise authorise the next request against the previous tenant's roles.
- `request-id`, `running-service` and `running-invocation` are `instance()` bindings, so they are listed under `flush`.
- `WebAuthn` is deliberately a `singleton()`: it holds no request state and keeps its serializer, which a worker then builds once.
- `IntegrationsServiceProvider` guards Saloon's global middleware with a static flag, and `AuditIntegrationCall` keeps per-request state in a `WeakMap`.
- Passport's `TokenGuard` caches the resolved user; Octane's own `FlushAuthenticationState` resets it.

When you add request-scoped state of your own, bind it with `scoped()`, list any `instance()` binding under `flush`, and extend `tests/Feature/Core/Octane/OctaneStateTest.php`, which simulates a reused worker. Set `OCTANE_HTTPS=true` (or `FORCE_HTTPS`) when TLS terminates upstream.

## Configuration

| Env | Config key | Default | Meaning |
|---|---|---|---|
| `HEALTH_TOKEN` | `health.token` | empty | Token `X-Health-Token` must match |
| | `health.checks` | database, cache, queue, mail | Checks `GET /api/health` runs |
| `RUN_MIGRATIONS` | | `false` | Migrate in the image's start-up hook |
| `OCTANE_SERVER` | `octane.server` | `frankenphp` | Octane server |
| `OCTANE_HTTPS` | `octane.https` | `false` | Generate `https` URLs under Octane |
