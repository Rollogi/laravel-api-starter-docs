The `Auth` module owns the `User` model (`App\Modules\Auth\Models\User`) and every way of signing in. Tokens are Passport personal access tokens on the `auth:api` guard; there are no sessions or cookies. Two-factor and passkeys have [their own page](/kit/two-factor-and-passkeys), as does [social sign-in](/kit/social-sign-in).

## Registering and signing in

`POST /api/auth/register` takes `name`, `email`, `password` and `tenantName`, creates the user and a tenant with them as `admin`, queues a verification email, and answers `201` with `AuthSessionData`:

```json
{
  "user": { "id": "...", "name": "Alice", "email": "alice@example.com", "twoFactorEnabled": false },
  "token": "eyJ0eXAiOiJKV1Qi...",
  "tenants": [{ "id": "...", "name": "Acme" }]
}
```

`POST /api/auth/login` takes `email`, `password` and an optional `deviceName` (up to 100 characters, which names the token in the sessions list). It answers `200` with the same shape, or `202` with `{ twoFactorRequired: true, challengeToken, expiresIn }` when the account has two-factor on ([Two-factor and passkeys](/kit/two-factor-and-passkeys)). `GET /api/auth/me` returns `{ user, tenants }`.

The user lookup goes through `FindUserByEmailAction`, which lowercases the address and runs inside `tenancy()->runWithout()`, so it is case-insensitive and never tenant-scoped, because users are global ([Multi-tenancy](/kit/multi-tenancy#users-are-global)).

### Token lifetime

Login, registration and invitation acceptance issue a token that expires after `passport.personal_access_token_lifetime_minutes` (`PASSPORT_PERSONAL_ACCESS_TOKEN_LIFETIME_MINUTES`, default **720**, 12 hours) rather than Passport's one year. After that the API answers `401` and the client signs in again. `bootstrap/app.php` schedules `passport:purge` daily to clear revoked and long-expired rows from `oauth_access_tokens`, so run the scheduler.

## Password policy

Every password the API accepts (registration, reset, change, invitation acceptance) goes through `Password::defaults()`, registered in `AuthServiceProvider`:

- at least `PASSWORD_MIN_LENGTH` characters (default **12**), with no composition rules, because length beats character classes;
- outside the `testing` environment, not present in the haveibeenpwned breach corpus (`PASSWORD_UNCOMPROMISED`, a k-anonymity range lookup over the network; set it to `false` when offline).

Data classes declare it as `#[Password(default: true)]`, never `Min(8)`.

## Changing and resetting the password

`PUT /api/auth/password` takes `currentPassword` and `password`. The current password must match (`422` on `currentPassword` otherwise), and every **other** access token is revoked: the device that proved the old password stays signed in, anyone holding a stolen token does not.

`POST /api/auth/forgot-password` takes `email` and always answers `200`, so it cannot be used to find out which addresses have accounts. It emails a link to `FRONTEND_URL/reset-password?token=...&email=...`. Your frontend posts `email`, `token` and `password` to `POST /api/auth/reset-password`, which resets the password and revokes every existing token.

## Email verification

Verification is **shipped but not enforced**. Registration queues a `VerifyEmailNotification` with a signed link to `GET /api/auth/email/verify/{id}/{hash}`, which marks the address verified and redirects to `FRONTEND_URL/email-verified`. `POST /api/auth/email/verification-notification` sends it again. To require a verified address on a route, add the framework's `verified` middleware:

```php
Route::get('/invoices', ListInvoicesController::class)->middleware(['api.tenant', 'verified']);
```

## Sessions and sign-out

A session is a live Passport access token. Logout, password change and the session routes deliberately sit outside `api.tenant`: they act on the account, and a member of a tenant that requires two-factor must still be able to sign out and revoke a leaked token before enrolling.

| Route | Effect |
|---|---|
| `GET /api/auth/sessions` | `data: [{ id, name, current, createdAt, expiresAt }]` for every live token, newest first. `name` is the `deviceName` sent at login |
| `DELETE /api/auth/sessions/{id}` | Revokes one of the caller's tokens; another user's token id is a `404` |
| `DELETE /api/auth/sessions` | Signs out everywhere else; returns `{ revoked: n }` and keeps the current token |
| `POST /api/auth/logout` | Revokes the current token only |

## Login attempts

Every sign-in attempt, successful or not, is written to `login_attempts` by `RecordLoginAttemptAction`: `user_id` (null for an unknown email), the lowercased `email` tried, `method`, `succeeded`, `ip` and `user_agent`. The method is one of `password`, `two_factor_code`, `recovery_code`, `magic_link`, `passkey` or `social:<provider>` (`LoginMethod`).

`LoginService` and `TwoFactorChallengeService` drop the `WrapInTransaction` stage on purpose: the failed attempt has to survive the rollback that would otherwise follow the `ValidationException`. `LoginAttempt` is prunable; `AuthServiceProvider` schedules `model:prune` for it daily and keeps `LOGIN_ATTEMPT_RETENTION_DAYS` (default **90**).

## Magic links

Passwordless sign-in by email, throttled like login (per IP and per address):

| Route | Body | Effect |
|---|---|---|
| `POST /api/auth/magic-link` | `email`, `deviceName?` | Emails a single-use link to `FRONTEND_URL/magic-link?token=<token>`; `202` with `{ message, expiresIn }`. The answer and the audit row are the same for an unknown address or a machine user |
| `POST /api/auth/magic-link/consume` | `token`, `deviceName?` | Trades the token for a session (`200`) or, with two-factor on, a challenge (`202`). A used, expired or made-up token is a `422` on `token` |

The token lives in the cache (`MagicLinkStore`, hash only) for `MAGIC_LINK_TTL` seconds (default 900) and is forgotten as it is read, so a link works once; if the sign-in then fails on the server's side, the link is put back for what remains of its life. Following it proves control of the mailbox, so an unverified address is marked verified on the way through.

## Configuration

| Env | Config key | Default | Meaning |
|---|---|---|---|
| `PASSWORD_MIN_LENGTH` | `security.password_min_length` | `12` | Minimum password length |
| `PASSWORD_UNCOMPROMISED` | `security.password_uncompromised` | `true` | Reject breached passwords (never in `testing`) |
| `LOGIN_ATTEMPT_RETENTION_DAYS` | `security.login_attempt_retention_days` | `90` | Days a login attempt is kept |
| `MAGIC_LINK_TTL` | `security.magic_link.ttl_seconds` | `900` | Seconds a magic link stays valid |
| `PASSPORT_PERSONAL_ACCESS_TOKEN_LIFETIME_MINUTES` | `passport.personal_access_token_lifetime_minutes` | `720` | Access token lifetime |
| `FRONTEND_URL` | `app.frontend_url` | `http://localhost:3000` | Base of every link in an email |

::warning
Set `FRONTEND_URL` in production. Its default is `http://localhost:3000`, so a forgotten value ships localhost links in every verification, reset, invitation and magic-link email.
::

## Mail and queues

Mail defaults to the `log` driver, so emails land in the application log with no setup; set the `MAIL_*` variables to send for real. The kit's notifications are queued (the account export is sent from a queued action instead), and the default `QUEUE_CONNECTION=database` needs a worker (`php artisan queue:work`). Set `QUEUE_CONNECTION=sync` locally to send inline.
