The kit is an API-only Laravel 13 application split into two layers. **rollogi/core** is shared infrastructure with no business logic: tenancy, feature toggles, the service pipeline, auditing, integrations, health, HTTP conventions. **Modules** under `app/Modules/` hold the features: each one owns its routes, migrations, models, policies and use-cases, and wires itself up in its own service provider.

Authentication is Passport OAuth on the `auth:api` guard. There are no sessions, no Blade views and no Vite.

## Directory layout

```text
app/
└── Modules/
    ├── Account/          # Self-service on the caller's own account
    ├── Auth/             # Registration, sign-in, two-factor, passkeys, social, sessions
    ├── Notifications/    # Push devices, preferences, in-app inbox
    ├── Tenants/          # A tenant and its people: lifecycle, members, invitations, roles, API keys
    └── Webhooks/         # Outbound webhook subscriptions and deliveries
bootstrap/
├── app.php               # Middleware aliases, groups, priority, error rendering
└── providers.php         # AppServiceProvider, CoreServiceProvider, ModuleServiceProvider
config/                   # The kit's own config files (features.php, security.php, ...)
database/migrations/      # Framework and Passport migrations only
packages/                 # Path repository for packages of your own
tests/
├── Feature/
├── Unit/
└── Pest.php              # createUserInTenant(), actingAsMember()
```

A module looks like this inside:

```text
app/Modules/Tenants/
├── Actions/
├── Console/
├── Data/
├── Database/Migrations/
├── Enums/
├── Events/
├── Http/Controllers/
├── Listeners/
├── Models/
├── Policies/
├── Services/
├── routes/api.php
└── TenantsServiceProvider.php
```

Where a module needs them it also has `Notifications/`, `Rules/`, `Exceptions/`, `Http/Middleware/`, and plain collaborator classes in a named subdirectory (the Auth module's `Social/`, `TwoFactor/`, `Passkeys/` and `MagicLink/`, for example).

## How modules are discovered

`bootstrap/providers.php` lists just three providers:

```php [bootstrap/providers.php]
return [
    AppServiceProvider::class,
    CoreServiceProvider::class,     // registers the Core concerns it lists
    ModuleServiceProvider::class,   // discovers app/Modules/*/
];
```

`ModuleServiceProvider` finds every `app/Modules/<Name>/<Name>ServiceProvider` and registers it, in directory-name order. There is no registry to edit: adding a module is adding a directory, and removing one is deleting it.

::warning
The naming is load-bearing. A provider that is not called `<DirectoryName>ServiceProvider` is silently never registered. `tests/Feature/Core/Modules/ModuleLayeringTest.php` fails the build when a module directory holds a provider that is not named after it.
::

To keep modules somewhere other than `app/Modules`, publish Core's `modules.php` config (`php artisan vendor:publish --tag=rollogi-core-config`) and set `path`, `namespace` (matching your `composer.json` autoload) and, for the generators, `tests_path`.

## What a module provider does

A module's provider is responsible for everything the module needs, in its `boot()`:

- `loadRoutesFrom()` for `routes/api.php`, inside `Route::middleware('api')`;
- `loadMigrationsFrom()` for `Database/Migrations`;
- `Gate::policy(...)` for its models;
- `Event::listen(...)` for its listeners;
- `$this->commands(...)` for its console commands;
- singleton or scoped bindings;
- its own `model:prune` schedule for a prunable model, through `callAfterResolving(Schedule::class, ...)`.

```php [app/Modules/Billing/BillingServiceProvider.php]
class BillingServiceProvider extends ServiceProvider
{
    public function boot(): void
    {
        Route::middleware('api')->group(function (): void {
            $this->loadRoutesFrom(__DIR__.'/routes/api.php');
        });

        $this->loadMigrationsFrom(__DIR__.'/Database/Migrations');

        Gate::policy(Invoice::class, InvoicePolicy::class);
    }
}
```

`php artisan make:module Billing` writes this provider for you, see [Use-cases](/kit/use-cases).

::caution
Never register a module's routes or policies in `bootstrap/app.php`, `routes/api.php` or a shared provider. That breaks the self-contained module contract.
::

## Two things that stay outside modules

- **Middleware aliases, groups and the priority list** live in `bootstrap/app.php`, the framework's own composition point and the one place the whole stack is visible. That is where `api.tenant`, `feature`, `permission`, `person`, `cache.public`, `scopes`, `scope` and `deprecated` are defined.
- **Framework and Passport migrations** (cache, jobs, password reset tokens, `oauth_*`) stay in `database/migrations/`. Everything else is owned by the module or Core concern whose table it is.

| Location | Tables |
|---|---|
| `packages/core/src/<Concern>/Database/Migrations/` | `tenants`, `tenant_user`, `tenant_settings`, `feature_settings`, `service_audits`, `integration_audits`, `webhook_events`, `audits`, the Spatie permission tables |
| `app/Modules/<Name>/Database/Migrations/` | Module tables: `users`, `invitations`, `social_accounts`, `login_attempts`, `push_devices`, `webhook_subscriptions`, ... |
| `database/migrations/` | Framework and Passport only |

When you add a table, put its migration next to the code that owns it.

## Core and the kit

rollogi/core is a Composer package. In the kit's own repository it is developed in `packages/core` and symlinked into `vendor/`; a project created from a release installs it from the private `Rollogi/core` repository instead (installing needs access to the private `Rollogi/*` repositories). Core expects a few things from the application around it: a user model that implements `TenantMember`, the `api` guard, the jobs migration, `config/permission.php` with teams on, `config/features.php` as the feature registry, and the middleware and problem renderer composed in `bootstrap/app.php`. See [rollogi/core](/core) for the full contract and the public API.

Core concerns are laid out like modules (each has its own `Models/`, `Database/Migrations/` and `<Concern>ServiceProvider`), but `CoreServiceProvider` registers them from a fixed `CONCERNS` list rather than by scanning. Infrastructure of your own belongs in a module, which is discovered.

Modules can also ship as Composer packages: see [Package modules](/core/package-modules). [rollogi/billing](/billing) and [rollogi/nuxt-ui](/nuxt-ui) are built that way.

## Conventions the tooling enforces

`composer check` runs Pint, Larastan at level 8, Rector (dry run) and Pest, and CI runs it on every push. The rules it holds the code to:

- `declare(strict_types=1)` in every file, single quotes, imports ordered alphabetically, never an inline fully qualified name.
- Models extend `Rollogi\Core\Models\Model`, which gives them UUIDv7 string primary keys. A tenant-owned model also uses `BelongsToTenant` ([Multi-tenancy](/kit/multi-tenancy)).
- Eloquent access is explicit: `getAttribute()`, `getKey()`, `getRelationValue()` and `Model::query()->...`, never magic properties or `User::where(...)`.
- Controllers are single-action invokable classes returning `JsonResponse` with `Response::HTTP_*` constants.
- Every closure and arrow function has typed parameters and a return type.
- Kit classes are not `final`, so a project can extend and rebind them.
- Overriding methods carry `#[Override]`.
- A closed set of values is a string-backed enum with its behaviour as methods.

Every UUIDv7 key sorts by creation time, which is what makes cursor pagination and the merged activity stream cheap: ordering by `id` is stable and chronological without a timestamp column.
