All tenants share one database. Tenant-owned rows carry a `tenant_id` column, and the `BelongsToTenant` trait does the rest:

```php [app/Modules/Billing/Models/Invoice.php]
use Rollogi\Core\Models\Concerns\BelongsToTenant;
use Rollogi\Core\Models\Model;

class Invoice extends Model
{
    use BelongsToTenant;
}
```

- A **global scope** (`TenantScope`) filters every query to the current tenant.
- A **`creating` hook** fills `tenant_id` from the current tenant context.

The context itself, the scope and the membership contract belong to rollogi/core and are described in depth in [Tenancy](/core/tenancy). This page covers how the kit uses them.

::caution
When no tenant context is set, `TenantScope` is a **no-op** and queries are **not filtered**. An authenticated resource route without `api.tenant` sees every tenant's data. Always put authenticated resource routes behind `api.tenant`.
::

## The api.tenant group

```php
Route::middleware('api.tenant')->group(function (): void {
    Route::get('/invoices', ListInvoicesController::class);
});
```

`api.tenant` is defined in `bootstrap/app.php` and runs, in order:

1. `auth:api` - resolves the `User` from the bearer token.
2. `ResolveTenant` - picks the active tenant, sets the tenant context and the Spatie permission team id.
3. `EnsureTwoFactorSatisfied` - refuses a member without two-factor when the tenant requires it ([Two-factor and passkeys](/kit/two-factor-and-passkeys)).
4. `throttle:tenant` - one rate-limit bucket per tenant ([Rate limiting and caching](/kit/rate-limiting-and-caching)).

`ResolveTenant` is moved ahead of `ThrottleRequests` in the middleware priority list so the tenant limiter keys on the resolved tenant. It is also available on its own as the `tenant` alias.

## Resolving the active tenant

The client names the tenant with an `X-Tenant` header:

```http
GET /api/tenants/current/members
Authorization: Bearer <token>
X-Tenant: 01960000-0000-7000-0000-000000000000
```

| Condition | Result |
|---|---|
| `X-Tenant` names a tenant the user belongs to | That tenant is active |
| `X-Tenant` names a tenant the user does not belong to | `403 tenant-forbidden` |
| No header, and the user belongs to exactly one tenant | That tenant is used |
| No header, and the user belongs to none or several | `400 tenant-required` |
| The tenant has `suspended_at` set | `403 tenant-suspended` |

Membership is re-checked on every request, so a member who is removed loses access from their next call without their token being revoked.

## Account-level routes

Some routes act on the **account** rather than on a tenant's data, and run on `auth:api` alone: logout, password change, sessions, two-factor enrolment, passkeys, linked social accounts, email verification resend, push devices, notification preferences and inbox, everything under `/api/account`, and listing or creating tenants. They must work for a person with several tenants or none, and a tenant that requires two-factor must not be able to stop a member from signing out or closing their account.

Such a route touches no `BelongsToTenant` model, and its `service_audits` row has `tenant_id = null`. If the resource has a `tenant_id`, the route belongs behind `api.tenant`.

All of them except logout (and `GET /api/tenants`) also carry the `person` alias (`EnsurePersonPrincipal`), which answers a tenant API key with `403 machine-forbidden`. A key authenticates as a machine user on the same guard, and must not be able to register a passkey, enrol two-factor or found a tenant ([Roles and API keys](/kit/roles-and-api-keys)).

## Reaching the tenant context

Use the `tenancy()` helper, which returns the request-scoped `TenantContext`:

```php
tenancy()->id();          // ?string, the active tenant id
tenancy()->current();     // ?Tenant
tenancy()->has();         // bool
tenancy()->set($tenant);  // make a tenant active
```

`TenantContext` is bound with `scoped()`, so each HTTP request, Octane operation and queued job starts without one. Prefer the helper to `app(TenantContext::class)`.

## Escaping tenant scope

For console commands, jobs and genuinely cross-tenant work, use the explicit escape hatch rather than clearing the context by hand:

```php
tenancy()->runWithout(function (): void {
    // queries here are unscoped
});
```

Actions and services queued with `dispatch()` capture the tenant, the acting user and the request id, and restore them on the worker ([Actions](/core/actions)), so most background work needs no escape at all.

## Users are global

`User` (`App\Modules\Auth\Models\User`) has **no** `tenant_id` and is deliberately not tenant-scoped: the auth principal has to load before any tenant context exists. Do not add a tenant scope to it.

- A user belongs to many tenants through the `tenant_user` pivot, which has a `joined_at` timestamp. `$user->tenants()` comes from Core's `HasTenants` trait, and `$tenant->users()` resolves the model named by `auth.providers.users.model`.
- **Email is globally unique and case-insensitive.** The model lowercases it on write, a unique index on `lower(email)` (`users_email_lower_unique`) backs it, and registering an address that exists in any case is a `422` (`UniqueUserEmail` rule). Look users up through `FindUserByEmailAction`, which lowercases its input, never with a raw `where('email', ...)`.
- `User` is the only authenticatable. An administrator is a user with a role, and a tenant API key is a `User` of kind `machine` ([Roles and API keys](/kit/roles-and-api-keys)). Several kit tables point at `users` (`tenant_user`, `social_accounts`, `passkeys`, `login_attempts`, `push_devices`, `notification_preferences`), so a second principal model would mean polymorphic owner columns throughout; do not start down that road without a product reason.

::note
Moving to per-tenant emails (the same address in two tenants) means replacing the unique email index with one over `tenant_id` and `email`, adding a tenant discriminator to the login request and resolving the tenant before the user lookup. The kit does not do this for you.
::

## Roles are per tenant

Roles and permissions use [spatie/laravel-permission](https://spatie.be/docs/laravel-permission) with **teams enabled, where `team_id` is the tenant id**. The same user can be `admin` in one tenant and `user` in another. Inside an `api.tenant` request `ResolveTenant` sets the team for you; outside a request, set it yourself before assigning a role:

```php
app(PermissionRegistrar::class)->setPermissionsTeamId($tenant->getKey());
$user->assignRole('admin');
```

::warning
Assigning a role without setting the team id first puts it in the wrong tenant, or makes it global.
::

`RolesAndPermissionsSeeder` creates the permissions and two global roles:

| Role | Permissions |
|---|---|
| `admin` | Every permission on the `api` guard: `members.view`, `members.update`, `members.remove`, `members.invite`, `tenant.view`, `tenant.update`, `tenant.delete`, `roles.view`, `roles.manage`, `activity.view`, `api-keys.manage`, `webhooks.manage`, plus any a package creates (rollogi/billing adds `billing.view` and `billing.manage`) |
| `user` | `members.view`, `tenant.view`, `roles.view` |

The two roles are global rows (`tenant_id` is null), so every tenant shares them. A tenant can define roles of its own through the API ([Roles and API keys](/kit/roles-and-api-keys)). The Spatie pivot tables carry a surrogate id plus a unique index rather than a composite primary key, so a global assignment (`tenant_id = null`) can be stored on SQLite, MySQL and PostgreSQL alike.

## Registration creates a tenant

`POST /api/auth/register` creates the user, a tenant named from `tenantName`, the membership, and the `admin` role in that tenant. The response, like login and `/me`, lists every tenant the user belongs to:

```json
{
  "user": { "id": "...", "name": "Alice", "email": "alice@example.com", "twoFactorEnabled": false },
  "token": "...",
  "tenants": [{ "id": "<uuid>", "name": "Acme Corp" }]
}
```

Further tenants are created with `POST /api/tenants` or `php artisan tenant:create` ([Tenants](/kit/tenants)).
