Every endpoint in the kit sits behind a feature key, so any capability can be switched off globally or for one tenant at runtime, without a deploy. A per-tenant policy such as "members must use two-factor" is the same mechanism read from a middleware instead of a route. The resolver itself, `FeatureManager`, belongs to rollogi/core and is described in [Features](/core/features); this page is how the kit uses it.

## The registry

`config/features.php` is the source of truth. Each key maps to a `default` and a `label`:

```php [config/features.php]
return [
    'features' => [
        'auth.register' => ['default' => true, 'label' => 'Public registration'],
        'auth.two_factor.required' => ['default' => false, 'label' => 'Members must have two-factor enabled (set per tenant)'],
        // ...
    ],

    'disabled_message' => 'This feature is disabled.',
];
```

Referencing a key that is not registered throws `Rollogi\Core\Features\Exceptions\UnknownFeatureException`. `make:use-case` adds its key here for you ([Use-cases](/kit/use-cases)), and packages merge their own keys in as defaults.

## Shipped keys

All default to on except `auth.two_factor.required`.

Each module page lists which key guards which route.

## Guarding a route

```php
Route::middleware(['api.tenant', 'feature:billing.invoices'])->get('/invoices', ListInvoicesController::class);
```

When the feature is off, the middleware answers `403` with the `feature-disabled` problem:

```json
{
  "type": "https://api.example.com/problems/feature-disabled",
  "title": "Feature disabled",
  "status": 403,
  "detail": "This feature is disabled.",
  "instance": "/api/billing/invoices",
  "request_id": "...",
  "feature": "billing.invoices"
}
```

The `detail` comes from `features.disabled_message`.

::note
`feature` reads the tenant context if it is already set. Inside `api.tenant`, tenant resolution runs first, so per-tenant overrides apply. On public routes (register, login) there is no tenant, so only global overrides and the default apply.
::

## Resolution order

For a given tenant, the first answer wins:

1. a per-tenant override;
2. a global override;
3. any `FeatureSource` a package has tagged (rollogi/billing's plans, for example);
4. the config default.

Overrides are rows in `feature_settings` (`feature`, `tenant_id`, `enabled`; global rows have `tenant_id = null`). Resolution is memoised per request; `FeatureManager` is request-scoped, so Octane never serves a stale answer.

::warning
`FeatureSetting` must stay global. Do not add `BelongsToTenant` or a tenant scope to it: global overrides and public routes have to resolve before any tenant context exists.
::

## Switching features at runtime

```bash
php artisan feature:list                              # every key with its resolved global state
php artisan feature:list --tenant=<uuid>              # resolved for one tenant

php artisan feature:set auth.register --off           # global override
php artisan feature:set auth.register --clear         # back to the config default

php artisan feature:set auth.login --tenant=<uuid> --off
php artisan feature:set auth.login --tenant=<uuid> --on
php artisan feature:set auth.login --tenant=<uuid> --clear
```

Or in code:

```php
use Rollogi\Core\Features\FeatureManager;

$features = app(FeatureManager::class);

$features->enabled('auth.login', $tenant);           // bool
$features->setGlobal('auth.register', false);
$features->clearGlobal('auth.register');
$features->setForTenant('auth.login', $tenant, false);
$features->clearForTenant('auth.login', $tenant);
```

Changing a key's `default` in `config/features.php` also works, but needs a deploy.

## Adding a feature

1. Register the key:

   ```php [config/features.php]
   'billing.invoices' => ['default' => true, 'label' => 'Invoice management'],
   ```

2. Guard the route with `feature:billing.invoices`.

That is all: the key is immediately available to `feature:list`, `feature:set` and `FeatureManager`. A feature flag that is a policy rather than a route (like `auth.two_factor.required`) is read with `app(FeatureManager::class)->enabled($key, tenancy()->current())` from a middleware or an action.
