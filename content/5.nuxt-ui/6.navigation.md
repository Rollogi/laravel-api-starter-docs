## Nav items

The sidebar comes from the `NavItem`s registered on `UiRegistry`, filtered for the viewer and sorted by `position`:

```php
use Rollogi\NuxtUi\Support\NavItem;

$registry->nav(new NavItem(
    label: 'Invoices',
    to: '/invoices',
    position: 20,
    icon: 'i-lucide-receipt',
    requires: 'invoices.view',
    badgeSource: '/invoices?filter[status]=open',
    badgeDisplay: 'count',
    badgeResolver: CountOpenInvoicesBadge::class,
));
```

| Argument | Holds |
| --- | --- |
| `label`, `to`, `position` | The text, the in-app path and the sort order |
| `icon` | An icon name, such as `i-lucide-receipt` |
| `requires` | The ability the viewer needs to see the item, or `null` |
| `badgeSource` | The endpoint behind the badge, which the renderer may fetch |
| `badgeDisplay` | `count` or `nodeStatus` |
| `badgeResolver` | A `NavBadgeResolver` class that fills the value on the server |
| `tenantFree` | List the item in a manifest served with no tenant too |

The nav is part of `GET /api/ui/routes`, and `GET /api/ui/nav` answers it alone so a sidebar can refresh its badges without reloading the routes. Each item is `{label, to, icon, badge}`, and a badge is `{get, display, value, attention}`.

With no tenant (see [Tenancy](/nuxt-ui/screens#tenancy)), only items built with `tenantFree: true` are listed.

## Badges

A badge needs both `badgeSource` and `badgeDisplay`. Without a resolver, the manifest names the source and display and leaves the renderer to fetch the count. With a `badgeResolver`, the manifest fills in the value, so the frontend need not fetch the list behind it.

A resolver is resolved from the container, takes a `NavBadgeContext` (the `user` and the `tenantId`) and returns a `NavBadgeValue` (the `count`, and for `nodeStatus` whether something needs `attention`):

```php [app/Modules/Invoices/Ui/CountOpenInvoicesBadge.php]
use Rollogi\NuxtUi\Contracts\NavBadgeResolver;
use Rollogi\NuxtUi\Support\NavBadgeContext;
use Rollogi\NuxtUi\Support\NavBadgeValue;

class CountOpenInvoicesBadge implements NavBadgeResolver
{
    public function __invoke(NavBadgeContext $context): NavBadgeValue
    {
        if ($context->tenantId === null) {
            return new NavBadgeValue(count: 0);
        }

        return new NavBadgeValue(count: Invoice::query()->where('status', 'open')->count());
    }
}
```

`tenantId` is null only for a `tenantFree` item on a manifest served with no tenant. Otherwise the tenant is active, so a `BelongsToTenant` model is already scoped.

A resolver that throws is reported and leaves the value `null`; the manifest still answers.

::tip
Count, never load. A resolver runs on every manifest request for every viewer who sees the item, so keep it to one indexed `count()`.
::

## Live updates

To refresh sidebars when a count changes, announce it from the write that changed it:

```php
use Rollogi\NuxtUi\Actions\AnnounceNavChangedAction;

AnnounceNavChangedAction::run(tenancy()->id());   // this tenant's sidebars
AnnounceNavChangedAction::run(null);              // every tenant's
```

Announcements are collected per transaction and sent once after commit:

- however many writes in the transaction announce, one `TeamNavChanged` event goes out;
- a rollback sends nothing;
- outside a transaction it is sent at once;
- a failure to queue it is logged as a warning ("sidebars fall back to polling"), never thrown.

`TeamNavChanged` is a queued broadcast (`ShouldBroadcast`) named `nav.changed`, with an empty payload, on `private-teams.{tenantId}.nav` for each tenant it names. An announcement for every tenant carries `everyTenant`, and the worker reads the tenant ids when it broadcasts, so a change every tenant counts never holds the request while the broadcaster reaches each one. On hearing it, the renderer can refetch `GET /api/ui/nav` for the new values.

A screen's sources can listen too, with `Source::get(...)->stream($channel, $event)`.

## The channel

The package registers the private channel `teams.{teamId}.nav` on the `api` guard. A subscription is allowed only when:

- the request has an active tenant, and `teamId` is that tenant's id;
- the member holds one of `nuxt-ui.nav_channel_abilities`, when any are listed. Empty lets every member of the active tenant listen.

List abilities there when the badges count rows some members cannot see: without a check, hearing `nav.changed` would tell them that such rows were created or deleted.

The package registers the channel but not the broadcasting auth route, which the host owns. That route must resolve the tenant (the client sends `X-Tenant`), or every subscription is refused:

```php
Broadcast::routes(['prefix' => 'api', 'middleware' => ['api', 'api.tenant']]);
```

A queue worker and a configured broadcaster are needed for any of this to reach a browser. See [Installation](/nuxt-ui/installation#broadcasting).
