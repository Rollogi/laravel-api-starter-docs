## Defining a screen

A screen implements `Rollogi\NuxtUi\Contracts\UiDefinition`, with three methods:

```php [app/Modules/Invoices/Ui/InvoicesPage.php]
use Override;
use Rollogi\NuxtUi\Builder\Layout\Page;
use Rollogi\NuxtUi\Builder\Node;
use Rollogi\NuxtUi\Builder\Sources\Source;
use Rollogi\NuxtUi\Contracts\UiDefinition;
use Rollogi\NuxtUi\Support\UiContext;

class InvoicesPage implements UiDefinition
{
    #[Override]
    public function requires(): ?string
    {
        return 'invoices.view';
    }

    #[Override]
    public function discriminators(): array
    {
        return [];
    }

    #[Override]
    public function build(UiContext $context): Node
    {
        return Page::make('Invoices')
            ->source('invoices', Source::get('/invoices'))
            ->children(InvoicesTable::make());
    }
}
```

- **`requires()`** is the ability the viewer needs, or `null` for none. Without it the screen answers `404`, never `403`, and is left out of the manifest, so a viewer cannot tell a screen they may not open from one that does not exist.
- **`discriminators()`** maps query keys to backed enums (`['kind' => InvoiceKind::class]`). A missing or unknown value is a `404`, and `$context->discriminator('kind')` hands the case to `build()`.
- **`build()`** returns the root node, built with the [builder](/nuxt-ui/builder). A page returns a `Page` or `Shell`; an overlay returns a `Modal`, `Slideover` or `ConfirmDialog`.

### The context

`UiContext` is a `readonly` class carrying:

| Property or method | Holds |
| --- | --- |
| `user` | The viewer, typed as Laravel's `Authorizable` |
| `tenantId` | The active tenant's id, or `''` with no tenant |
| `discriminators` | The resolved enum cases, keyed by name |
| `params` | String params from `?params[name]=value` |
| `can(string $permission)` | Whether the viewer holds the ability; every `can` condition is folded through it |
| `discriminator(string $name)` | One resolved case, or `null` |

### Tenant-free screens

A screen that implements the marker interface `Rollogi\NuxtUi\Contracts\TenantFree` always builds with no tenant, whatever tenant the request names: the caller's own account, founding a tenant, an operator's dashboards. Every source, action and endpoint it uses must work without one.

## Registering screens

Register screens on `UiRegistry` from an app module provider's `boot()`:

```php [app/Modules/Invoices/InvoicesServiceProvider.php]
use Rollogi\NuxtUi\Support\NavItem;
use Rollogi\NuxtUi\Support\UiRegistry;

$this->callAfterResolving(UiRegistry::class, function (UiRegistry $registry): void {
    $registry->page('invoices.list', InvoicesPage::class, path: '/invoices');
    $registry->page('invoices.shell', InvoiceShell::class);
    $registry->page('invoices.overview', InvoiceOverviewPage::class, path: '/invoices/{id}', shell: 'invoices.shell');
    $registry->overlay('invoices.refund', RefundModal::class);
    $registry->nav(new NavItem('Invoices', '/invoices', 20, 'i-lucide-receipt', 'invoices.view'));
});
```

| Method | Registers |
| --- | --- |
| `page(string $name, string $definition, ?string $path = null, ?string $shell = null)` | A page or shell. With a `path` it is listed in the route manifest; with a `shell` it renders inside that shell |
| `overlay(string $name, string $definition)` | A modal, slideover or confirm dialog, fetched by name |
| `nav(NavItem $item)` | A sidebar entry; see [Navigation](/nuxt-ui/navigation) |

The rules:

- Names match `^[a-z0-9.-]+$` and are unique across pages and overlays.
- A page in a `shell` is listed only while the viewer may open the shell too.
- Pages are ordered by the application module that defines them, so the manifest does not depend on boot order.
- Params arrive as `?params[name]=value` and reach `build()` as `$context->params`. Builder strings can also name them as placeholders, such as `HttpAction::delete('/invoices/{params.id}')`, for the renderer to fill in.

## Endpoints

All four run on `auth:api` under `/api/ui`:

| Route | Answers |
| --- | --- |
| `GET /api/ui/routes` | `uiVersion`, the routes and the nav the viewer may see |
| `GET /api/ui/nav` | The nav alone, so a sidebar can refresh its badges |
| `GET /api/ui/pages/{name}[?shell=]` | A `page` or `shell` tree; with `shell`, both trees together |
| `GET /api/ui/overlays/{name}` | A `modal`, `slideover` or `dialog.confirm` tree |

Every answer carries `uiVersion`, the [contract version](/nuxt-ui/configuration#the-contract-version). The manifest's `routes` are `{pattern, page, shell}`, and its `nav` items are `{label, to, icon, badge}`. A screen answers `{uiVersion, tree}`, plus `shell` when one was asked for.

The services behind them extend Core's `ReadService`, so each call is authorised, logged and counted like any other read.

## Tenancy

The `/api/ui` routes do not use the kit's `api.tenant` group, because some screens have no tenant. `ResolveOptionalTenant` stands in for it:

1. The tenant is resolved as Core's `ResolveTenant` does: from `X-Tenant`, or the caller's sole membership. The usual `400 tenant-required`, `403 tenant-forbidden` and `403 tenant-suspended` apply.
2. Then `nuxt-ui.tenant_middleware` runs, as the host's `api.tenant` group runs its own middleware. In a kit project that list defaults to `EnsureTwoFactorSatisfied`, so a tenant that requires two-factor answers `403 two-factor-required` here too. Add any other per-tenant requirement of yours to it.

Two cases skip both steps and run with the tenant context cleared, like the kit's account-level routes:

- a `TenantFree` page or overlay, whatever `X-Tenant` says;
- the manifest (`/routes` and `/nav`) of someone who names no tenant and belongs to none. That manifest lists only `TenantFree` routes and nav items built with `tenantFree: true`.

A host with more tenant-free cases, such as an operator outside every tenant or a suspended sole tenant, rebinds `IsTenantFreeManifestAction`.

Requests are throttled on Core's `tenant` limiter, or per user on `ui-user` when there is no tenant.

::warning
A `TenantFree` screen runs with no tenant, so `TenantScope` filters nothing. Never read tenant-owned models from one. See [Multi-tenancy](/kit/multi-tenancy).
::

## Errors

| Status | When |
| --- | --- |
| `404` | An unknown name, a screen the viewer may not open, a missing or unknown discriminator, or a `shell` that does not match the page |
| `400`, `403` | The tenant problems above, and `two-factor-required` from the tenant middleware |
| `429` | The rate limit |

All of them are RFC 9457 problems, like the rest of the API (see [HTTP conventions](/kit/http)).
