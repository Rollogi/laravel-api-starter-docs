`rollogi/nuxt-ui` is server-driven UI for a Nuxt UI renderer. Screens are PHP classes built with a fluent builder: pages, shells, overlays, forms, tables, display nodes, actions and expressions. The API serves them as JSON trees, together with a route and nav manifest filtered by what the viewer may do, and runs the server-side list queries that back its tables.

This package is the PHP side only. The Nuxt renderer that draws the trees, and the JSON Schema of the contract between the two, live with the frontend.

The current release is **1.0.0**, building to UI contract version **1.34** (`UiSchema::VERSION`). It requires PHP 8.5, `laravel/framework` `^13.32`, `rollogi/core` `^1.1`, `spatie/laravel-data` `^4.23` and `spatie/laravel-query-builder` `^7.3.2`.

## Why server-driven

The API already knows who the viewer is, which tenant they are in and what they may do. With the screens defined next to the endpoints they call:

- **Permissions are decided once.** A button guarded by `Expr::can('invoices.delete')` is folded on the server, so the tree a viewer receives never names an action they may not take.
- **Screens ship with the API.** A new page, column or form field is a PHP change, deployed with the endpoint it needs; the renderer does not change.
- **The frontend stays generic.** It renders node types from the contract, rather than knowing about invoices or members.

## How it fits together

```
UiDefinition classes          your screens: build(UiContext): Node
        |
UiRegistry                    pages (with a path and an optional shell), overlays, nav items
        |
/api/ui/routes, /nav          the manifest the viewer may see, with nav badges
/api/ui/pages/{name}          one page (and its shell) as a JSON tree
/api/ui/overlays/{name}       one modal, slideover or confirm dialog
        |
Nuxt UI renderer              draws the tree, calls your endpoints, refreshes sources
```

The package installs as a [package module](/core/package-modules), so its routes and middleware are wired for you, and every service runs through Core's [read pipeline](/core/service-pipeline).
